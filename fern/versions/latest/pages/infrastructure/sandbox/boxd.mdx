The `boxd` provider runs each sandbox on its own [boxd](https://boxd.sh?ref=Gym) machine: a
microVM with Ubuntu 24.04, a Docker daemon, and a 100 GB disk. It uses the `boxd` Python SDK.

When `SandboxSpec.image` is set, the provider pulls the image with the machine's Docker daemon
and runs commands in one container started from it, so tasks see exactly the image's filesystem,
user, and tools. When `image` is omitted, commands run directly on the machine.

## Setup

Install the boxd extra in the environment that creates sandboxes:

```bash
uv sync --extra boxd
```

For a package install, use:

```bash
pip install "nemo-gym[boxd]"
```

The provider requires `boxd>=0.3.1`. It is a separate extra from `sandbox` because the SDK talks
gRPC and brings `grpcio` and `protobuf`.

### Get service access

Create an API key with the [boxd CLI](https://docs.boxd.sh/cli/authentication?ref=Gym#api-keys):
`boxd auth keys create <name> --org <org>`. A key belongs to one organization, and the machines it
creates belong to that organization. Set it in the host environment through your secret manager:

```bash
export BOXD_API_KEY="your-api-key"
export BOXD_ORG="your-org"        # optional, the key's organization
export BOXD_REGION="nyc"          # optional, fra or nyc
```

The shipped config leaves `connection.api_key` unset, so the SDK reads `BOXD_API_KEY` from the
environment and the key never appears in a resolved or dumped config. `mini_swe_agent_2` forwards
`BOXD_API_KEY` to its Ray workers the same way it forwards `E2B_API_KEY`.

## Provider Config

NeMo Gym ships a boxd config at `nemo_gym/sandbox/providers/boxd/configs/boxd.yaml`. It defines a
top-level `sandbox` block that agents reference with `sandbox_provider: sandbox`:

```yaml
sandbox:
  default_metadata:
    sandbox-api: boxd
  boxd:
    connection:
      org: ${oc.env:BOXD_ORG,null}
      region: ${oc.env:BOXD_REGION,null}
    create:
      from_snapshot: null
      vcpu: null
      memory: null
      isolated: true
      auto_suspend_timeout: 0
      name_prefix: nemo-gym-
      labels: {}
      ready_timeout_s: 180.0
      image_pull_timeout_s: 1200.0
      always_pull: false
      max_lifetime_s: 3600.0
    exec:
      default_timeout_s: 180.0
      shell: null
    operations:
      retries: 2
      retry_delay_s: 1.0
      retry_max_delay_s: 10.0
    attribution:
      enabled: true
      key_prefix: nemo-gym.nvidia.com/
```

Pass the provider config beside the agent and model configs:

```bash
gym env start \
  --config responses_api_agents/mini_swe_agent_2/configs/mini_swe_agent_2.yaml \
  --config nemo_gym/sandbox/providers/boxd/configs/boxd.yaml \
  --config responses_api_models/vllm_model/configs/vllm_model.yaml
```

## First Run

```python
import asyncio

from nemo_gym.sandbox import AsyncSandbox, SandboxSpec


provider_config = {"boxd": {"connection": {"region": "nyc"}}}

spec = SandboxSpec(
    image="python:3.13-slim",
    workdir="/sandbox",
    files={"/sandbox/hello.py": "print('hello from boxd')\n"},
    resources={"cpu": 2, "memory_mib": 8192},
)


async def main() -> None:
    sandbox = AsyncSandbox(provider_config, spec)
    try:
        await sandbox.start()
        result = await sandbox.exec("python hello.py", timeout_s=60)
        print(result.return_code, result.stdout)
    finally:
        await sandbox.stop()


asyncio.run(main())
```

## Relevant `SandboxSpec` Fields

| Field | boxd behavior |
| --- | --- |
| `image` | Pulled with `docker pull` on the machine (a `docker://` prefix is dropped) and run as one container with host networking. Omit it to run commands on the machine. |
| `entrypoint` | Container mode only. Replaces the image entrypoint, like the `docker` provider. Without it, the container runs a keep-alive shell. |
| `workdir` | The container's working directory, or a directory the provider creates on the machine. |
| `env` | Set on the container, or passed to every command on the machine. |
| `resources` | `cpu` and `memory_mib` pick the smallest machine size that holds them: 1 vCPU / 4 GiB, 2 / 8, 4 / 16 or 8 / 32. `disk_gib` up to 100 is accepted. `gpu` is refused. |
| `ttl_s` | boxd deletes the machine when the lifetime ends, even if `stop()` never runs. When it is unset, `create.max_lifetime_s` applies (3600 seconds by default). |
| `metadata` | Becomes machine labels, next to `create.labels` and job attribution. |
| `ports` | Not supported; the provider refuses a spec that sets them. |
| `provider_options` | `from_snapshot` overrides `create.from_snapshot` for one sandbox. `resource_requests` is accepted and ignored: the machine size comes from `resources`. |

`exec(user=...)` maps to `docker exec --user` in a container (`root` becomes `0`). On the machine,
commands run as the machine's user `boxd`, and any other user goes through `sudo`.

## Snapshots

`create.from_snapshot` starts each machine from a boxd snapshot instead of the default image. Make
one from a machine that already pulled your task images or installed your dependencies, and new
sandboxes skip that work. The provider skips `docker pull` when the machine already has the image;
set `create.always_pull: true` to pull anyway. A machine created from a snapshot keeps the
snapshot's size, so `resources` is ignored with a warning.

## Timeouts

A command that outlives `timeout_s` returns `return_code=124` and `error_type="timeout"`. On the
machine, boxd stops the command's process group at the deadline. In a container, the deadline ends
the `docker exec` client, and the process inside the container ends when the sandbox stops, as with
the `docker` provider.

Machine creation is never retried, and a command that may have started is never run again, because
either may already have taken effect. A command whose stream ends without an exit status raises
`provider_command_outcome_unknown`. Readiness, delete, connect, pause, resume, and file calls retry
transport failures `operations.retries` times. Those are the only retries: the provider turns off
the SDK client's own, so the two never multiply.

Long silent commands get a keepalive: a command with a deadline over 15 minutes, or none, writes a
short marker to stderr every 5 minutes. The marker is unique to the call, and the provider removes
it from the command's stderr, so the output you get is the command's own.

## Lifetime

Every machine carries a lifetime, and boxd deletes the machine when it ends, whether or not
`stop()` ran. The lifetime is `SandboxSpec.ttl_s` when the spec sets it, and `create.max_lifetime_s`
otherwise: 3600 seconds in the shipped config, the same default as the E2B provider's
`create.timeout_s`. It counts from creation and keeps counting while a machine is paused. Raise it
for longer work, or set `create.max_lifetime_s: null` to create machines without a lifetime when
`ttl_s` is unset.

## Pause and Resume

`pause()` hibernates the machine: memory and disk are kept, so the container and any background
processes continue where they were after `resume()`. A hibernated machine does not use compute.
`status()` reports `paused` while it sleeps.

## Errors

Allocation, readiness, lifecycle, and transport failures raise `NgFailureEvent` with
`boundary="sandbox"` and `provider="boxd"`:

| Observation | `failure_kind` |
| --- | --- |
| The API key was refused or lacks permission | `provider_credentials_rejected` |
| Rate limit or organization quota | `provider_quota_exhausted` |
| boxd could not be reached | `provider_unavailable` |
| The machine did not answer a command within the ready deadline | `provider_create_timeout` |
| `docker pull`, `docker run` or a file copy exited nonzero | `provider_setup_failed` |
| A command's stream ended without an exit status | `provider_command_outcome_unknown` |
| The container did not answer the readiness probe | `provider_not_ready` |

When create fails after the machine exists, or the caller is cancelled, the provider deletes the
machine before raising. A create call that ends without an answer may still make its machine, so
the provider looks for it by name for 15 seconds and deletes it when it appears. If a delete fails,
or the machine appears later than that, its lifetime removes it. Command exits, including nonzero
exits, return `SandboxExecResult`.

## Security and Isolation

Machines are created with `isolated: true`: they cannot reach other machines of the organization,
and they hold no boxd credentials, so code in the sandbox cannot use the API key. The key stays in
the process that creates sandboxes. Outbound internet access is available for package installs and
image pulls.

Values in `SandboxSpec.env` reach the sandbox, so pass only what the workload needs. `stop()` deletes
the machine, and the machine's lifetime (see [Lifetime](#lifetime)) deletes machines that a crashed
process leaves behind. Use
`labels` and job attribution to find a run's machines with `boxd.machines.list(labels=...)`.
