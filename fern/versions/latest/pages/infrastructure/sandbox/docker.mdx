The `docker` provider runs each sandbox as one long-lived container on the local Docker daemon. It shells out to the `docker` CLI (`docker run`, `docker exec`, `docker cp`, `docker rm`), so it needs a running daemon but no OpenSandbox server, control plane, or Kubernetes. Use it for local development, CI, and single-machine setups where Docker is the available runtime.

## Setup

Install Docker and make sure the `docker` binary is on `PATH` with a running daemon. The provider does not install or start Docker; constructing it raises `RuntimeError` if the binary is missing, and `create()` fails if the daemon is unreachable.

Images can be any reference the daemon can run, such as `ubuntu:22.04`, `python:3.13.14-slim`, or a registry reference. An Apptainer-style `docker://` prefix is tolerated and stripped. GPU passthrough needs the NVIDIA Container Toolkit; CPU and memory limits need cgroups.

## Provider Config

NeMo Gym ships a Docker provider config at `nemo_gym/sandbox/providers/docker/configs/docker.yaml`. It defines a top-level `sandbox` block that agents reference with `sandbox_provider: sandbox`.

```yaml
sandbox:
  default_metadata:
    sandbox-api: docker-cli
  docker:
    create:
      keepalive_shell: /bin/sh
      keepalive_cmd: "while :; do sleep 2147483647; done"
      start_timeout_s: 600
      use_init: true
      apply_resource_limits: true
      # Isolation knobs -- opt in when running untrusted code (see Isolation and Security):
      # network: none
      # read_only: true
      # cap_drop: ["ALL"]
      # security_opt: ["no-new-privileges"]
      # pids_limit: 512
    exec:
      default_timeout_s: 180
      concurrency: 32
      # exec_shell: /bin/bash   # null auto-detects bash, then falls back to sh
    probe:
      command: printf docker-sandbox-ready
      expected_stdout: docker-sandbox-ready
      timeout_s: 30
      deadline_s: 60
      stable_count: 1
```

Run an agent with the provider config by passing it alongside the agent and model configs:

```bash
gym env start \
  --config responses_api_agents/mini_swe_agent_2/configs/mini_swe_agent_2.yaml \
  --config nemo_gym/sandbox/providers/docker/configs/docker.yaml \
  --config responses_api_models/vllm_model/configs/vllm_model.yaml
```

The provider constructor accepts three optional config sections:

| Section | Purpose |
| --- | --- |
| `create` | Keep-alive command, `docker run` start timeout, `--init` zombie reaping, isolation flags (network, read-only root, dropped capabilities, security options, pids limit), and CPU/memory limit behavior. |
| `exec` | Per-command timeout, the shell used for `<shell> -c <command>` (auto-detected when unset), extra `docker exec` flags, and subprocess concurrency. |
| `probe` | Post-create command probe used to verify command execution before the sandbox is returned. |

## SandboxSpec Provider Options

Set Docker-specific create options under `SandboxSpec.provider_options`, or under `sandbox_spec.provider_options` in an agent config:

```yaml
sandbox_spec:
  provider_options:
    volumes:
      - /datasets/swebench:/datasets/swebench:ro
    run_args: ["--shm-size", "1g"]
```

| Option | Purpose |
| --- | --- |
| `volumes` | A `src:dst[:opts]` bind-mount string or list of them, added as `-v` at `docker run`. |
| `run_args` | Extra raw flags appended to `docker run` for this sandbox. |

## Relevant SandboxSpec Fields

| Field | Docker behavior |
| --- | --- |
| `image` | Required. Any image the daemon can run. A `docker://` prefix is stripped. |
| `env` | Passed as `--env KEY=VALUE` at `docker run` and re-applied on each `exec()`. |
| `workdir` | `-w` at `docker run` (created if absent) and the default `exec()` working directory. |
| `files` | Seed files uploaded before the first command. |
| `resources` | Mapped to CPU, memory, and GPU flags (see Resource Mapping). |
| `entrypoint` | Overrides the keep-alive: the container runs this as its main process instead. |
| `provider_options` | `volumes` and `run_args`, applied per-sandbox. |
| `ttl_s` | Max lifetime: the keep-alive sleeps for `ttl_s` and the container self-removes (`--rm`) on exit. Ignored when a custom `entrypoint` owns the container lifetime. |

## Resource Mapping

`SandboxResources` is translated into Docker CLI flags when `create.apply_resource_limits` is enabled:

| SandboxResources field | Docker flag |
| --- | --- |
| `cpu` | `--cpus <value>` |
| `memory_mib` | `--memory <value>m`, plus a matching `--memory-swap` so the limit is a hard cap rather than doubled through swap. |
| `gpu` | `--gpus <count>` when nonzero (needs the NVIDIA Container Toolkit). |
| `disk_gib` | No direct flag; ignored. |
| `gpu_type` | No direct flag; ignored. |

## Lifecycle

The provider runs one detached container per sandbox:

| Operation | Docker command |
| --- | --- |
| Create | `docker run -d --name nemo-gym-<uuid> --label nemo-gym.sandbox=1 --init [flags] --entrypoint <shell> <image> -c <keepalive>` |
| Exec | `docker exec [-w cwd] [--env ...] [--user ...] <name> <shell> -c <command>` |
| PTY session | `docker exec -i [-t] [-w cwd] [--env ...] --env NEMO_GYM_PTY_SESSION=<session id> [--user ...] <name> <shell> -c <launcher> <pid file> <fallback pid file> <program>`, the client under a host pseudo-terminal (see Interactive Terminals) |
| Status | `docker inspect -f '{{.State.Status}}' <name>` |
| Close | `docker rm -f <name>` |

Containers are named `nemo-gym-<uuid>`, and the image `ENTRYPOINT` is overridden with a keep-alive command so images that define their own entrypoint (common for SWE benchmark images) stay up across `exec()` calls. State written by one command is visible to later commands in the same sandbox. `--init` inserts a minimal init process so the many short `docker exec` children are reaped instead of accumulating as zombies.

## File Transfer

Uploads and downloads use `docker cp` in both directions, creating the target's parent directory first on upload. Uploaded files are owned by `root`; read them as root or `chown` them for a non-root user. Download any files you need before stopping the sandbox — stopping force-removes the container.

## Interactive Terminals

The provider implements `SupportsSandboxPty`, so `await sandbox.pty.create(...)` and `await sandbox.pty.exec(...)` work on Docker as they do on OpenSandbox, and so does the interactive sandbox shell (`python -m nemo_gym.sandbox.shell`). A harness that drives a terminal session, a Terminus-2-style PTY harness say, can build on them; the Terminus-2 sandboxed agent shipped in this repository drives tmux over `exec` and does not use them. A session is one `docker exec -i -t` client process running under a host pseudo-terminal of its own: the CLI sees a terminal, allocates one in the container and forwards bytes both ways, and the session reads and writes the host terminal's master side. `rows`/`cols` size the host terminal before the client starts, and the CLI applies that size to the container's terminal when the exec starts, so a program that reads the size at once sees the requested one; `resize()` changes the size and sends the client `SIGWINCH`, which the CLI turns into a resize of the container's terminal. `cwd`, `env` and `user` map to `-w`, `--env` and `--user` as for `exec()`. `pty=False` runs the client on plain pipes, so `read()` carries stdout and `read_stderr()` stderr.

The session's program starts through a one-line launcher that records its pid in `/tmp/.nemo-gym-pty-<session id>.pid` inside the container, or in `/dev/shm/.nemo-gym-pty-<session id>.pid` when `/tmp` refuses the write (a container run with `read_only: true` and no tmpfs on `/tmp`; `/dev/shm` is a writable tmpfs in every container that does not run with `--ipc=none`), and then `exec`s the program (the shell itself when `create()` names no command: `bash` when the image has it, else `sh`). That pid is how `send_signal()` and `close()` reach the process. A session whose pid can be recorded in neither place could be neither signalled nor cleaned up, so the launcher does not start it: it prints `nemo-gym: cannot record the pid of this PTY session in ...` on stderr (the terminal in PTY mode) and exits 1, and the session ends at once with that message (`create_pty()` itself returns as soon as the client is spawned, without a round trip). The record is read when `send_signal()` or `close()` first needs it, and the read waits up to two seconds for the launcher to write it, because a call issued right after `create_pty()` reaches the container through a second `docker exec` that races the session's own to the daemon. The read is bounded against the record's owner too: a record that is not a regular file (a FIFO, or a link to a device, put at the path by the session's user) is refused at once rather than opened, the file is opened on a pinned descriptor and tested again there, so a swap of the path after the test cannot hand the read something that blocks, at most 32 bytes are read, and the exec that reads it runs under a 30-second timeout of its own (`PID_READ_TIMEOUT_S`) instead of `exec.default_timeout_s`; the session's user can make its record useless, never make `send_signal()` or `close()` wait on it. `send_signal("SIGINT" | "SIGTERM" | "SIGKILL" | "SIGQUIT" | "SIGHUP")` runs `kill` through a second `docker exec` as root, addressed in PTY mode to the foreground process group of the session's terminal (read from `/proc/<pid>/stat`), which is what a key press would reach: the program of a command session, or the job an interactive shell is running (the idle shell itself when there is none). A shell with job control runs each job in a process group of its own, so a signal to the shell's group would never reach the running command; a pipe session has no terminal, and there the signal goes to the process's own group and then the process. Because a docker client that goes away does not end the process it started, `close()` of a live session ends it through one more exec: `SIGHUP` to the recorded process's group, up to a second for a shell to relay the hangup to its jobs (under job control the foreground and the background jobs of an interactive shell sit in process groups of their own, which a signal to the shell's group never reaches), then `SIGKILL` to every process still in the recorded process's session; both pid paths are removed with it. `close()` of a session whose process exited only removes them. The pid file is written by the session's own user, who can rewrite it or replace it by a link to a file it does not own (in a world-writable `/tmp` a hard link keeps the linked inode's owner, so the file's owner is no identity either), so neither its content nor its owner is trusted as such: it is read once, as the session's own user (`/proc/<pid>/environ` is readable by the process's own uid but not by a root without `CAP_SYS_PTRACE`, which Docker's default capability set does not grant, so a root-side read would fail for every non-root session; the `kill` and the cleanup run as root and need no added capability), and followed only when it names a plain pid above 1 whose process carries the session's marker in its environment (`NEMO_GYM_PTY_SESSION=<session id>`, set by the session's own `docker exec --env`, which a process can pass only to its own children) and whose parent is outside the container (`PPid` 0 in the container's pid namespace, true of a process the runtime injected and of nothing started inside it, the agent's own children included) and, in PTY mode, leads its session; otherwise `send_signal()` raises `SandboxPtyError` and `close()` leaves the process to the container's removal. A rewritten or relinked file can therefore never aim the root-side `kill` at a process the session did not start. The in-container `kill` lines are spelled for busybox `sh` as well as dash and bash (`kill -INT -<pgid>`), since `sh` is busybox in Alpine-based images. `wait_exit()` returns the program's exit status as `docker exec` reports it. A client that exits without having started the program (the daemon refused the exec: the container is paused or gone, or the daemon is unreachable, told by the client's own stderr with the same lines that make `exec()` return `error_type="sandbox"`) ends the session with `SandboxPtyError` from `wait_exit()` and `read()` instead of reporting the client's exit code as the program's, so `sandbox.pty.exec()` raises where `sandbox.exec()` returns the runtime sentinel; in PTY mode the client's own stderr is kept apart from the terminal's output for that, in pipe mode it is the program's stderr too and is classified as `exec()` classifies its stderr.

Sessions live in the Gym process, not in the sandbox: there is no re-attach by id from another process (`SupportsSandboxPtyAttach` is not implemented), and `pty.exec(detach=True)` runs attached, since there is no proxied connection to spare between polls. `send_signal()` and `close()` rely on the container's own pid namespace (`PPid` 0 marks the runtime's execs), so a container that shares the host's (`--pid=host` through `extra_run_args`) cannot be signalled or cleaned up through them, and neither can a session whose program changes its user or `exec`s a setuid program (`su`, `sudo -i`): its environment is no longer readable by the session's user, so `send_signal()` raises and `close()` leaves the process to the container's removal. A record the session's user has made unusable (rewritten, relinked, or replaced by something that is not a regular file) is refused, not waited on: `send_signal()` raises within the two-second wait and `close()` only removes the record. The pid record needs a writable `/tmp` or `/dev/shm`: under `read_only: true` without a tmpfs on `/tmp` it goes to `/dev/shm` (a file on the host's `/dev/shm` under `--ipc=host`), and a container with neither (`--ipc=none` as well) cannot host a PTY session; it ends at once with the launcher's message. Session clients are long-lived and are not counted against `exec.concurrency`. Stopping the sandbox releases its sessions before `docker rm -f`; `aclose()` on the provider closes any still open.

## Isolation and Security

<Warning>
Docker containers share the host kernel. This is process and namespace isolation, not a virtual machine, and is not a hard boundary for hostile code. For adversarial or untrusted workloads, run Docker on a disposable VM or use a stronger runtime such as gVisor, Kata Containers, or a microVM.
</Warning>

- Never run with `--privileged` and never mount the Docker socket into the sandbox; either grants host root.
- Networking is on by default because most tasks need egress (pip, git). Set `network: none` to cut it entirely, or `network: <name>` to attach a locked-down internal network.
- Harden with `read_only: true`, `cap_drop: ["ALL"]`, `security_opt: ["no-new-privileges"]`, and `pids_limit: <n>` as a fork-bomb guard. Enforce `resources` so one sandbox cannot starve the host. `read_only: true` leaves `/tmp` read-only too (add `extra_run_args: ["--tmpfs", "/tmp"]` for programs that need one); PTY sessions keep working, their pid record moves to `/dev/shm` (see Interactive Terminals).
- Rootless Docker narrows the blast radius (container root is not host root) and is recommended for shared machines; `docker cp` ownership and some `--user` behaviors differ under it.
- Every container is labeled `nemo-gym.sandbox=1`. Reap leaks from an unclean shutdown with `docker rm -f $(docker ps -aq --filter label=nemo-gym.sandbox=1)`.

## User and Runtime Notes

The neutral `user` argument to `exec()` maps onto `--user`:

| `user` value | Behavior |
| --- | --- |
| `None` | Run as the image's default user. |
| `"root"` or `0` | Run as `--user 0`. |
| Other user or uid | Passed through as `--user <value>`. |

By default `exec_shell` is unset, so the provider auto-detects `bash` once the container is ready (conda and SWE-bench setup commands use `source`, which POSIX `sh`/dash lack) and falls back to `sh`. Pin `exec_shell` to `/bin/sh` or `/bin/bash` to skip the per-create probe.

Command failures return `SandboxExecResult` with the command's exit code. A command timeout returns code `125` with `error_type="timeout"`, and a docker runtime failure — daemon down or container gone, detected via stderr markers — returns code `125` with `error_type="sandbox"`. A timed-out command's in-container process is reaped when the sandbox is closed, since `docker rm -f` stops the whole process tree.
