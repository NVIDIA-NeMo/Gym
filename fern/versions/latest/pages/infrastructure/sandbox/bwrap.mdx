The `bwrap` provider runs each sandboxed command under [bubblewrap](https://github.com/containers/bubblewrap) on the host of the Gym process. In practice that host is usually a Slurm/pyxis container of the task image. A sandbox is a directory, `<base_dir>/<id>/{workspace,tmp,home}`, so there is no long-lived container process, no daemon and no image unpack. Every `exec` spawns a fresh `bwrap` with these properties:

- **Namespaces.** User, pid, ipc and uts namespaces are new. The network namespace is also new unless `network: host`.
- **Capabilities.** All are dropped (`--cap-drop ALL`).
- **Filesystem.** The host's system directories are bound read-only and the root is remounted read-only. Only the sandbox's own workspace, `/tmp` and home are writable.

## Setup

Use a pinned bwrap binary and pass its absolute path. Sandboxes need unprivileged user namespaces. Inside pyxis, add `/proc:/proc` to `--container-mounts`. Otherwise bwrap fails with "Can't mount proc … Operation not permitted".

```yaml
sandbox:
  bwrap:
    bwrap_path: /abs/path/to/bwrap-0.11.2/bwrap
    base_dir: /raid/nemo-gym-bwrap   # node-local storage
    workdir: /workspace
    network: host                    # default: none (loopback only)
    mounts:
      - {src: /path/to/tools, dst: /tools, ro: true}
```

The provider README (`nemo_gym/sandbox/providers/bwrap/README.md`) has the full config reference: read-only bind lists, environment whitelist, concurrency and timeouts.

## Behavior

| Operation | bwrap behavior |
| --- | --- |
| Create | Creates the sandbox directory (mode 0700). With `probe_on_create` (the default), runs `true` once as a readiness probe. |
| Exec | `bwrap <flags> -- /bin/bash -c <command>`, in `--chdir <cwd or workdir>`. The environment is whitelisted, and GPUs are hidden (`CUDA_VISIBLE_DEVICES=""`, `NVIDIA_VISIBLE_DEVICES=void`, fresh `/dev`). |
| Timeout | SIGKILLs the bwrap process group, which tears down the command's whole pid namespace. Returns `error_type="timeout"`. |
| Cancel | The same kill, then re-raises `CancelledError`. |
| Process proof | `AsyncSandbox.exec_processes_terminated()` is True only when no exec of the sandbox is queued, starting or running and every recorded bwrap process and namespace init is gone (`SupportsSandboxExecScopedProcesses`). |
| Upload / download | Host-side file I/O. Paths may be under the workdir, `/tmp`, the home path or an extra mount. `..` and symlinks are refused. |
| Status | `running` while the directory exists. |
| Stop | Refuses new execs, kills every recorded bwrap process of the sandbox, waits for this instance's execs that are about to spawn, then deletes the directory. |

bwrap still reports setup failures through the compatibility classes (`SandboxCreateError`, error-valued exec results); it is listed under [Required provider migrations](./index#required-provider-migrations) for the failure-event contract.

Processes never outlive their exec, so there are no background services, endpoints or PTYs. `user`, `entrypoint` and `resources.gpu` are rejected. `image`, `ttl_s` and the cpu, memory and disk limits are ignored with a warning.

## Sharing a sandbox

`serialize()` returns `{provider, host, uid, base_dir, sandbox_id, workdir, network}`. `AsyncSandbox.connect` with a `bwrap` provider of the same config accepts it only on the same host and uid, with the same `base_dir`. The sandbox directory and its state file must also still exist. This lets a resources server create a task sandbox that an agent server in the same container borrows.

Each exec has its own pid namespace, so a pid recorded by one exec cannot be signalled from another exec. Stop sandboxes through the provider rather than with `kill` commands run in later execs.

## Isolation limits

All sandboxes share the Gym process's uid and host. The namespaces, the read-only binds and `--cap-drop ALL` do the isolating, with these limits:

- **One exec is one pid namespace.** A sandboxed command cannot signal processes outside its exec: the Gym servers, other sandboxes or other execs. Inside one exec, everything shares the namespace. A harness that runs as one long exec (a Codex episode) can therefore be ended by its own tool commands, for example `kill -9 -1` or `pkill -f codex`. Only the exec's init (bwrap) and the calling shell are spared. Gym's harness supervisor ignores stop signals it did not request, and codex_agent's `tool_pid_namespace` runs tool commands in a nested pid namespace; see [the codex_agent README](https://github.com/NVIDIA-NeMo/Gym/tree/main/responses_api_agents/codex_agent#tool-commands-versus-the-harness).
- **`network: host` is not an isolation boundary.** The sandbox shares the host's network namespace, loopback included, so it can reach every service the Gym process can. With Ray enabled, the head Gym starts serves its dashboard and Jobs API on `127.0.0.1:8265` without authentication, so sandboxed code can submit a Ray job that runs as the Gym uid outside every namespace. Use `network: none` for code that needs no network, and keep untrusted code away from hosts that run a Ray head.
- **No resource limits.** The provider sets no cgroup or rlimit bounds. A fork bomb or a memory blow-up in an exec counts against the Gym server's uid and job cgroup. It can stop the server from starting threads or get it OOM-killed before the exec timeout fires. Bound a task's commands yourself (`prlimit` or `ulimit` in the command) when that matters.
