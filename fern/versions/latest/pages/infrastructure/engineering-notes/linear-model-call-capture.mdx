This note explains why [model-call capture](/main/model-server/model-call-capture) grew with the square of a long agent
session, and the two opt-in settings that keep it linear on disk and bounded in memory:
`model_call_capture_format: delta` and `model_call_payloads: reference`. A third, `row_media: reference`, stores each
image of a finished rollout row once (see [Images in finished rows](#images-in-finished-rows)). Defaults are
unchanged.

## The problem

An agent re-sends its whole conversation on every model call. Capture stored each request in full, so a rollout's
capture file is about `0.7 × calls × last request size`. Codex also re-sends every earlier tool-output screenshot,
2-4 MB of base64 each, on every call.

A Terminal-Bench Science run (DeepSeek V4.1 Flash with Codex, 70 sessions of 8 hours) wrote 60 GB of captures in its
first hour. One file reached 25.9 GB, with single requests of 90 MB. A text-only session grows by about 80 MB per hour;
a session with screenshots by up to 26 GB per hour.

When a rollout finished, the merge parsed its whole capture into memory, payloads included, even when the row kept
none. The trajectory then copied each call's full input twice, into `ng_trajectory.model_calls[].request` and
`turns[].question`. Rows reached 27 GB, and the Gym head swung between 59 and 112 GB of RSS assembling them until the
host killed it.

## Delta capture format

With `model_call_capture_format: delta`, each line stores what the rollout's earlier calls did not already hold:

- **History.** The request's history list (`input` for Responses, `messages` for Chat and Messages) holds only the
  new items. `base_model_call_id` names an earlier line of the same file, and `shared_prefix` says how many of
  that line's items come first.
- **Inherited fields.** Request fields equal to the base call's, such as `tools` and `instructions`, are listed in
  `inherited_keys` and left `null`.
- **Blobs.** Base64 `data:` URLs of at least 1 KiB are stored once per rollout as
  `blobs/<rollout_id>/<sha256>`, next to the capture files. The line lists the JSON path of each one it replaced
  and leaves `null` there.

All of this sits under one `capture_format` key, which a full-format line never has. No value inside an exchange
can be mistaken for a reference. A line looks like this, shortened:

```json
{"model_call_id": "c7", "dialect": "responses",
 "request": {"model": "m", "instructions": null, "tools": null,
             "input": [{"type": "function_call_output", "call_id": "t7",
                        "output": [{"type": "input_image", "image_url": null}]}]},
 "response": {"...": "..."},
 "capture_format": {"version": 2, "base_model_call_id": "c6", "history_key": "input", "shared_prefix": 41,
                    "inherited_keys": ["instructions", "tools"],
                    "blobs": [[["request", "input", 0, "output", 0, "image_url"], "9f2c...e1"]]}}
```

Every other field of the exchange, such as `model_ref`, `agent_instance`, timings and the response, is stored as in
the full format.

**Choosing the base.** Policy, subagent, judge and user-simulator calls interleave in one file, in completion
order, and several processes append to it. So the base is not "the previous line". Each writer process remembers
the item digests of the last few calls it wrote for each rollout. It picks the one with the longest common prefix,
and under the file lock it reads the base line's head back to check that its `model_call_id` is still at that
offset. A capture that was deleted and recreated for a retry fails this check, and a writer that restarted
remembers no calls. In both cases, and after a context compaction (no common prefix), the line stores the whole
history. A writer never names a line written by another process.

**Crash safety.** Appends keep the existing lock, fsync and pending markers. Blobs are written to a temporary file,
fsynced and renamed, together with their directories, before the line that names them. A crash between the two
leaves an unreferenced blob, which is harmless. A writer killed in the middle of an append leaves a partial last
line; the next append, in either format, ends that line first, so only it is lost and no later line extends it.

## Readers

`CaptureStore.read()` and `read_available()` return full exchanges from either format, line by line, so a file may
mix both. `iter_available()` yields one exchange at a time. Its `payloads=False` view drops the request history and
other large request fields, so metadata readers never hold a conversation.

Rebuilt requests of consecutive calls share the item objects of their common prefix, and each blob is read once.
Reading a whole rollout costs about its unique content. Full-format lines get the same sharing: each one's items
are compared with the call it continues and replaced by the earlier objects when equal.

A line whose base or blob cannot be read is reported unreadable, like a damaged line. It is never rebuilt
wrongly, and `capture_index` is still the line's position.

## The finished-rollout merge

The merge streams the capture. Unless the row keeps request payloads, it reads the metadata view, keeping only each
call's response for the tool and turn joins. Its memory no longer grows with the conversation. A v2 trajectory
(`trajectory_schema_version: "2.0"`) links each tool call to the response that requested it, so it reads responses
even for a row that keeps no payloads; it no longer reads their requests to do so.

## Where rows keep payloads

`model_call_payloads` chooses what each rollout row copies, for `gym eval run` and `run_examples`:

| Value | `model_calls[].request`, `turns[].question` | `model_calls[].response`, turn answers |
|---|---|---|
| `inline` (default) | Copied, as today | Copied |
| `reference` | Omitted; `payload_ref` names the capture line | Copied |
| `none` | Omitted | Omitted (as `include_model_call_payloads=False`) |

`payload_ref` is `{capture_file, call_index, model_call_id}`, relative to the run's `model_call_capture_dir`.
`nemo_gym.rollouts.resolve_model_call_payloads(trajectory, capture_dirs)` restores both omitted fields.
Responses stay inline: each holds only its own call's output, so they grow linearly, and the health checks and the
tool-request evidence read them.

The one health check input that is a request, the opening of a conversation (to tell an overflow after an answer in
the same conversation from one in another), is read from the capture. It is read only for chains that end on an
overflow. Without a readable capture, that check is unobserved rather than flagged.

`delete_model_call_capture` needs `inline`. ATIF export asks for referenced rows to be resolved first, and says how.

## Images in finished rows

With `reference` payloads a row no longer copies requests, but a Codex row still holds every screenshot three times.
Codex's own session record becomes the agent's observation records (`ng_agent_observations`), the trajectory builds
its invocation conversation from those records, and it copies each tool output into `tool_calls[].output`. On the
run above, a row two hours in was 344 MB, of which model calls took 4 MB; rows later reached 1.15 GB.

`row_media: reference` (opt-in; `inline` is the default) stores each image of a finished row once. In the evidence
keys (`ng_agent_observations`, `ng_trajectory`, `ng_model_call_capture`, `ng_verifier_invocations`), every base64
`data:` URL of at least 1 KiB is replaced by `null`, and the row lists each replaced place under one key after its
other keys:

```json
"ng_row_media": {"version": 1, "root": "model_call_capture_dir", "dir": "blobs/7-0",
                 "blobs": [[["ng_trajectory", "tool_calls", 12, "output", 0, "image_url"], "9f2c...e1"]]}
```

The blob is the URL's text in a file named by its SHA-256, the same file the delta capture format writes. With a
capture directory, a row's images go to `<capture dir>/blobs/<rollout_id>/`, where the delta capture already holds
every image the model was sent, so the row adds none. Without one, they go to `<rollouts stem>_blobs/<rollout_id>/`
next to the rollouts file (`root: rollouts_dir`). Blobs are written durably before the row names them; if one cannot
be written, the row stays inline. The harness output (`response`) and the task input are never changed: verification
recovery and training read them.

Collection applies it to the record before anything else keeps or writes it, so the row, a result kept in memory, and
the exporters' spool hold the same references; a recorded `run_examples` shard references its rows, while the result
returned to the caller keeps its images. A shard staged in a node-local folder (`record_staging_dir`) still writes its
blobs to their final place as each row is written, so its published rows name blobs that are already there.

`nemo_gym.trajectory.restore_row_media` gives the row back exactly as it was. Readers that need the images restore
or refuse:

| Reader | With `ng_row_media` |
|---|---|
| ATIF export (`gym eval export atif`) | Restores each row from the run's blob directories, found through the saved config next to the rollouts file. `gym_rollout_to_atif` on a referenced row raises and says how to restore it. |
| Harness conformance bundle check | Restores each row (`--capture-dir`, or the saved config). `inspect_record` on a referenced row raises. |
| Exporters (W&B, MLflow) | Their projection drops conversations; the listing keeps only the entries the projection still holds. |
| Rollout health checks | Unaffected: they read tool output text, never image data. On the rows below, every health digest is equal before and after. |

`delete_model_call_capture` needs `inline`, because the capture's blob directory holds the row's images.

## Compatibility

- The defaults stay `full` and `inline`: lines and rows are written as before.
- Every reader in Gym accepts both formats. `CaptureStore.copy_full()` writes a self-contained full-format copy;
  the SWE-Together judge evidence uses it.
- External readers of `*.capture.jsonl` lines need to handle `capture_format` lines, through `CaptureStore` or
  `scripts/replay_capture_delta.py`, before a run turns `delta` on.
- Deleting a rollout's capture, including the collector's cleanup before a retry, also deletes its blob directory.
- `payload_ref` is a new optional field of `TrajectoryModelCall` and `TrajectoryTurn`, written only in `reference`
  mode. Older readers that forbid unknown fields reject such rows.
- A `reference` row needs the run's capture directory to restore its requests: keep the directory with the rows.
- `ng_row_media` is a new top-level row key, written only with `row_media: reference`. A reader that reads images
  from rows needs `restore_row_media` first; EvalRDL uploads the whole run directory, blobs included.

## Measurements

These are real captures from the run above. Each was converted with `scripts/replay_capture_delta.py` under a
16 GB memory cap, and every rebuilt exchange is byte-identical to its source line.

| Capture | Calls | Full format | Delta (lines + blobs) | Ratio | Convert + verify | Peak RSS |
|---|---|---|---|---|---|---|
| `0-0` (text) | 167 | 87 MB | 22.5 MB | 3.9× | 1.4 s | 0.1 GB |
| `9-0` (screenshots) | 93 | 5.2 GB | 101 MB (42 blobs) | 51× | 35 s | 0.8 GB |
| `4-0` (screenshots) | 286 | 13.3 GB | 151 MB (166 blobs) | 88× | 88 s | 0.6 GB |
| `61-0` (screenshots) | 211 | 25.9 GB | 385 MB (128 blobs) | 67× | 173 s | 2.1 GB |

The finished-rollout enrichment (merge, trajectory and `ng_perf`, then serializing the row) was also measured,
with each measurement in its own process under the same 16 GB cap:

| Capture | Code and payloads | Peak RSS | Time | Row |
|---|---|---|---|---|
| `9-0`, full format | before, inline | 10.5 GB | 15 s | 5.2 GB |
| `9-0`, full format | before, none | 5.6 GB | 14 s | 0.5 MB |
| `9-0`, full format | after, reference | 0.6 GB | 11 s | 4.4 MB |
| `61-0`, full format | before, none | killed at 16 GB | — | — |
| `61-0`, full format | after, reference | 1.7 GB | 58 s | 9.3 MB |
| `61-0`, delta format | after, reference | 0.3 GB | 0.3 s | 9.3 MB |
| `61-0`, either format | after, inline | killed at 16 GB | — | (26 GB of requests) |

An `inline` row holds every call's full request by definition, so for long sessions only `reference` or `none`
can keep rows bounded.

The merge alone (`scripts/replay_capture_delta.py merge`) on `9-0` peaks at 0.5 GB in `reference` or `none` on the
full format, and at 0.16 GB in `reference` on the delta format, against 5.5 GB in `inline` on either format.

In a text-only session, about 90% of the delta bytes are each call's own output. Two thirds of that is the raw
SSE text kept next to the reassembled response.

### Row media

Finished rows of the same run and of an earlier `inline`-payload run, each converted with
`scripts/replay_row_media.py` under a 12 GB memory cap, restored, and checked byte for byte against the original line.
"Held by capture" counts the row's images already in the run's delta capture blobs.

| Row | Original | With `row_media: reference` | Images (unique) | Blob bytes | Held by capture | Reference step | Its peak RSS |
|---|---|---|---|---|---|---|---|
| `35-0` (text) | 8.9 MB | 8.9 MB (unchanged) | 0 | 0 | — | 0.01 s | 0.13 GB |
| `37-0` | 454 MB | 26.9 MB | 171 (39) | 98 MB | 39 of 39 | 0.7 s | 0.56 GB |
| `12-0` | 863 MB | 96.2 MB | 1,083 (268) | 202 MB | 268 of 268 | 3.4 s | 1.12 GB |
| `7-0` | 1,146 MB | 122.1 MB | 2,598 (688) | 268 MB | 688 of 688 | 7.7 s | 1.45 GB |
| `16-0`, inline payloads | 317 MB | 121.0 MB | 611 (10) | 3.3 MB | full-format capture | 0.3 s | 0.55 GB |
| `66-0`, inline payloads | 4,104 MB | 91.0 MB | 3,244 (30) | 34 MB | full-format capture | 2.4 s | 4.27 GB |

The reference step's peak RSS equals the RSS of the parsed row before it: it adds no memory. Its time is mostly
writing and fsyncing new blob files; with the capture's blobs already present it writes none. What is left of a
long Codex row is mostly text, which is still held three times.
