---
title: Failure observations
description: Failure evidence, explicit causes, reports and shared outcome policies.
---

Gym records an observed failure as one `NgFailureEvent` exception. The same object
is raised and serialized with `to_record()`; `from_record()` reconstructs it. It names the boundary that observed it (`model`, `harness`,
`agent`, `sandbox`, `resources_server`, `environment` or `collection`), its kind, stage, HTTP
status and the event ID of its explicit cause. Existing handlers, outcome policy,
retry budgets and scoring remain in control.

The flow for one failure:

1. A boundary raises `NgFailureEvent(...) from error`. The event ID is assigned here.
2. `failure_report_for` turns the explicit cause chain (`raise ... from`) into a
   `FailureReport`: `failure_id` names the current failure, `cause_id` links causes.
   Implicit Python context is not a cause.
3. The server middleware sends the report in the `X-NG-Failure-Report` reply header,
   on success and failure replies, with the failures observed while serving the
   request (for example a model attempt that a retry recovered).
4. The caller's `raise_boundary_failure` raises the reconstructed remote failure,
   preserving event IDs and explicit causes. Its `http_error` keeps this hop's status
   and body separately. `raise_for_status` remains the HTTP exception compatibility
   path for callers whose retry or routing logic depends on `ClientResponseError`.
5. Collection saves the report beside the existing result or failure record
   (`_ng_failure_events`, `_ng_failure_id`).

## Policy by execution stage

`FailureStage` in [failure_kinds.py](https://github.com/NVIDIA-NeMo/Gym/blob/main/nemo_gym/core/failure_kinds.py)
is the shared vocabulary for failure events, sandbox observations and outcome policies. Use `stage`, including
in sandbox observations; do not introduce a separate `phase` vocabulary. Task preparation uses `seed`;
preparing or running a verifier uses `verification`. Preserve the originating stage when forwarding a failure:
an agent failure caught by a verifier still belongs to `agent`. Leave the stage unset when it is unknown.

`FailureClass` and `FailureClassificationConfig` in `failure_kinds.py` define one configurable classification:
`model`, `evaluation` (including infrastructure), or `unknown`. Classification interprets observed evidence;
it does not change the event or prescribe a retry, score or health verdict.

`StageOutcomePolicyConfig` selects rules by stage, then checks HTTP status, failure kind, failure class and
the default action, in that order. The caller establishes the failure's origin and sandbox ownership before applying these rules;
a provider cannot infer them. Unknown ownership must not enter the agent OOM policy.

The shared defaults are:

| Admitted failure | Action | Class |
| --- | --- | --- |
| Confirmed OOM in the agent's assigned sandbox during `agent` execution | `count_as_zero` | `model` |
| Confirmed OOM during `seed` | `retry` | `evaluation` |
| Inconclusive verification attempt, including confirmed OOM | `retry` | `evaluation` |
| Verification failure reporting cancellation, shutdown, a SIGTERM interruption or lost worker (`kill_shaped`) or rejected credentials | `fail` ungraded | `evaluation` |
| OOM without an established stage or ownership | `fail` ungraded | `unknown` |

Other failures use the shared classification defaults and the selected stage's action rules. For example, a
sandbox-create timeout is `evaluation`; class alone does not authorize a retry.

A confirmed policy response timeout normally remains `model_policy_response_timeout` (class `model`). Queue evidence
can reclassify it as a server failure. When a request to a vLLM model server times out waiting for
its response, the client reads that server's queue from its `/metrics` page at the timeout and records
`server_requests_waiting` and `server_requests_running` on the attempt's failure, also when nothing is waiting;
they stay unset when the server publishes no queue metrics. If every attempt of the timed-out call saw requests
waiting, the agent reports `model_server_queue_timeout` instead: class `evaluation` (server), retried within the
evaluation's retry budget, never counted as the model's zero. If any attempt has no queue reading or an
empty queue, the timeout keeps `model_policy_response_timeout` and its configured handling. The reading describes the whole server, so on a saturated server a request that
had already started generating is treated as the server's too; that errs towards a retry, not a zero.

A `retry` decision never authorizes replaying an uncertain command. The caller retains its retry safety checks
and existing attempt/deadline budget; exhaustion stays ungraded. Task cancellation continues to propagate. Verification rules apply to inconclusive attempts,
not ordinary verifier scores. `count_as_zero` ends the episode without retry and includes its zero in the denominator.

Policies are configurable. This fragment is a `StageOutcomePolicyConfig` value; place it under the consuming
server's field of that type. It overrides the agent OOM action without replacing the other stages:

```yaml
by_stage:
  agent:
    by_failure_kind:
      provider_oom_killed: fail
```

This override fails ungraded while retaining the `model` classification. To change the classification,
set `classification` in the same `StageOutcomePolicyConfig` value:

```yaml
classification:
  by_stage:
    agent:
      by_failure_kind:
        provider_oom_killed: unknown
```

This configures the shared mapper for this boundary. Other boundaries have their own configuration;
readers of an applied result preserve its recorded class. Each stage can also select actions through
`by_failure_class`, for example `{evaluation: retry}` where that boundary supports retry.
Partial overrides retain unspecified defaults. Changing an action does not change the class.

`choose_stage_outcome` returns an `OutcomeDecision` containing the selected `action` and its shared
`FailureClass` in `attribution`. Keep the applied action and class available with the final result and
attempt identity. DeepSWE uses `failure_outcome_action` and `failure_outcome_attribution` on its result
for these choices, including after save/reload. Results and failure events remain separate:
a completed result can carry failures recovered along the way, without becoming a failed result.
Provider-operation retry policies remain separate from episode decisions.

## Recovered failures

Before retrying a failed operation, call `observe_failure(error)` from `nemo_gym.core`.
It adds the event and its explicit causes to the current request's failure log, so the reply can carry
them even when a later attempt succeeds. It does not raise, choose an outcome action or mark the request
failed. Outside a request capture scope it does nothing.

Reports deduplicate events by `event_id`; count each ID once across saved reports. A recovered failure
remains diagnostic evidence and does not by itself change a successful result, score or health assessment.

## Scored despite a failure

A server sometimes swallows a failure and goes on to return a normal result: an agent whose harness crashed and is
scored zero, a judge that did not answer and fell back to a default reward, a step limit that ended the run, a
verifier whose sandbox could not run. The rollout is then scored from a degraded path, and without a record it cannot be
told from one that was graded normally.

Where the code carries on, call `observe_scored_despite_failure(boundary=..., failure_kind=..., failure_reason=...,
stage=...)` from `nemo_gym.core`. It records an event with the operation `scored_despite_failure` in the same request
failure log as `observe_failure`, so it travels with the reply and is saved beside the row. It changes nothing else: the
reward, the response, the retry decision and the exit code are as they were, and no `failure_id` is set, because it is not
the rollout's own failure. Use it only where the result is a consequence of the failure. A failure that a retry
recovered from is a recovered failure, and `observe_failure` is the call for it.

The `rollout_scored_despite_failure` [health check](/main/evaluation/rollout-health) counts these events, so the run's health
summary says how many rollouts were scored this way and from which failure kinds. The shipped agents and verifiers
record the cases they swallow: a crashed harness (`agent_run_error`), a step limit (`agent_limit`), a judge that did not
answer (`judge_failed`), a verifier that could not run its sandbox (`verifier_error`), an agent that reported failure
without a classified outcome, and a `/run` that was resent after it may have been delivered.

A result that is served again without running again keeps its events. A server that persists a result it will replay (a
cache hit, a restored checkpoint) saves the request's events with it using `with_saved_failure_report(payload)` and
observes them again with `restore_saved_failure_report(payload)`, so the replayed result carries the same events under
the same ids. When an agent retries an attempt and throws its result away, it calls
`RequestFailureLog.discard_scored_despite_failures(known_event_ids)` first: what the discarded attempt swallowed stays in
the report as an ordinary diagnostic (`discarded_attempt`) and does not mark the result that is scored.

## Causes and transport

An environment uses `handled_episode_failure(...)` with event fields, its local
`terminal` decision and separate partial evidence. It returns an `NgFailureEvent`;
the response adapter constructs `EpisodeFailure` after cleanup, including late
observations and trajectory evidence. Diagnostics never borrow a cause's kind.
The v1 `EpisodeFailure` keeps its existing four fields; `failure_report` travels
beside it in the response.

Pickle and cloudpickle retain canonical Gym causes, captured IDs and selected SDK
facts. Foreign exceptions do not become boundary-less events: their type, bounded
selected message and status go in the nearest Gym event's `foreign_error`. Gym
causes below a foreign intermediary remain linked. Exception type names stay data;
decoding never imports them. Every event requires an explicit boundary and a
registered or namespaced kind, including recovered reports.

There are no boundary-specific exception subclasses. Catch `NgFailureEvent` and
select by `boundary`, `failure_kind` and, where needed, `operation`. A judge call
records `judge_failed` above its provider cause; standalone parser `JudgeError`s
remain supported by the judge failsafe.

The optional `foreign_error` field holds diagnostics that an adapter selected from an
SDK error: its type, a scalar message and its HTTP status. SDK objects, request bodies
and response payloads are not serialized. A long message keeps a visible
`[truncated]` marker.

aiohttp rejects a reply header line over 8190 bytes. A report over 4096 bytes is
therefore not sent: the header carries `{"omitted": true}`, every hop above keeps the
flag, and Collection saves `_ng_failure_events_omitted`. The report's
scored-despite-failure events are the exception: they still travel beside the flag,
with their reasons cut to 200 characters and their details and causes dropped, so
the `rollout_scored_despite_failure` health check still sees a degraded rollout. If
even these do not fit, only the flag is sent. The real status and body
still arrive. This diagnostic loss does not change the task outcome. Old records with
no failure report keep their meaning. The final saved-record migration remains a
separate change.

### Delivery of a dispatch that was not bounded

Collection now observes every dropped `/run` attempt, including those of a caller that sets no attempt bound
(`run_examples`, for example). Before, only a bounded dispatch recorded them. A caller that persists the failed
outcome of such a dispatch sees one change. When an attempt dropped after it connected and every later attempt was
refused, the failure's `delivery` is now `possibly_delivered`, where it was `not_sent`. The earlier attempt may have
delivered `/run`, so the new value is the accurate one. `is_interruption_failure`, which retry budgets and progress
accounting read, follows it: it is now false for that sequence. A dispatch whose attempts were all refused or timed
out connecting is still `not_sent`.
