<Note>
This is NeMo Gym's **strongly recommended golden path (SHOULD, not MUST)** for failure handling.
Shared recovery, observability and health tooling increasingly relies on these conventions.
Other implementations can still reach main: deviation alone is not a merge blocker, and this guide
adds no required CI gate. When choosing another path, explain the tradeoff and any effect on callers
or tooling so reviewers can assess the behavior. Existing API validation and correctness requirements
still apply when using those APIs.
</Note>

## Recommended path

Contributors should use this pattern when adding or changing failure handling in sandbox providers,
model clients, harnesses, Agent Servers, Resources Servers, Environment Servers and collection:

1. **Record what happened.** Raise `NgFailureEvent` with a named kind from
   [failure_kinds.py](https://github.com/NVIDIA-NeMo/Gym/blob/main/nemo_gym/core/failure_kinds.py),
   an explicit observing boundary and the originating stage when known. Prefer an existing kind;
   add a shared kind for a new reusable observation. Keep occurrence details in `failure_reason` or
   typed details. Namespaced kinds remain available for component-specific observations, although
   shared policy kind rules currently validate against the registered vocabulary.
2. **Choose treatment through configuration.** Reuse the shared outcome-policy mechanism and
   the consuming boundary's supported actions and defaults. A failure kind or class describes an
   observation or interpretation; it does not itself prescribe retry, scoring or a health verdict.
3. **Execute at the owning boundary.** Keep attempt budgets, cancellation, deadlines, saved-output
   prerequisites and replay safety with the executor. A configured retry does not make an uncertain
   command safe to repeat or create another retry allowance.
4. **Pass evidence upstream.** Forward events and reports through callers on both failure and
   recovered-success paths, preserving IDs, originating stages and explicit causes. Wrap an event
   only to report a distinct failure of the caller's own operation. Retain the diagnostics-omitted
   flag when the transport cannot carry a report.
5. **Preserve the result and its meaning.** Collection and readers should retain the applied
   outcome decision and failure evidence through persistence. A consumer should honor a saved
   decision rather than silently choose it again from current defaults. Recovery of unresolved work
   can make a separate decision at its own boundary.

Use the [failure-contracts skill](https://github.com/NVIDIA-NeMo/Gym/tree/main/.agents/skills/failure-contracts)
for a short implementation and review walkthrough. Adoption is incremental; this page does not claim
that every existing path already follows the pattern.

## Failure observations

NeMo Gym records an observed failure as one `NgFailureEvent` exception. The same object
is raised and serialized with `to_record()`; `from_record()` reconstructs it. It names the boundary that observed it (`model`, `harness`,
`agent`, `sandbox`, `resources_server`, `environment` or `collection`), its kind, stage, HTTP
status and the event ID of its explicit cause. Existing handlers, outcome policy,
retry budgets and scoring remain in control.

The flow for one failure:

1. A boundary raises `NgFailureEvent(...) from error`. The event ID is assigned here.
2. `failure_report_for` turns the explicit cause chain (`raise ... from`) into a
   `FailureReport`: `failure_id` names the current failure, `cause_id` links causes.
   Implicit Python context is not a cause.
3. The server middleware sends the report in the `X-NG-Failure-Report` reply header,
   on success and failure replies, with the failures observed while serving the
   request (for example a model attempt that a retry recovered).
4. The caller's `raise_boundary_failure` raises the reconstructed remote failure,
   preserving event IDs and explicit causes. Its `http_error` keeps this hop's status
   and body separately. `raise_for_status` remains the HTTP exception compatibility
   path for callers whose retry or routing logic depends on `ClientResponseError`.
5. Collection saves the report beside the existing result or failure record
   (`_ng_failure_events`, `_ng_failure_id`).

## Configurable actions

[OutcomeAction and OutcomePolicyConfig](https://github.com/NVIDIA-NeMo/Gym/blob/main/nemo_gym/core/outcome_policy.py)
provide the shared vocabulary and selector. Each boundary supports only actions it can execute.

| Action | Meaning at the executing boundary |
| --- | --- |
| `retry` | Try the operation again within its existing safety and budget constraints. |
| `verify` | Grade available output; retrying a failed judge request is a separate retry operation. |
| `fail` | Stop ungraded; stopping retries does not imply a zero score. |
| `count_as_zero` | Apply an explicit zero-score treatment, including that zero in the denominator. |

Masking represents an ungraded sample; it is not a separate `OutcomeAction` and should not contradict
an applied `count_as_zero`. Preserve execution status, verification outcome and applied scoring
choice separately: incomplete execution does not by itself determine the score.

This standalone example selects treatment for an observed model failure. It uses public APIs;
in a server, expose the policy through its typed configuration rather than constructing fixed rules
inside the error handler. Prefer the existing boundary config when one is available.

```python
from nemo_gym.core import (
    MODEL_REQUEST_ERROR,
    NgFailureEvent,
    OutcomeAction,
    OutcomePolicyConfig,
    choose_action,
)

failure = NgFailureEvent(
    boundary="model",
    failure_kind=MODEL_REQUEST_ERROR,
    failure_reason="Model endpoint returned HTTP 503",
    stage="agent",
    http_status=503,
)
policy = OutcomePolicyConfig(default_action="fail", by_status_code={503: "retry"})
assert choose_action(
    failure_kind=failure.failure_kind, http_status=failure.http_status, config=policy,
) == OutcomeAction.RETRY

# Change treatment without changing the observed failure.
override = OutcomePolicyConfig(default_action="fail", by_status_code={503: "fail"})
assert choose_action(
    failure_kind=failure.failure_kind, http_status=failure.http_status, config=override,
) == OutcomeAction.FAIL
assert failure.http_status == 503
```

The selector does not execute retries. Use a boundary's validated configuration to restrict supported
actions; the stage-aware configuration below also preserves unspecified defaults on partial overrides.

## Policy by execution stage

`FailureStage` in [failure_kinds.py](https://github.com/NVIDIA-NeMo/Gym/blob/main/nemo_gym/core/failure_kinds.py)
is the shared vocabulary for failure events, sandbox observations and outcome policies. Use `stage`, including
in sandbox observations; do not introduce a separate `phase` vocabulary. Task preparation uses `seed`;
preparing or running a verifier uses `verification`. Preserve the originating stage when forwarding a failure:
an agent failure caught by a verifier still belongs to `agent`. Leave the stage unset when it is unknown.

`FailureClass` and `FailureClassificationConfig` in `failure_kinds.py` define one configurable classification:
`model`, `evaluation` (including infrastructure), or `unknown`. Classification interprets observed evidence;
it does not change the event or prescribe a retry, score or health verdict.

`StageOutcomePolicyConfig` selects rules by stage, then checks HTTP status, failure kind, failure class and
the default action, in that order. The caller establishes the failure's origin and sandbox ownership before applying these rules;
a provider cannot infer them. Unknown ownership must not enter the agent OOM policy.

The shared defaults are:

| Admitted failure | Action | Class |
| --- | --- | --- |
| Confirmed OOM in the agent's assigned sandbox during `agent` execution | `count_as_zero` | `model` |
| Confirmed OOM during `seed` | `retry` | `evaluation` |
| Inconclusive verification attempt, including confirmed OOM | `retry` | `evaluation` |
| Verification failure reporting cancellation, shutdown, a SIGTERM interruption or lost worker (`kill_shaped`) or rejected credentials | `fail` ungraded | `evaluation` |
| OOM without an established stage or ownership | `fail` ungraded | `unknown` |

Other failures use the shared classification defaults and the selected stage's action rules. For example, a
sandbox-create timeout is `evaluation`; class alone does not authorize a retry.

A confirmed policy response timeout normally remains `model_policy_response_timeout` (class `model`). Queue evidence
can reclassify it as a server failure. When a request to a vLLM model server times out waiting for
its response, the client reads that server's queue from its `/metrics` page at the timeout and records
`server_requests_waiting` and `server_requests_running` on the attempt's failure, also when nothing is waiting;
they stay unset when the server publishes no queue metrics. If every attempt of the timed-out call saw requests
waiting, the agent reports `model_server_queue_timeout` instead: class `evaluation` (server), retried within the
evaluation's retry budget, never counted as the model's zero. If any attempt has no queue reading or an
empty queue, the timeout keeps `model_policy_response_timeout` and its configured handling. The reading describes the whole server, so on a saturated server a request that
had already started generating is treated as the server's too; that errs towards a retry, not a zero.

A `retry` decision never authorizes replaying an uncertain command. The caller retains its retry safety checks
and existing attempt/deadline budget; exhaustion stays ungraded. Task cancellation continues to propagate. Verification rules apply to inconclusive attempts,
not ordinary verifier scores. `count_as_zero` ends the episode without retry and includes its zero in the denominator.

Policies are configurable. This fragment is a `StageOutcomePolicyConfig` value; place it under the consuming
server's field of that type. It overrides the agent OOM action without replacing the other stages:

```yaml
by_stage:
  agent:
    by_failure_kind:
      provider_oom_killed: fail
```

This override fails ungraded while retaining the `model` classification. To change the classification,
set `classification` in the same `StageOutcomePolicyConfig` value:

```yaml
classification:
  by_stage:
    agent:
      by_failure_kind:
        provider_oom_killed: unknown
```

This configures the shared mapper for this boundary. Other boundaries have their own configuration;
readers of an applied result preserve its recorded class. Each stage can also select actions through
`by_failure_class`, for example `{evaluation: retry}` where that boundary supports retry.
Partial overrides retain unspecified defaults. Changing an action does not change the class.

`choose_stage_outcome` returns an `OutcomeDecision` containing the selected `action` and its shared
`FailureClass` in `attribution`. Keep the applied action and class available with the final result and
attempt identity. DeepSWE uses `failure_outcome_action` and `failure_outcome_attribution` on its result
for these choices, including after save/reload. Results and failure events remain separate:
a completed result can carry failures recovered along the way, without becoming a failed result.
Provider-operation retry policies remain separate from episode decisions.

## Recovered failures

Before retrying a failed operation, call `observe_failure(error)` from `nemo_gym.core`.
It adds the event and its explicit causes to the current request's failure log, so the reply can carry
them even when a later attempt succeeds. It does not raise, choose an outcome action or mark the request
failed. Outside a request capture scope it does nothing.

Reports deduplicate events by `event_id`; count each ID once across saved reports. A recovered failure
remains diagnostic evidence and does not by itself change a successful result, score or health assessment.

## Causes and transport

An environment uses `handled_episode_failure(...)` with event fields, its local
`terminal` decision and separate partial evidence. It returns an `NgFailureEvent`;
the response adapter constructs `EpisodeFailure` after cleanup, including late
observations and trajectory evidence. Diagnostics never borrow a cause's kind.
The v1 `EpisodeFailure` keeps its existing four fields; `failure_report` travels
beside it in the response.

Pickle and cloudpickle retain canonical Gym causes, captured IDs and selected SDK
facts. Foreign exceptions do not become boundary-less events: their type, bounded
selected message and status go in the nearest Gym event's `foreign_error`. Gym
causes below a foreign intermediary remain linked. Exception type names stay data;
decoding never imports them. Every event requires an explicit boundary and a
registered or namespaced kind, including recovered reports.

There are no boundary-specific exception subclasses. Catch `NgFailureEvent` and
select by `boundary`, `failure_kind` and, where needed, `operation`. A judge call
records `judge_failed` above its provider cause; standalone parser `JudgeError`s
remain supported by the judge failsafe.

The optional `foreign_error` field holds diagnostics that an adapter selected from an
SDK error: its type, a scalar message and its HTTP status. SDK objects, request bodies
and response payloads are not serialized. A long message keeps a visible
`[truncated]` marker.

aiohttp rejects a reply header line over 8190 bytes. A report over 4096 bytes is
therefore not sent: the header carries `{"omitted": true}`, every hop above keeps the
flag, and Collection saves `_ng_failure_events_omitted`. The real status and body
still arrive. This diagnostic loss does not change the task outcome. Old records with
no failure report keep their meaning. The final saved-record migration remains a
separate change.

## Forwarding a cause

Within one process, a bare `raise` forwards the original event. A caller reporting its own failed
operation raises a new event `from` the inner failure. Across process boundaries, use the shared
report and reconstruction helpers rather than replacing the failure with its message or HTTP status.
This standalone round-trip illustrates the distinction:

```python
import json

from nemo_gym.core import AGENT_RUN_ERROR, MODEL_REQUEST_ERROR, NgFailureEvent

model_failure = NgFailureEvent(
    boundary="model", failure_kind=MODEL_REQUEST_ERROR,
    failure_reason="Model endpoint returned HTTP 503", stage="agent", http_status=503,
)
try:
    raise NgFailureEvent(
        boundary="agent", failure_kind=AGENT_RUN_ERROR,
        failure_reason="Agent run failed after a model request", stage="agent",
    ) from model_failure
except NgFailureEvent as agent_failure:
    restored = NgFailureEvent.from_record(json.loads(json.dumps(agent_failure.to_record())))
    assert restored.event_id == agent_failure.event_id
    assert restored.__cause__.event_id == model_failure.event_id
    assert restored.event_id != restored.__cause__.event_id
```

Before retrying, retain the event with `observe_failure` as described above. A recovered-success
report carries the observed events without naming a terminal failure. Cleanup should preserve the
original failure while retaining any separate cleanup observations. Recording or forwarding an event
does not create an operation attempt or spend a retry budget.

## Health and reporting

Health readers should distinguish observed failure events, failed episode attempts and final outcomes.
A recovered event remains useful evidence without automatically failing the rollout or making it
unhealthy. Deduplicate event counts by ID; forwarding one event through several callers is not several
failed attempts. Keep unavailable or disabled health checks distinguishable from observed healthy
checks, and report missing execution coverage separately from scored rows.

Use the shared classification and configured health thresholds rather than inferring attribution
from a failure-name prefix, exception text or a zero reward. Reporting a health verdict and enforcing
whether a score may be published are separate consumer behaviors. See
[Rollout Health Checks](/main/evaluation/rollout-health).

## Suggested validation and review

Choose checks relevant to the behavior being changed. These are useful demonstrations of the golden
path, not a mandatory suite or a new merge gate:

- Override treatment for the same failure and confirm the facts and cause links stay unchanged;
  check partial overrides and the boundary's unsupported-action validation where applicable.
- Exercise a failed attempt followed by success: the result and reward remain successful, with
  the recovered event still visible to the caller.
- Follow a failure through the actual caller or transport and save/reload path, checking IDs,
  causes, originating stages, omission flags and the applied decision.
- Exercise exhaustion and cleanup: neither silently converts an ungraded failure into a counted zero,
  loses the original failure, or reopens a terminal decision.

Reuse core coverage for shared serialization behavior and focus adapter checks on its own wiring.
Reviewers should assess demonstrated behavior and consumer impact. A different implementation alone
is not a defect or grounds to block a merge; distinguish adoption suggestions from correctness findings.
