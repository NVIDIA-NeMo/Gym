---
title: Failure observations
description: Failure evidence, explicit causes, reports and shared outcome policies.
---

Gym records an observed failure as one `NgFailureEvent` exception. The same object
is raised and serialized with `to_record()`; `from_record()` reconstructs it. It names the boundary that observed it (`model`, `harness`,
`agent`, `sandbox`, `resources_server`, `environment` or `collection`), its kind, stage, HTTP
status and the event ID of its explicit cause. Existing handlers, outcome policy,
retry budgets and scoring remain in control.

The flow for one failure:

1. A boundary raises `NgFailureEvent(...) from error`. The event ID is assigned here.
2. `failure_report_for` turns the explicit cause chain (`raise ... from`) into a
   `FailureReport`: `failure_id` names the current failure, `cause_id` links causes.
   Implicit Python context is not a cause.
3. The server middleware sends the report in the `X-NG-Failure-Report` reply header,
   on success and failure replies, with the failures observed while serving the
   request (for example a model attempt that a retry recovered).
4. The caller's `raise_boundary_failure` raises the reconstructed remote failure,
   preserving event IDs and explicit causes. Its `http_error` keeps this hop's status
   and body separately. `raise_for_status` remains the HTTP exception compatibility
   path for callers whose retry or routing logic depends on `ClientResponseError`.
5. Collection saves the report beside the existing result or failure record
   (`_ng_failure_events`, `_ng_failure_id`).

## Policy by execution stage

`FailureStage` in [failure_kinds.py](https://github.com/NVIDIA-NeMo/Gym/blob/main/nemo_gym/core/failure_kinds.py)
is the shared vocabulary for failure events, sandbox observations and outcome policies. Use `stage`, including
in sandbox observations; do not introduce a separate `phase` vocabulary. Task preparation uses `seed`;
preparing or running a verifier uses `verification`. Preserve the originating stage when forwarding a failure:
an agent failure caught by a verifier still belongs to `agent`. Leave the stage unset when it is unknown.

`StageOutcomePolicyConfig` selects rules by stage, then uses the existing HTTP-status, failure-kind and default-action
precedence. The caller establishes the failure's origin and sandbox ownership before applying these rules;
a provider cannot infer them. Unknown ownership must not enter the agent OOM policy.

The shared defaults are:

| Admitted failure | Action | Attribution |
| --- | --- | --- |
| Confirmed OOM in the agent's assigned sandbox during `agent` execution | `count_as_zero` | `model` |
| Confirmed OOM during `seed` | `retry` | `evaluation` |
| Inconclusive verification attempt, including confirmed OOM | `retry` | `evaluation` |
| Verification failure reporting cancellation, shutdown, a kill-shaped exit or rejected credentials | `fail` ungraded | `evaluation` |
| Other failures, unknown stage or unknown ownership | `fail` ungraded | `unknown` |

A `retry` decision never authorizes replaying an uncertain command. The caller retains its retry safety checks
and existing attempt/deadline budget; exhaustion stays ungraded. Task cancellation continues to propagate. Verification rules apply to inconclusive attempts,
not ordinary verifier scores. `count_as_zero` ends the episode without retry and includes its zero in the denominator.

Policies are configurable. This fragment is a `StageOutcomePolicyConfig` value; place it under the consuming
server's field of that type. It overrides the agent OOM action without replacing the other stages:

```yaml
by_stage:
  agent:
    by_failure_kind:
      provider_oom_killed: fail
```

This override fails ungraded while retaining the explicit `model` attribution. To change that attribution too,
set `attribution_by_failure_kind: {provider_oom_killed: unknown}` in the same `agent` block.

Partial overrides retain other defaults. `choose_stage_outcome` returns one `OutcomeDecision` with `action` and
`attribution`. Attribution is configured independently through `attribution_by_failure_kind` and `default_attribution`;
changing an action, including via `by_status_code`, does not change attribution. Consumers must preserve and use the
selected decision for scoring and health instead of interpreting the failure evidence again. Provider-operation retry
policies remain separate from these episode decisions.

## Recovered failures

Before retrying a failed operation, call `observe_failure(error)` from `nemo_gym.core`.
It adds the event and its explicit causes to the current request's failure log, so the reply can carry
them even when a later attempt succeeds. It does not raise, choose an outcome action or mark the request
failed. Outside a request capture scope it does nothing.

Reports deduplicate events by `event_id`; count each ID once across saved reports. A recovered failure
remains diagnostic evidence and does not by itself change a successful result, score or health assessment.

## Causes and transport

An environment uses `handled_episode_failure(...)` with event fields, its local
`terminal` decision and separate partial evidence. It returns an `NgFailureEvent`;
the response adapter constructs `EpisodeFailure` after cleanup, including late
observations and trajectory evidence. Diagnostics never borrow a cause's kind.
The v1 `EpisodeFailure` keeps its existing four fields; `failure_report` travels
beside it in the response.

Pickle and cloudpickle retain canonical Gym causes, captured IDs and selected SDK
facts. Foreign exceptions do not become boundary-less events: their type, bounded
selected message and status go in the nearest Gym event's `foreign_error`. Gym
causes below a foreign intermediary remain linked. Exception type names stay data;
decoding never imports them. Every event requires an explicit boundary and a
registered or namespaced kind, including recovered reports.

There are no boundary-specific exception subclasses. Catch `NgFailureEvent` and
select by `boundary`, `failure_kind` and, where needed, `operation`. A judge call
records `judge_failed` above its provider cause; standalone parser `JudgeError`s
remain supported by the judge failsafe.

The optional `foreign_error` field holds diagnostics that an adapter selected from an
SDK error: its type, a scalar message and its HTTP status. SDK objects, request bodies
and response payloads are not serialized. A long message keeps a visible
`[truncated]` marker.

aiohttp rejects a reply header line over 8190 bytes. A report over 4096 bytes is
therefore not sent: the header carries `{"omitted": true}`, every hop above keeps the
flag, and Collection saves `_ng_failure_events_omitted`. The real status and body
still arrive. This diagnostic loss does not change the task outcome. Old records with
no failure report keep their meaning. The final saved-record migration remains a
separate change.
