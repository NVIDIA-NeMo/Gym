NeMo Gym emits a small, deliberate set of metrics. This page lists them, and explains what
is deliberately absent and why.

## Application Telemetry, Not Experiment Telemetry

These metrics answer "how is this software behaving?" — where time goes, what failed, how
a configuration performs on hardware you do not control.

They do not answer "how is my run doing?" Reward, accuracy, and benchmark scores are
experiment telemetry. They belong in Weights & Biases or MLflow, which are built for
comparing runs and keep data for the lifetime of a project. NeMo Gym already reports them
through `AggregateMetricsMixin` and continues to do so, unchanged.

Mirroring reward into OpenTelemetry would put a number in a system that aggregates across
every deployment and retains for weeks. That is the wrong home for it, and the two systems
would disagree the first time one dropped a sample.

## Metrics NeMo Gym Emits

| `gym.http.connection_pool.connect_total` | Observable counter | count | All outbound aiohttp connection attempts (`connect()` calls), including attempts that later fail or are abandoned. |

Rollout duration is recorded even when a rollout fails. A crashed rollout still consumed
wall-clock time, and dropping those samples would bias the histogram toward the fast path.

### Memory Metrics

Memory metrics are emitted only when `telemetry.memory_profiling.enabled` is true. Server points carry `nemo.gym.server.name`, `nemo.gym.server.type`, and the root `process.pid`; server memory gauges also carry `memory.type`, which is `rss` or `pss`. Host points rely on the existing `host.name` resource attribute and carry no per-sample attributes.

RSS counts every resident page mapped by every process and can double-count pages shared by Uvicorn workers. PSS divides shared pages among the processes mapping them, so summing PSS across server trees is the better estimate of their combined host footprint. The sampled peak is not the kernel's exact lifetime peak: an allocation that begins and ends between samples can be missed.

Host usage is `total - available`, matching the memory the operating system cannot make available without swapping. Host totals describe the whole node, not only Gym processes; compare them with summed server PSS to separate Gym footprint from training, inference, Ray, and system pressure.

Descendants remain attributed while they stay in the server's Linux process tree. Detached or reparented processes and remote Ray actors are not included.

Compare these series with `http.server.active_requests` while increasing workload concurrency. Separate server processes export their HTTP metrics independently, so sum active requests by Gym server name when a server uses several Uvicorn workers.

### Token-Capture Metrics

Training-token capture runs on every captured model call, so these metrics are built to stay
cheap: with no metrics exporter a capture site does almost nothing, and frequent events
(outcomes, digests) are counted in process memory and read at each export rather than sent
to the SDK one by one.

`gym.token_capture.operation.duration_ms` carries:

- `nemo.gym.token_capture.operation`: what was timed. Operations at a protocol call site
  (`lineage.resolve`, `sink.begin_call`, `sink.put`, `ledger.record`, `ledger.record_failure`,
  `staging.build_record`, `staging_sink.stage`, `source.freeze`, `source.drop`) include time spent
  waiting for a worker thread. Gym's file stores also report their in-thread work
  (`sink.put.in_thread`, `ledger.record.in_thread`), so the difference is queueing.
  `file_lock.wait` is recorded only when acquiring a lock took at least 0.1 ms.
- `nemo.gym.token_capture.implementation`: the class implementing the protocol at that call
  site, for example `TokenCaptureStore` or a training framework's own sink, so pluggable
  implementations are measured without changes to them.
- `nemo.gym.token_capture.size_class`: the record's token count, bucketed as `lt_4k`, `lt_32k`,
  `lt_128k` or `ge_128k`, so a percentile compares records of similar length. Absent for
  operations without a record.
- `nemo.gym.token_capture.error`: `error` or `cancelled`, present only when the operation did
  not complete.

Dividing the duration sum by `gym.token_capture.operation.tokens_total` gives milliseconds per
token, which separates a slower implementation from longer sequences. Digest calls per staged
record show duplicated hashing; digest bytes per record show how much of a prefix is re-hashed.
`gym.token_capture.outcome_total` counts these outcomes: `parent_root`, `parent_resolved`, and
`parent_unresolved` (with the resolver's reason) for parent resolution; `poisoned` (with the ledger
failure reason); `capture_failed` (`write` on the model server; `build`, `staging_sink_error`, or
`staging_sink_rejected` on the inference worker); `late_write_dropped`; `marked_incomplete`;
`retire_skipped` (`stale_snapshot`); and `lock_acquired` (`shared` or `exclusive`). Reasons come
from a fixed set, and a reason a custom implementation invents is counted as `other`. An operation slower than 5 seconds also logs one warning per operation per minute.

### What `gym.verify.success_rate` Measures

It measures whether the **verification call completed**, not whether the task passed.

A verifier that correctly scores a wrong answer is a success. A verifier that raises an
exception is a failure. Task correctness is experiment telemetry, and putting it here would
turn this into a low-resolution accuracy metric living in the wrong system.

The value is cumulative over the reporting process's lifetime, not a windowed rate. A gauge
carries last-value semantics, so a rate cannot be expressed directly. A long-lived server
therefore shows a figure that moves more slowly as it ages. Read it as "this process's
success fraction so far," and use traces for anything finer.

### Why Only the Orchestrator Reports `gym.servers.active`

`gym.servers.active` is a gauge, so the exported value is whichever process wrote last.
If every server reported it, the result would be neither the fleet size nor any process's
view of it. The orchestrator is the only process that knows how many servers it started,
so it is the only writer. It sets the count after startup and zero on shutdown.

## HTTP Metrics

FastAPI auto-instrumentation emits the standard HTTP server metrics on every NeMo Gym
server:

| Metric | Dimensions |
| --- | --- |
| `http.server.active_requests` | `http.server_name`, `http.method` |
| `http.server.request.duration` | `http.route`, `http.request.method`, `http.response.status_code` |

Use these for request latency. They are dimensioned, so you can compare `/verify` against
`/v1/responses`, or isolate 500s, which is what latency questions usually require.

The Gym-specific `gym.http.connection_pool.queue_duration_ms` histogram measures client-side
connection acquisition separately from request latency. Its bounded attributes identify the
destination server, queue outcome (`ok` or `abandoned`), and which pool constraint caused the
wait (`total`, `per_host`, or `unknown`). It records one sample for each queued connection
acquisition (`connect()`), combining repeated waiter wakeups within that acquisition.
Redirect hops, aiohttp's internal reconnects, and Gym retries record separate samples when
their acquisitions queue. Connection attempts that acquire a slot immediately do not record
a queue-duration histogram sample.
`abandoned` means the wait ended before a slot became available, including timeout and cancellation.
Divide the number of `gym.http.connection_pool.queue_duration_ms` histogram samples by
`gym.http.connection_pool.connect_total` over the same interval and destination to calculate the
fraction of connection attempts that queued.

Both instruments use `nemo.gym.http.destination.server.name` for the request destination:
the configured server name for `ServerClient` calls, `remote_agent_service` for calls to the
remote agent's external service, or `external` for unlabeled direct calls. This differs from
the resource attribute `nemo.gym.server.name`, which identifies the Gym process recording the metric.

These pool metrics require telemetry initialization before client construction. Standalone
collection does not initialize telemetry automatically, so missing metrics do not mean no
queueing. See [HTTP Connection Pool](/reference/configuration#http-connection-pool) for process coverage.

### A Note on `gym.server.request_duration_ms`

`nemo-lens` declares a `gym.server.request_duration_ms` histogram. NeMo Gym does not use
it.

At the pinned `nemo-lens` version, that instrument records without attributes. Every
endpoint of every server type would land in one undimensioned histogram: a verification,
an inference call, and a liveness probe sharing one set of buckets. The result answers no
question anyone has. The dimensioned `http.server.request.duration` above supersedes it.

## Enabling and Disabling

Metrics follow the master switch and can be turned off independently:

```yaml
telemetry:
  enabled: true
  metrics_enabled: false   # traces only
```

Metrics export on a timer. The default interval is 10 seconds and is configurable with the
standard `OTEL_METRIC_EXPORT_INTERVAL` environment variable, in milliseconds. A process
that lives for less than one interval may exit before exporting anything.
