NeMo Gym emits a small, deliberate set of metrics. This page lists them, and explains what
is deliberately absent and why.

## Application Telemetry, Not Experiment Telemetry

These metrics answer "how is this software behaving?" — where time goes, what failed, how
a configuration performs on hardware you do not control.

They do not answer "how is my run doing?" Reward, accuracy, and benchmark scores are
experiment telemetry. They belong in Weights & Biases or MLflow, which are built for
comparing runs and keep data for the lifetime of a project. NeMo Gym already reports them
through `AggregateMetricsMixin` and continues to do so, unchanged.

Mirroring reward into OpenTelemetry would put a number in a system that aggregates across
every deployment and retains for weeks. That is the wrong home for it, and the two systems
would disagree the first time one dropped a sample.

## Metrics NeMo Gym Emits

| Metric | Type | Unit | Meaning |
| --- | --- | --- | --- |
| `gym.rollout.duration_ms` | Histogram | ms | Wall-clock duration of one rollout, from the agent server's `/run`. |
| `gym.verify.duration_ms` | Histogram | ms | Wall-clock duration of one verification. |
| `gym.verify.success_rate` | Gauge | fraction | Cumulative fraction of verifications that completed. See below. |
| `gym.servers.active` | Gauge | count | Number of servers the orchestrator started. |

Rollout duration is recorded even when a rollout fails. A crashed rollout still consumed
wall-clock time, and dropping those samples would bias the histogram toward the fast path.

## Attributed Metrics (Bottleneck Diagnosis)

The five metrics above all forward through `nemo-lens`'s `record_gym_metrics`, which is
undimensioned at the pinned commit — see "A Note on `gym.server.request_duration_ms`"
below for why that rules out using it for anything that needs to be broken down further.
The metrics in this section are created directly against the OTel Metrics API instead
(`nemo_gym.telemetry.gym_metrics`), specifically so they **can** carry attributes. Each
answers a "what is limiting this run" question the metrics above cannot:

| Metric | Type | Unit | Attributes | Gated By | Answers |
| --- | --- | --- | --- | --- | --- |
| `gym.concurrency.queue_wait_duration_ms` | Histogram | ms | `nemo.gym.concurrency.site` | `concurrency` | Is a task waiting for a concurrency-limiting semaphore slot instead of doing work? |
| `gym.rollout.completed_total` | Counter | count | `nemo.gym.rollout.outcome` (`success`\|`failure`) | `rollout` | What is this run's rollout throughput and failure rate? |
| `gym.sandbox.startup_duration_ms` | Histogram | ms | `nemo.gym.sandbox.provider` | `sandbox` | How long does provisioning one sandbox take, per provider? |
| `gym.sandbox.create_retry_total` | Counter | count | `nemo.gym.sandbox.provider` | `sandbox` | Is sandbox creation retrying, and how often? |
| `gym.model.call_duration_ms` | Histogram | ms | `nemo.gym.model.dialect`, `nemo.gym.server.name` | `model_call` | How long does one model-server call take, per dialect and server? |
| `gym.model.time_to_first_byte_ms` | Histogram | ms | `nemo.gym.model.dialect`, `nemo.gym.server.name` | `model_call` | How long until the first response byte — is inference queued behind other work? |
| `gym.http.timeout_total` | Counter | count | `nemo.gym.http.internal` | `http_client` | Is an outbound HTTP call timing out? |
| `gym.http.retry_total` | Counter | count | `nemo.gym.http.retry_reason` (`server_disconnected`\|`client_os_error`\|`timeout`\|`other`) | `http_client` | Is Gym's HTTP client retrying, and why? |
| `gym.process.cpu.percent` | Gauge | % | none — see resource attributes | `telemetry.cpu_sampling_enabled` | Is this process CPU-bound, and which span was running when it spiked? |

### Why These Are Attributed and the First Five Are Not

An undimensioned `gym.concurrency.queue_wait_duration_ms` would mix the rollout driver's
semaphore (typically hundreds of parallel tasks) with a judge's (typically single-digit
concurrency) into one histogram — exactly the "answers no question anyone has" failure
`gym.server.request_duration_ms` hits below, for the same reason: a number that averages
unrelated things together. The difference is that `record_gym_metrics` cannot be given
attributes at the pinned `nemo-lens` commit, so the metrics above route around it and talk
to the OTel SDK directly. Filter by `nemo.gym.concurrency.site` (or the equivalent
attribute on the other rows) to compare like with like — e.g. is the *rollout driver*
queueing, or is a *specific judge*, or a *specific sandbox provider*.

### Trajectory Throughput Is a Counter, Not a Rate

`gym.rollout.completed_total` counts completed rollouts by outcome; throughput and
failure rate are both derived downstream (`rate(...)` in your metrics backend) rather
than computed and flattened in NeMo Gym. This is the same tradeoff `gym.verify.success_rate`
hit — a gauge cannot express a rate on its own — resolved the other way: that one is
stuck with a lens-provided gauge and has to keep a cumulative running fraction instead;
this one is a local instrument, so it can just be a counter.

### Process CPU: a Gauge Linked to the Exact Span That Was Running

`gym.process.cpu.percent` is sampled **inline at span boundaries** — inside
`traced_endpoint`'s `finally`, `AsyncSandbox.start`/`exec`, and the `gym.job` span —
rather than on a background timer. That is a deliberate design constraint, not an
implementation shortcut: an OTel exemplar (a data point that carries a trace/span id) can
only be attached while the originating span is the *active* context, and OTel context does
not cross OS threads without explicit propagation. A decoupled background-thread sampler
would have no span to link to. So every `gym.process.cpu.percent` reading is taken by the
same code path that also stamps the reading onto that span's `nemo.gym.cpu.percent`
attribute — click through from a metric data point's exemplar to the exact span active
when it was recorded (Honeycomb supports this natively; confirmed against the pinned
`opentelemetry-sdk` 1.44.0, which attaches exemplars to a synchronous Gauge with no extra
filter configuration).

Both surfaces share one process-local sampler (`nemo_gym.telemetry.cpu`), rate-limited to
one real `psutil` read per `telemetry.cpu_sampling_enabled`'s
`cpu_min_resample_interval_s` (default 1 second) — a span closing inside that window
reuses the last cached reading rather than triggering a fresh syscall, which is also why
`nemo.gym.cpu.percent` can be up to that many seconds stale, the same "cumulative window"
caveat `gym.verify.success_rate` carries below.

`cpu_sampling_enabled` defaults to **off** — it is not implied by `metrics_enabled` or any
span group, since even inline sampling is an extra syscall on every (rate-limited) span
close plus an extra resource attribute per process:

```yaml
telemetry:
  cpu_sampling_enabled: true
  cpu_min_resample_interval_s: 1.0
```

**Reading `gym.process.cpu.percent` on a multi-core node:** `psutil` normalizes to one
logical core = 100%, so a busy multi-threaded process on a many-core node can legitimately
read 800%+. Every process that has `cpu_sampling_enabled` on also reports a static
`nemo.gym.host.cpu_count` resource attribute (read once, not sampled) — divide by
`100 * nemo.gym.host.cpu_count` for percent-of-node-capacity.

**Multi-node runs** need no special handling: every span/metric already carries
`host.name`, `process.pid`, and `service.instance.id` as resource attributes (see
[Configuration](/observability/configuration)), so each node's processes are
distinguishable without anything new from this feature.

### Not Yet Covered: Sandbox CPU, Ray Worker CPU, and All Memory

Process-level CPU for Gym's own server processes (agent/model/resources servers, the
rollout driver) is covered above. Still unmeasured: CPU *inside* a sandbox/container
(would need new per-provider work — a `docker stats` read, a cgroup v2 accounting-file
read — with no existing hook to build on), CPU of Ray worker processes spawned for sandbox
execution (separate OS processes with their own PID), and memory pressure of any kind.
`SandboxObservation` (the offline trajectory-capture schema, unrelated to OTel) has
`cpu_time_s` / `peak_memory_mib` fields, but nothing populates them from a real
measurement today. All of this is tracked as follow-up work.

### What `gym.verify.success_rate` Measures

It measures whether the **verification call completed**, not whether the task passed.

A verifier that correctly scores a wrong answer is a success. A verifier that raises an
exception is a failure. Task correctness is experiment telemetry, and putting it here would
turn this into a low-resolution accuracy metric living in the wrong system.

The value is cumulative over the reporting process's lifetime, not a windowed rate. A gauge
carries last-value semantics, so a rate cannot be expressed directly. A long-lived server
therefore shows a figure that moves more slowly as it ages. Read it as "this process's
success fraction so far," and use traces for anything finer.

### Why Only the Orchestrator Reports `gym.servers.active`

`gym.servers.active` is a gauge, so the exported value is whichever process wrote last.
If every server reported it, the result would be neither the fleet size nor any process's
view of it. The orchestrator is the only process that knows how many servers it started,
so it is the only writer. It sets the count after startup and zero on shutdown.

## HTTP Metrics

FastAPI auto-instrumentation emits the standard HTTP server metrics on every NeMo Gym
server:

| Metric | Dimensions |
| --- | --- |
| `http.server.request.duration` | `http.route`, `http.request.method`, `http.response.status_code` |

Use these for request latency. They are dimensioned, so you can compare `/verify` against
`/v1/responses`, or isolate 500s, which is what latency questions usually require.

### A Note on `gym.server.request_duration_ms`

`nemo-lens` declares a `gym.server.request_duration_ms` histogram. NeMo Gym does not use
it.

At the pinned `nemo-lens` version, that instrument records without attributes. Every
endpoint of every server type would land in one undimensioned histogram: a verification,
an inference call, and a liveness probe sharing one set of buckets. The result answers no
question anyone has. The dimensioned `http.server.request.duration` above supersedes it.

## Enabling and Disabling

Metrics follow the master switch and can be turned off independently:

```yaml
telemetry:
  enabled: true
  metrics_enabled: false   # traces only
```

Metrics export on a timer. The default interval is 10 seconds and is configurable with the
standard `OTEL_METRIC_EXPORT_INTERVAL` environment variable, in milliseconds. A process
that lives for less than one interval may exit before exporting anything.
