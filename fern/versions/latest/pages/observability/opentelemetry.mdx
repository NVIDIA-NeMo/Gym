NeMo Gym exports traces, metrics, and optional logs through
[nemo-lens](https://github.com/NVIDIA-NeMo/Lens). Telemetry is off by default.

A distributed trace follows a rollout across agent, model, and resources servers. Use it to find
slow requests and service failures. For saved model calls and agent activity, see
[Rollout Evidence](/main/observability/rollout-evidence).

## Quick Start

Install the optional dependency:

```bash
uv sync --extra dev --extra telemetry
```

Export to the console:

```bash
NEMO_GYM_OTEL_ENABLED=1 NEMO_GYM_OTEL_EXPORTER=console \
gym env start --resources-server example_single_tool_call --model-type vllm_model
```

Or send telemetry to an OTLP collector:

```bash
NEMO_GYM_OTEL_ENABLED=1 OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 \
gym env start --resources-server example_single_tool_call --model-type vllm_model
```

| Signal | Contents |
| --- | --- |
| Traces | Request spans across agent, model, and resources servers |
| Metrics | Rollout and verification durations, verification success rate, active servers, and HTTP metrics |
| Logs | Optional Python log records correlated with traces |

Instrumentation is a no-op when disabled or when nemo-lens is absent.

## Sandbox resources

Enable sandbox spans to record the number and declared shape of sandbox requests and
collect existing OpenSandbox resource readings through the same OTLP collector:

```yaml
telemetry:
  enabled: true
  span_groups: default,sandbox
  sandbox_resource_sample_interval_seconds: 10
```

`gym.sandbox.request` records one logical request, with
`nemo.gym.sandbox.request.id`, `requested.count`, and declared `requested.cpu`,
`requested.memory_mib`, `requested.disk_gib`, `requested.gpu` and `requested.gpu_type`
attributes under `nemo.gym.sandbox`. Missing quantities are unspecified. Sidecar
shapes are recorded separately. Compose records all service requests before starting
services, with collection and service identifiers; a failed creation therefore remains
in the requested inventory. Other callers record requests as they reach `start()`.
Count distinct request IDs per rollout, rather than counting provider retries.

`gym.sandbox.start` joins a successful request to `nemo.gym.sandbox.id` and records
the OpenSandbox submission under `submitted.requests.*` and `submitted.limits.*`
after provider clamping. Unspecified submission values are left to SDK defaults. OpenSandbox
adds `gym.sandbox.resource.allocation` with the inspection endpoint's effective
per-container requests and limits, preserving Kubernetes quantity strings and node
identity. Declared shape, effective scheduling requests, and effective limits are
separate quantities. The inspection endpoint is deployment-dependent; unavailable
or unrecognized responses produce `resource.status=unavailable` and an error type.
They never fall back to declared resources.

`gym.sandbox.resource.sample` preserves execd's original timestamp in
`nemo.gym.sandbox.sample.timestamp_ms`, CPU count, CPU usage percentage, and total/used
memory in MiB. With metrics enabled, the same readings also populate
`gym.sandbox.cpu_count`, `gym.sandbox.cpu_used_percentage`,
`gym.sandbox.memory_total_mib`, and `gym.sandbox.memory_used_mib` gauges. Gauge
exports contain the latest observation; resource spans preserve individual samples
and their source timestamps. These are instantaneous readings, not cumulative CPU
time, RSS, or lifetime memory peaks.

The creator owns sampling and carries its rollout, request and sandbox identity into
later records. Borrowed connections do not start duplicate samplers. Sampling stops
before deletion and attempts a final read. Each provider read has a two-second bound;
failures are recorded without blocking normal operation. Process death, expired
sandboxes and trace sampling can leave gaps; missing records are not zero usage.

Set the interval to `0` to disable provider resource reads. Request inventory remains
available. Provider reads require an active trace exporter and the sandbox span group;
metrics-only configurations do not start a sampler. No OpenSandbox deployment changes
or additional in-sandbox commands are needed. Providers without the resource capability
retain the requested inventory and lifecycle spans only.
