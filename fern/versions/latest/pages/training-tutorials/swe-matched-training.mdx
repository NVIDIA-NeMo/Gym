title: Matched SWE-Next training
---

These recipes bind SWE-Next tasks to the original `/run` adapters, SingleAgentTurn,
or Harbor. They support the reported small-task comparisons and larger experiments.
The recipe helpers prepare configurations and inputs; the launcher uses NeMo RL's
existing controller and `ray.sub`.

## Prepare from a resolved recipe

Use the original resolved configuration and provenance for the intended model and
route. The reference YAML `examples/training/swe_single_agent_turn.yaml` is an overlay
on RL's controller defaults, not a standalone resolved configuration. Preserve the
model checkpoint, sampling, context limit, optimizer and runtime settings from the
experiment being reproduced. There is no model download, parser clone or source/image
inventory in the preparation path.

```bash
python -m scripts.prepare_swe_single_agent_turn_recipe retarget \
  --prepared "$TEMPLATE_PREPARATION" --output "$NEW_PREPARATION" \
  --task-rows "$SELECTED_SWE_NEXT_ROWS" --dataset-manifest "$DATASET_MANIFEST" \
  --wandb-project "$WANDB_PROJECT" --wandb-entity "$WANDB_ENTITY"
```

This preserves selected task prompts and hidden verification fields. It replaces task
bindings and physical output paths, then materializes tasks in task-major, harness-minor
order. A single harness produces one row per task; the original five-harness mixture
produces five. With eight tasks and four generations, the corresponding update batches
are 32 and 160 episodes. The update target comes from the template. `--harness` composes
a different single harness from a single-harness template on the same route; Codex
also needs `--harness-assets-from` pointing to its prepared catalog.

Harbor conversion retains the SWE-Next grader, image, prompt and hidden-test isolation.
It uses the maintained task preparation path, which may read image metadata from a
registry. The lower-level converter accepts `--grader-python-archive` for task images
without a compatible grading interpreter. This archive is delivered only to the
verifier; task tests keep their own interpreter.

### Harness controls and prepared files

Every arm keeps the RL/vLLM context limit at 32,768, the per-call output limit at 1,024, temperature and top-p at 1, and thinking enabled with prior reasoning retained. The framework sampling settings also govern retry calls. Preserve the masked-reward `include` policy and complete batches when comparing arms.

| Harness | Paired runtime and automatic compaction control |
| --- | --- |
| OpenCode | 1.17.11; `compaction.auto=false` and `compaction.prune=false`. Per-adapter concurrency is 8 on both paths. Both enable `report_agent_sandbox_oom`; `/run` then separates setup from the 480-second invocation budget. Both routes bound setup commands at 480 seconds and retain explicit agent OOM observations. |
| Claude Code | 2.1.108; both routes bind `model_server` to `policy_model` and use CLI alias `claude-sonnet-4-6`. Preparation writes `claude-settings.json` with environment values `DISABLE_COMPACT=1`, `CLAUDE_CODE_MAX_CONTEXT_TOKENS=32768` and `CLAUDE_CODE_MAX_OUTPUT_TOKENS=1024`. The adapter stages this file in the sandbox through its `settings` option. Bare mode, thinking and 30 turns are explicit. |
| Hermes | Both routes use the pinned `hermes_agent` runtime; `/run` selects it with `runtime_python=null`. Compression is disabled, with 30 turns and a 60-second terminal timeout on both paths. |
| Pi | 0.80.2; `auto_compaction=false`, fixed 1,024-token output. The sandboxed adapter is configured directly, without importing a benchmark's settings. |
| Codex | 0.144.4; both routes use CLI alias `gym-policy-model` and the exported catalog described below. `multi_agent`, `code_mode` and `token_budget` remain disabled. |
| Atom (`nooa`) | Sandboxed `AtomHarness` with `handle_batch`, a 32,768-token context window and a 480-second worker budget. The shared sampling transport supplies the 1,024-token per-call limit. Preparation writes `atom-settings.yaml` with `atom.summarization.policy=none` and `atom.context_error_policy=raise`; `settings_file` stages it in each sandbox. |

Codex requires an existing export from [source revision `8c68d4c87dc54d38861f5114e920c3de2efa5876`](https://github.com/openai/codex/tree/8c68d4c87dc54d38861f5114e920c3de2efa5876), with adjacent `models.json`, `fallback.json` and `provenance.json` from Gym's pinned exporter. Preparation checks the source/version/exporter receipt, both content hashes, the exact alias, unique model records and unchanged fallback fields except the three context fields. It copies all three files into the output's `codex/` directory and hashes them in the recipe provenance. No catalog blob is checked into this recipe.

The catalog deliberately omits `context_window`, `max_context_window` and `auto_compact_token_limit` for that alias. Both adapter context overrides remain null. This removes Codex's automatic context threshold; the real 32,768-token boundary remains in RL/vLLM. The stable CLI alias is mapped to the configured policy model by Gym and need not equal the checkpoint pathname. Passing catalog checks alone does not qualify native CLI behavior or prove engine enforcement. Use a stack containing the catalog-support adapter change, and inspect real boundary and failure controls before training.

Atom requires the reviewed NOOA SDK change that supports `context_error_policy=raise`, together with the adapter’s `settings_file` transport. This stops context-error recovery from archiving history; `summarization.policy=none` separately disables automatic summarization. Keep the shared RL setting `token_capture.forest_training=false`. Recipe and schema checks alone do not establish runtime enforcement, capture correctness or training success.

Keep prepared Claude settings, Codex files and Atom settings on the shared mount at the recorded paths. Treat each running snapshot as fixed. Experimental launches do not repeat preparation inventories or conformance probes.

## Launch a fixed source snapshot

Record the RL and Gym revisions/diffs, resolved configuration, frozen task input and
compiled image path/build identity for each run. The original reported executions
used Gym `6b4cdc921d995f2061ff3e657025f846ebecbfe3` and RL
`ca10ee19d2856f299bf4b6217999d20b87be5ea4` plus recorded fixes. Those executions do not
qualify a later complete PR head. Use a compatible image built through RL's supported
Dockerfile; Python-only source changes do not require rebuilding compiled dependencies.

The source-mount route expects the image's editable paths `/opt/nemo-rl`,
`/opt/nemo_rl_venv`, `/opt/ray_venvs` and `/opt/gym_venvs`. Mount a fixed RL source tree
including its Gym submodule; keep results and caches outside it. Other image layouts
need their supported launcher configuration. Do not modify source used by active jobs.

```bash
export SLURM_ACCOUNT SLURM_PARTITION SHARED_ROOT
export NEMO_RL_ROOT CONTAINER CONFIG_PATH
export OPENSANDBOX_DOMAIN OPENSANDBOX_API_KEY
bash scripts/launch_swe_single_agent_turn_training.sh --source-mount --dry-run
bash scripts/launch_swe_single_agent_turn_training.sh --source-mount
```

The launcher starts the real program without extra preflight inventories. It reads
`cluster.gpus_per_node` unless `GPUS_PER_NODE` is supplied, requests one exclusive node
and node memory, and accepts `--walltime`, `--exclude` and optional `SLURM_QOS`.
Four-GPU ARM Blackwell and eight-GPU x86 H100 configurations require compatible
model parallelism and compiled images; changing allocation alone does not adapt a recipe.
The baked-source route remains available by omitting `--source-mount`.

For the original compiled image, `--reuse-swe-rebench-venv` aliases its compatible
resource-server environment to SWE-Next inside the disposable container. This reuses
dependencies, not the SWE-rebench benchmark or grader. W&B credentials can be supplied
through `scripts/with_wandb_auth.py`; they must remain outside source and configuration.

## Continue the same logical run

```bash
python -m scripts.prepare_swe_single_agent_turn_recipe continue \
  --prepared "$ORIGINAL_PREPARATION" --output-dir "$NEW_ATTEMPT" \
  --wandb-id "$ORIGINAL_WANDB_ID" --prior-job-id "$PRIOR_JOB_ID"
```

Use the original checkpoint-producing preparation, not a failed continuation directory.
The helper preserves the complete data and checkpoint blocks and original input paths,
sets W&B `resume=must`, and relocates physical output paths. Keep the original inputs
available. Launch without W&B overrides that would clear this identity. The owner must
identify a published checkpoint; this command neither inspects nor selects one.
Continuation is not a fresh baseline, and discarded updates must not be counted twice.
The RL companion includes the guarded optimizer restore fix used by the continuation.

## Larger runs from prepared inputs

Reuse a resolved config for the intended model, harness and route. Keep its referenced
harness files, Harbor tasksets and image metadata available. Supply a frozen JSONL
with one materialized row per distinct task. This path does not repeat task conversion,
registry lookups, model downloads or checkpoint inspection.

```bash
python -m scripts.prepare_swe_single_agent_turn_recipe experiment train \
  --template "$PREPARED/config.yaml" --inputs "$FROZEN_TRAIN_JSONL" \
  --output "$NEW_RUN" --policy opencode-pi-harbor \
  --steps 100 --tasks-per-step 16 --generations 4 --checkpoint-period 25
```

With 512 distinct rows, this plans 6,400 episodes and checkpoints at steps 25, 50,
75 and 100, retaining four checkpoints. The fast configuration uses 128 rows,
`--steps 40 --tasks-per-step 8 --checkpoint-period 10`. Other scientific settings,
including the original model, sampling and optimizer, come from the supplied template.
Logs, caches, checkpoints and Pi sandboxed artifact exports receive fresh output
paths. This starts a fresh run; use `continue` for a checkpoint continuation.

For a matched 50:50 mixture, use the same task order as the single-harness arm and
assign alternate rows to OpenCode and Pi. The maintained materializer accepts
`task_harnesses=["opencode", "pi"] * (len(rows) // 2)` together with
`harnesses=["opencode", "pi"]`. It emits one row per task; four generation siblings
stay on that task's assigned harness. Without `task_harnesses`, the materializer's
existing behavior repeats every task across every requested harness. Do not use
that cross-product as a substitute for a matched distinct-task mixture.

The template determines concurrency, resources and route wiring. The command does
not choose a dataset split, authorize compute, or establish scientific comparability.
Record the frozen train/held-out split, exclusions, source snapshot and image identity
alongside the generated `EXPERIMENT.json` and configuration.

## Raw held-out evaluation

Use an evaluation template already wired for one harness and its benchmark, plus
one materialized row per held-out task. Taskset names must end in the selected
harness name, such as `swe_next_opencode`. The command expands every task into three
identical trial rows and writes `EVALUATION.json`, `evaluation.jsonl` and `config.yaml`.

```bash
python -m scripts.prepare_swe_single_agent_turn_recipe experiment evaluate \
  --template "$EVAL_TEMPLATE" --inputs "$HELD_OUT_JSONL" \
  --output "$EVAL_OUTPUT" --policy original --harness opencode --trials 3

export CONFIG_PATH="$EVAL_OUTPUT/config.yaml"
bash scripts/launch_swe_single_agent_turn_training.sh --collect-trajectories
```

To evaluate a trained policy, additionally pass `--step 25 --weights
"$TRAIN_RUN/checkpoints/step_25/policy/weights"` and an appropriate policy label.
Choose an explicitly published checkpoint; do not pass `tmp_step_*` or select
`latest` implicitly. The configuration uses `megatron_bridge` weights, disables
checkpoint writing and starts with fresh controller state. It does not resume the
training optimizer or export/copy the checkpoint. Normal model loading must establish
that the chosen weights can be restored.

This requires the companion RL raw collector. It refits the generation workers and
calls the production Gym environment without reconstructing training tokens. Each
completed result or infrastructure-failure sidecar is appended immediately with a
global row index, so a later transport failure preserves earlier rows. Collection
performs no optimizer updates. The ordinary training path retains its capture checks.

```bash
python -m scripts.summarize_swe_evaluation \
  --run original "$BASELINE/EVALUATION.json" "$BASELINE/logs/exp_001/trajectory_collection.jsonl" \
  --run candidate "$CANDIDATE/EVALUATION.json" "$CANDIDATE/logs/exp_001/trajectory_collection.jsonl" \
  --baseline original --output comparison.json
```

Scores use all trials per task, then average across tasks; they are not best-of-three.
Missing, duplicate, malformed or infrastructure-incomplete rows withhold the score.
Complete matched runs use a paired bootstrap over tasks, preserving their repeated
trials. Comparisons require the same harness and exact evaluation input bytes; this
check does not independently establish matched scientific settings. External test
results must not select a checkpoint or tune the recipe.

Original-model OpenCode and Pi collection has completed through this raw path with
384/384 valid results per harness and final logger sync. Trained-checkpoint evaluation
and the portable preparation command still require their own runtime qualification;
those baseline results do not establish learning or checkpoint restore correctness.
