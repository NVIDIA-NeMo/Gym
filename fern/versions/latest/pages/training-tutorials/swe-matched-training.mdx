# Matched SWE training

This experimental recipe runs repeated SWE-rebench tasks through NeMo RL's existing single-controller GRPO entrypoint. The preparer wires OpenCode, Claude Code, Hermes, Pi and Codex on all three routes. `old-run` relays each harness's actual `/run` endpoint and explicitly configures its provider for attaching to the resource-owned sandbox; `single-agent-turn` and `harbor` use agent sessions. Preparation and offline checks do not establish training success or equivalence between routes.

Prepared configs set the existing Gym development override `allow_unsupported_pairing=true`. SWE-rebench's unchanged `allowed_agents` list names only `opencode_sandboxed_agent`; the collector otherwise rejects the other `/run` pairings and all five session adapter types. This override admits experimental validation runs while real pairing qualification is pending. It also applies to a Harbor dataset's declared harness restrictions; the converted dataset currently declares none. Complete real model/task controls and obtain benchmark-owner review before adding qualified pairings to the catalog.

The default is 32 tasks, 20 updates, eight prompts per harness per update and four generations per prompt. Rows follow task order, then harness order, without shuffling. Each group of eight tasks is one update; four updates visit the full 32-task roster. A five-harness run has 160 input rows, 40 prompts per update and 160 episodes per update. One harness has 32 episodes per update. The single input file, in-order sampler and full-group thresholds keep each complete cohort together; faster completions cannot replace it with later tasks. The same seed, model, tasks and training settings must be used for both comparison arms.

Supported harness order is `opencode claude_code hermes pi codex`, including subsets in that order. Atom is unavailable: its pinned SDK still archives history on context overflow, and its sandbox worker does not receive the required settings file. A proposed SDK `context_error_policy=raise` needs approval and qualification, along with worker settings transport and separate `summarization.policy=none`. A six-harness run would require 192 episodes per update; this recipe does not emit one.

## Prepare one arm

Set `NEMO_RL_ROOT`, `RL_REVISION`, `SOURCE_ROWS`, `PARSER_CACHE`, `MODEL_PATH` and `OUTPUT_DIR` to your selected inputs. Run from the Gym checkout:

```bash
uv run python scripts/prepare_swe_single_agent_turn_recipe.py \
  --rl-root "$NEMO_RL_ROOT" --rl-revision "$RL_REVISION" \
  --source "$SOURCE_ROWS" --parser-cache "$PARSER_CACHE" \
  --model 4b --model-path "$MODEL_PATH" --output-dir "$OUTPUT_DIR" \
  --route single-agent-turn --harnesses opencode --count 32 --steps 20
```

Prepare a fresh output directory for each arm. Change `--route` to `old-run` for the corresponding harness baseline or `harbor` for converted tasks. Use `--harnesses opencode claude_code hermes pi codex --codex-catalog "$CODEX_EXPORT/models.json"` for all five, or retain `--harnesses opencode hermes pi` for the original three-harness blend. `--count 8 --steps 5 --harnesses opencode` selects the smaller qualification run. For first-update timing, use `--count 8 --steps 1 --harnesses opencode`: eight prompts produce 32 episodes at up to 16 concurrent episodes, followed by one optimizer update and a step-one checkpoint. Repeat with `--model 30b` and its pinned snapshot to compare models. Keep collection, policy training, refit and checkpoint durations separate; one update does not establish learning. Add `--wandb-project` with an existing destination, and provide `WANDB_ENTITY` and credentials through the environment. Without that option, local logs remain enabled.

The output contains `source.jsonl`, `train.jsonl`, `config.yaml` and `provenance.json`. Harbor also contains converted tasks, their vendored verifier code and prepared image metadata. Verifier fields remain outside the model prompt. Preparation rejects skipped Harbor tasks, modified source rows, changed code and missing image pins. It starts no model, sandbox or training job.

### Harness controls and prepared files

Every arm keeps the RL/vLLM context limit at 32,768, the per-call output limit at 1,024, temperature and top-p at 1, and thinking enabled with prior reasoning retained. The framework sampling settings also govern retry calls. Preserve the masked-reward `include` policy and complete batches when comparing arms.

| Harness | Paired runtime and automatic compaction control |
| --- | --- |
| OpenCode | 1.17.11; `compaction.auto=false` and `compaction.prune=false`. Per-adapter concurrency is 8 on both paths. Both enable `report_agent_sandbox_oom`; `/run` then separates setup from the 480-second invocation budget. Both routes bound setup commands at 480 seconds and retain explicit agent OOM observations. |
| Claude Code | 2.1.108; both routes bind `model_server` to `policy_model` and use CLI alias `claude-sonnet-4-6`. Preparation writes `claude-settings.json` with environment values `DISABLE_COMPACT=1`, `CLAUDE_CODE_MAX_CONTEXT_TOKENS=32768` and `CLAUDE_CODE_MAX_OUTPUT_TOKENS=1024`. The adapter stages this file in the sandbox through its `settings` option. Bare mode, thinking and 30 turns are explicit. |
| Hermes | Both routes use the pinned `hermes_agent` runtime; `/run` selects it with `runtime_python=null`. Compression is disabled, with 30 turns and a 60-second terminal timeout on both paths. |
| Pi | 0.80.2; `auto_compaction=false`, fixed 1,024-token output. The sandboxed adapter is configured directly, without importing a benchmark's settings. |
| Codex | 0.144.4; both routes use CLI alias `gym-policy-model` and the exported catalog described below. `multi_agent`, `code_mode` and `token_budget` remain disabled. |

Codex requires an existing export from [source revision `8c68d4c87dc54d38861f5114e920c3de2efa5876`](https://github.com/openai/codex/tree/8c68d4c87dc54d38861f5114e920c3de2efa5876), with adjacent `models.json`, `fallback.json` and `provenance.json` from Gym's pinned exporter. Preparation checks the source/version/exporter receipt, both content hashes, the exact alias, unique model records and unchanged fallback fields except the three context fields. It copies all three files into the output's `codex/` directory and hashes them in the recipe provenance. No catalog blob is checked into this recipe.

The catalog deliberately omits `context_window`, `max_context_window` and `auto_compact_token_limit` for that alias. Both adapter context overrides remain null. This removes Codex's automatic context threshold; the real 32,768-token boundary remains in RL/vLLM. The stable CLI alias is mapped to the configured policy model by Gym and need not equal the checkpoint pathname. Passing catalog checks alone does not qualify native CLI behavior or prove engine enforcement. Use a stack containing the catalog-support adapter change, and inspect real boundary and failure controls before training.

Prepared Claude settings and Codex files are included in the launcher's existing content-hash checks. Keep the entire output directory on the shared mount; moving or editing individual files invalidates the prepared configuration.

## Build and identify the runtime

Use RL's official `docker/Dockerfile`, its selected dependency lock and initialized submodules. Current Gym requires `uv >=0.13.4`; select `0.13.6` through the Dockerfile's supported build argument and use that version to check the lock. Build a Linux ARM64 release image from the reviewed local checkout:

```bash
cd "$NEMO_RL_ROOT"
git submodule update --init --recursive
docker buildx build --platform linux/arm64 --target release \
  --build-context nemo-rl=. --build-arg UV_VERSION=0.13.6 \
  -f docker/Dockerfile --tag "$IMAGE_TAG" --push .
```

Record the resulting immutable image reference as `registry/repository@sha256:...`, then convert that exact image to the cluster's SquashFS format using its supported Enroot workflow. The launcher requires a build receipt JSON with `image`, `platform` (`linux/arm64`), `gym_commit`, `rl_commit`, `gym_lock_sha256`, `rl_lock_sha256` and `squashfs_sha256`. Obtain these from the actual build checkout, lockfiles, image registry and SquashFS bytes. A receipt describes a completed build; copying expected recipe values into a receipt is not build evidence.

The launcher compares that receipt with preparation, hashes the SquashFS, and checks production source files again inside the image. It imports Gym and RL from the image's checked paths. Source mounts do not replace the installed dependencies. A successful preflight still does not prove optimizer, weight-refit or checkpoint behavior.

## Submit one four-GPU node

This recipe targets a whole ARM64 node with four GB300 GPUs, with two GPUs training and two serving vLLM. Both use tensor parallelism of two. It requires at least 32 host CPUs and 128 GiB RAM. Check account, partition, QOS and available hardware before submission; eight-GPU H100 nodes need a different qualified recipe.

Keep the prepared assets, parser, model snapshot, container and both source checkouts under `SHARED_ROOT`. Set `CONTAINER` to the SquashFS, `CONTAINER_PROVENANCE` to its build receipt, and `CONFIG_PATH` to the prepared YAML. Supply the required `OPENSANDBOX_DOMAIN` and `OPENSANDBOX_API_KEY` through the environment. Then run from Gym:

```bash
export SLURM_ACCOUNT SLURM_PARTITION SHARED_ROOT
export NEMO_RL_ROOT CONTAINER CONTAINER_PROVENANCE CONFIG_PATH
export OPENSANDBOX_DOMAIN OPENSANDBOX_API_KEY
bash scripts/launch_swe_single_agent_turn_training.sh --dry-run
bash scripts/launch_swe_single_agent_turn_training.sh
```

The dry run performs host checks and prints the command without submitting. The real invocation uses the selected RL `ray.sub`, one node, and `examples/run_grpo_single_controller.py`. `SLURM_QOS`, `WALLTIME` and `EXP_NAME` are optional. Prepare another arm to change training settings; the launcher accepts no hidden configuration overrides.

## Inspect the evidence

Before training, run the gold, empty-patch and infrastructure-failure verifier controls through the selected routes. Keep incomplete verification masked and report unknown termination causes honestly. During training, preserve full rollout records, token/logprob captures, training masks, retry and cleanup evidence. This recipe uses RL's ordinary receipt mode (`forest_training=false`): a reconstructed training row is overlong when its token count reaches the training sequence limit. Inspect the actual consumed records, including separate harness and capture failure masks.

Require nonempty trainable tokens, finite loss and gradients, actual optimizer updates, successful refits and step-10/20 model and optimizer checkpoints for the full run. Compare rewards over complete four-update task cycles, per harness and task, with actual throughput and collection time. Checkpoints from the five-update qualification do not satisfy the full-run checkpoint requirement. Neither preparing this recipe nor passing its unit tests is a learning result.
