# Single- and Multi-Harness Training

SingleAgentTurn asks a Resources Server to prepare and verify tasks. Harbor reads the sandbox and verifier from native task folders. Both support one harness or several harnesses training the same policy. A prompt's GRPO siblings share its harness; different groups can use different harnesses.

Use [NeMo RL setup](/main/tutorials/training-tutorials/nemo-rl-grpo/setup), a checkout with [taskset routing](https://github.com/NVIDIA-NeMo/RL/pull/4429), your sandbox/runtime configuration, and [external harness capture](/main/tutorials/training-tutorials/external-agent-harnesses). Keep Gym at `3rdparty/Gym-workspace/Gym` in the RL checkout.

## SingleAgentTurn

The [full configuration](https://github.com/NVIDIA-NeMo/Gym/blob/main/examples/training/single_agent_turn_multi_harness.yaml) uses SWE-rebench and SWEmer v1 with OpenCode, and SWEmer v2 and SWE Internal v1 with Pi. Each complete dataset has one taskset and one harness. For example, its SWE-rebench environment is:

```yaml
swe_rebench_single_agent_turn:
  _inherit_from: single_agent_turn
  environment_servers:
    single_agent_turn:
      resources_server:
        type: resources_servers
        name: swe_rebench_resources_server
      agent_server:
        type: responses_api_agents
        name: opencode_agent
      resources_tool_transports: []
environment_server_routes:
  swe_rebench: swe_rebench_single_agent_turn
```

From Gym, run `python resources_servers/swe_rebench/prepare_swe_rebench.py`. Obtain the other prepared training files through their existing internal distribution. The configuration names all four paths under `resources_servers/<dataset>/data/<dataset>_training.jsonl`; the corresponding READMEs describe access and row formats. Source JSONL files stay unchanged. Dataset `taskset` declarations tell ordinary collation which route to attach.

## Harbor

The [full configuration](https://github.com/NVIDIA-NeMo/Gym/blob/main/examples/training/harbor_multi_harness.yaml) reuses an **already prepared native Terminal-Bench 2.1 run** from the [existing Harbor tutorial](/main/tutorials/evaluation-tutorials/terminal-bench-2-1-harbor). It expects `results/harbor/terminal_bench_2_1/tasks_opencode_agent.jsonl` and `run_config_opencode_agent.yaml`, with the selected task folders still available. `gym dataset pull terminal_bench_2_1` fetches folders; it does not create those prepared run artifacts. Reuse your existing selection and mapping.

Both harnesses use the same selected tasks. Keep the OpenCode rows as prepared. This command changes only the Pi routing label:

```bash
mkdir -p results/training/harbor
jq -c '.task_id.taskset="terminal-bench-pi"' \
  results/harbor/terminal_bench_2_1/tasks_opencode_agent.jsonl > results/training/harbor/pi.jsonl
```

The OpenCode environment stays as prepared. Pi uses the same folder and digest mapping:

```yaml
terminal-bench-pi-environment:
  _inherit_from: harbor_environment_server
  environment_servers:
    harbor:
      agent_server:
        type: responses_api_agents
        name: terminal-bench-pi-agent
      tasksets:
        terminal-bench-pi: ${harbor_terminal_5fbench_5f2_5f1_environment.environment_servers.harbor.tasksets.terminal_bench_2_1}
environment_server_routes:
  terminal-bench-pi: terminal-bench-pi-environment
```

The full configuration includes the matching Pi agent, OpenCode route and dataset declarations. Native Harbor uses each task's own verifier; SWE Resources Server settings do not apply to it.

## Collate and train

From Gym, select either configuration and collate its declared datasets:

```bash
CONFIG=examples/training/single_agent_turn_multi_harness.yaml
ROUTE=sat
# Or: CONFIG=examples/training/harbor_multi_harness.yaml; ROUTE=harbor

gym dataset collate --config "$CONFIG" \
  +output_dirpath="results/training/$ROUTE" +mode=train_preparation \
  ++use_absolute_ip=false ++policy_base_url=http://127.0.0.1:8000 \
  ++policy_api_key=unused ++policy_model_name=unused
```

The placeholder model settings are for collation, which starts no model. NeMo RL supplies the real policy endpoint during training. Add your usual provider/runtime configuration to the selected Gym configuration.

From RL, use the existing Nano single-controller recipe and launcher. These overrides replace its Gym wiring and training-data path; model, optimizer, sampling and GPU layout stay in the base recipe:

```bash
uv run examples/run_grpo_single_controller.py \
  --config examples/configs/recipes/llm/grpo-nanov3-30BA3B-2n8g-noncolocated-async-gym-single-controller-token_capture-r3-defer.yaml \
  '~env.nemo_gym' "++env.nemo_gym.config_paths=[3rdparty/Gym-workspace/Gym/$CONFIG]" \
  "data.train.data_path=3rdparty/Gym-workspace/Gym/results/training/$ROUTE/train.jsonl" \
  "checkpointing.checkpoint_dir=results/$ROUTE-multi-harness" \
  "logger.log_dir=logs/$ROUTE-multi-harness" "logger.wandb.name=$ROUTE-multi-harness"
```

This base recipe uses two eight-GPU nodes. Retain its runtime and allocation requirements and use fresh output directories. For single-harness training, keep just that harness's datasets and routes. Declaring a whole dataset for both harnesses uses every task twice; collation does not create a disjoint split.
