# Multi-Harness Training Development Handoff

This handoff describes how to resume the two-repository implementation and
complete its GPU validation. The target behavior matches FineEnvs fan-out:
each source task is expanded once for every configured harness, repeated GRPO
siblings stay inside their task-and-harness prompt group, and all groups train
one shared policy.

The P0 harnesses are:

- OpenCode (`anyterminal_opencode`)
- OpenClaw (`anyterminal_openclaw`)
- Pi (`anyterminal_pi`)
- Hermes (`anyterminal_hermes`)

## Implemented contract

Gym exposes three distinct routing modes:

| Field | Contract |
|---|---|
| `agent_map` | Route every matching row to one named harness. |
| `agent_pool` | Deterministically choose one configured harness per source task. |
| `fan_out` | Create the task-by-harness cross-product. |

The training configuration uses this generic source route:

```yaml
env:
  nemo_gym:
    fan_out:
      anyterminal_multi_harness:
        - anyterminal_opencode
        - anyterminal_openclaw
        - anyterminal_pi
        - anyterminal_hermes
```

`fan_out` expansion happens before repeated generations, dataloader batching,
and NeMo RL Gym-shard selection. Every expanded row receives a concrete
`agent_ref` and `_ng_fan_out_index`. NeMo RL consumes that assignment before
Gym dispatch so a row is not expanded twice. A rollout never changes harness
after it starts.

Do not rename the generic source to a harness-specific name such as
`anyterminal_hermes`; the source route is intentionally neutral.

## OpenClaw runtime fix

The unresolved configuration is in
`responses_api_agents/anyterminal_agent/configs/anyterminal_openclaw.yaml`.
It previously selected `tools.profile: coding`. OpenClaw 2026.6.11 expands
that profile into a broad tool catalog, including web, memory, sessions, cron,
media, planning, and other tools that Terminal-Bench does not need. Their
schemas overflow this model's initial context before the first model request.

The branch now uses this minimal Terminal-Bench policy:

```yaml
openclaw_config:
  agents:
    defaults:
      workspace: "."
  tools:
    profile: minimal
    alsoAllow:
      - exec
    deny:
      - session_status
```

OpenClaw's `minimal` profile contributes `session_status`; `alsoAllow` adds the
shell `exec` tool; the explicit deny removes `session_status`. Gym's
`OpenClawAgent._merge_headless_tool_denies()` additionally denies `message`,
so the intended effective tool set is only `exec`. That is enough to inspect,
edit, and test files in a Terminal-Bench container while keeping the prompt
small.

The resolved profile is asserted in
`tests/unit_tests/test_anyterminal_multi_harness.py`. An OpenClaw app unit test
also verifies that config construction preserves `profile`, `alsoAllow`, and
the user deny while adding the headless `message` deny. The focused tests pass
57/57 with:

```bash
uv run pytest -q tests/unit_tests/test_anyterminal_multi_harness.py
uv run pytest -q responses_api_agents/openclaw_agent/tests/test_app.py
git diff --check
```

The decisive check is still a real Nano rollout: both OpenClaw siblings must
reach the model server, create token-capture records, and avoid the local
context-overflow response.

## Expected shape and acceptance gates

With four source tasks, four harnesses, and two siblings per prompt group, the
run must produce:

```text
4 source tasks x 4 harnesses = 16 prompt groups
16 prompt groups x 2 siblings = 32 rollouts
32 rollouts / train batch 8 = 4 optimizer steps
```

Do not call a run successful from its process exit code alone. Verify all of
the following:

1. Every source task has two results under each of OpenCode, OpenClaw, Pi, and
   Hermes.
2. Every result has non-empty policy output, `mask_sample=false`, no failure
   kind or reason, and no agent, container, or sandbox timeout.
3. Every unmasked rollout contains captured generated token IDs and log
   probabilities, with no incomplete or ambiguous capture chain.
4. TMPE is finite for every accepted sample and every optimizer step has eight
   valid samples.
5. W&B contains four optimizer steps plus the complete Gym result tables.
6. Reward and advantages are finite and have non-zero variance; loss and
   gradient norm are finite, and gradient norm is not identically zero.
7. Policy-to-generation weight synchronization or refit completes initially
   and after every optimizer step.

## Evidence and known failure

The first real Nano Omni two-node run reached all four harnesses for the first
Terminal-Bench task and created W&B run
[`0iisypwg`](https://wandb.ai/adlr/multi-harness-RL/runs/0iisypwg). It is
diagnostic evidence only, not a passing training run:

- OpenCode rendered a prompt at the old 8,192-token context limit, leaving no
  generation token; vLLM returned HTTP 400.
- Hermes consumed the old 4,096-token budget entirely in reasoning.
- SingleController failed closed before optimizer step 0 when only three of
  four required prompt groups remained.

Commit `c4f1a073` raises the policy context to 16K, raises generation to 8K,
reserves OpenCode input/output headroom, and disables debug-only FlashInfer
autotuning. A second diagnostic run
([`174bdvd7`](https://wandb.ai/adlr/multi-harness-RL/runs/174bdvd7)) proved
real two-sibling dispatch through all four harnesses, but showed that an
OpenCode automatic-compaction prompt could still reach the full advertised
16K boundary and leave no serving token. Commit `8bf35a99` therefore advertises
15,872 tokens to OpenCode while retaining vLLM's 16,384-token hard limit.

A subsequent run
([`ygai6fjs`](https://wandb.ai/adlr/multi-harness-RL/runs/ygai6fjs)) made the
request owner unambiguous: both OpenClaw siblings rendered 16,384-token prompts,
received HTTP 400, and finalized with `rollout_failed:no_records`. Commit
`85c79975` applies the 15,872-token advertised context to OpenClaw in all three
multi-harness recipes. These runs are diagnostic evidence only, not passing
training runs.

The latest Nano run was Slurm job `2177783`, with W&B run
[`z31vasi6`](https://wandb.ai/adlr/multi-harness-RL/runs/z31vasi6). It started
all four harness groups and confirmed that the OpenClaw 15,872-token guard
prevents the earlier vLLM HTTP 400. However, both OpenClaw siblings failed
locally before making a model request. Each stored this response with zero
input and output usage:


token.
