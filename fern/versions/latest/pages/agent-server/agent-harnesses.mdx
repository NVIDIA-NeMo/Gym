# Agent Harnesses

An agent harness is the orchestration layer between a model and an environment. It owns the agent loop, prompts, tool execution, trajectory construction, and stopping behavior. Choosing a different harness can change results even when the model and dataset stay fixed.

NeMo Gym includes two kinds of agents:

- **General-purpose harnesses** can be reused across environments or provide a reusable bridge to an external agent framework.
- **Benchmark-specific agents** encode the protocol, tools, or grading flow for one benchmark. They are documented with that benchmark rather than in this reference.

<Note>
The table describes the 20 general-purpose harnesses currently shipped in `responses_api_agents/`. Each linked README is the source of truth for prerequisites, supported execution modes, and harness-specific fields.
</Note>

## Choose a Harness

Start with the simplest harness that provides the interaction pattern your environment needs:

- **No tools or straightforward tool calling:** use `simple_agent`. Use `non_executing_simple_agent` only when the model's tool call is the final answer and must not be executed.
- **A `reset`/`step` environment with per-step rewards:** use `gymnasium_agent`.
- **Simulated tools:** use `tool_simulation_agent`.
- **SWE-bench-style coding:** use `swe_agents` for OpenHands or OpenCode, `mini_swe_agent_2` for mini-swe-agent with a provider-neutral sandbox, or `anyswe_agent` to compare multiple Gym coding agents behind one execution and grading path. `mini_swe_agent` remains available for its legacy Docker or Singularity workflow.
- **Agentic coding through an external CLI:** use `claude_code_agent`, `codex_agent`, `kilocode_agent`, `opencode_agent`, `openclaw_agent`, or `pi_agent`. Check the README before training: several of these integrations are eval-only.
- **Terminal-Bench tasks:** use `anyterminal_agent` to place a compatible Gym agent and verifier in the same task container.
- **LangGraph research patterns:** use `langgraph_agent`. Non-monotonic trajectories, such as parallel-thinking graphs, require extra handling before NeMo RL training.
- **Reusable external environment libraries:** use `aviary_agent` for FutureHouse Aviary or `verifiers_agent` for Prime Intellect Verifiers.
- **Hermes:** use `hermes_agent` for the Hermes tool-using harness directly.
- **A service you host:** use `remote_agent` when your service can implement the OpenAI `/v1/responses` contract.

<Tip>
For a new environment, begin with `simple_agent` unless the environment protocol or external harness requires one of the specialized adapters. This keeps the model, tools, and verifier easy to isolate while you validate the task.
</Tip>

## Configure a Harness

Configuration is composed from named server blocks. Harnesses do not all expose identical fields, so use the harness README and config files alongside these common patterns.

### Wire a Model Server

Harnesses that use a Gym model server declare a `ModelServerRef` by server `type` and `name`:

```yaml
my_agent:
  responses_api_agents:
    simple_agent:
      entrypoint: app.py
      resources_server:
        type: resources_servers
        name: my_resources
      model_server:
        type: responses_api_models
        name: policy_model
```

The reference points to the top-level `policy_model` block selected by `--model-type` or supplied in a config file. This lets the same agent config run against vLLM, OpenAI, Azure OpenAI, or another supported model server without embedding its network address.

Some CLI-backed harnesses also support a direct provider URL, while others require or prefer `model_server`. The harness README documents which path takes precedence. See [Configuration: Agent Server Fields](/reference/configuration#agent-server-fields) and [Configure Models](/model-server) for the full server syntax.

### Attach a Sandbox Provider

Sandbox-backed harnesses commonly select a named provider and provide a per-task `sandbox_spec`:

```yaml
my_agent:
  responses_api_agents:
    mini_swe_agent_2:
      entrypoint: app.py
      sandbox_provider: sandbox
      sandbox_spec:
        image: docker://python:3.12-slim
        ttl_s: 1800
        resources:
          cpu: 2
          memory_mib: 8192

sandbox:
  opensandbox:
    connection:
      domain: ${oc.env:OPENSANDBOX_DOMAIN}
      api_key: ${oc.env:OPENSANDBOX_API_KEY}
```

Pass the agent and provider configs together to `gym env start`. Keeping the provider in a separate named block allows a compatible harness to switch between OpenSandbox, Docker, Apptainer, and other providers without changing its orchestration logic. See [Sandbox API](/infrastructure/sandbox) for provider setup and supported `SandboxSpec` fields.

### Load Agent Skills

Skills are a run-level input. Point `skills.path` at a directory containing one subdirectory per skill:

```bash
gym eval run --no-serve \
  --agent my_agent \
  --input data/tasks.jsonl \
  --output results/rollouts.jsonl \
  +skills.path=.agents/skills/
```

Gym records and forwards a `skills_ref`; the harness must then stage the files where its runtime discovers them. `claude_code_agent` and `codex_agent` provide native adapters today. Do not assume that another harness loads skills merely because `skills.path` is accepted by rollout collection. See [Agent Skills](/agent-server/agent-skills) for the directory contract, provenance fields, and adapter instructions.

### Override the Policy Endpoint Per Request

External RL trainers may route each episode through a different OpenAI-compatible proxy. Harnesses that implement this capability accept `policy_base_url`, and optionally `policy_api_key`, on the `/run` request:

```json
{
  "responses_create_params": {
    "input": [{"role": "user", "content": "Fix the failing test."}]
  },
  "policy_base_url": "http://trainer-proxy:8000/v1",
  "policy_api_key": "EMPTY"
}
```

When present, the request-level endpoint takes precedence over the configured `model_server` for that rollout. This is **not a universal Agent Server field**: `mini_swe_agent` and `mini_swe_agent_2` support it, while other harnesses may ignore or reject it. Confirm support in the harness request model before relying on this integration.

## Run a Harness

Start the composed environment, model, and agent servers, then collect rollouts using the top-level agent server name:

```bash
gym env start \
  --config path/to/agent-and-resources.yaml \
  --model-type vllm_model
```

```bash
gym eval run --no-serve \
  --agent my_agent \
  --input data/tasks.jsonl \
  --output results/rollouts.jsonl
```

Use `gym env validate` with the same configuration before a large run, and follow the selected harness README for required CLIs, container images, credentials, and harness-specific overrides.
