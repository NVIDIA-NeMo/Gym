# Use your agent framework or harness as a remote agent
[Drive a Remote Agent](/agent-server/remote-agent) specifies the implementation details. This is a tutorial based
on the remote agent implementation and uses [LangChain DeepAgents](https://github.com/langchain-ai/deepagents)
to walk through a full example in NeMo Gym. However, any agent framework or harnesscan follow this pattern. 

<Note>
**Remote agents are for evaluation only today.** `remote_agent` has no `model_server` reference and
never calls one — your service brings its own model, so the resulting rollouts are off-policy and
carry no token IDs to train on. If you need the policy model, write an in-tree agent server instead.
</Note>

The full example source code lives in
[`examples/langchain_deepagent`](https://github.com/NVIDIA-NeMo/Gym/tree/main/examples/langchain_deepagent). 

- [`langchain_agent/`](https://github.com/NVIDIA-NeMo/Gym/tree/main/examples/langchain_deepagent/langchain_agent)
is the agent itself. 
- Everything else in that directory is NeMo Gym wiring that uses `langchain_agent` as a local package.

## Run the agent standalone

If you're an agent builder, you're used to building your agent and sending requests to it. 
So, start there with the LangChain DeepAgent. Don't even think about NeMo Gym yet!
Remember, this can be any agent, but we are using LangChain deepagents as a tutorial. 

First, set API keys in the `.env` file. OpenRouter is used for the model powering the agent.
Tavily is used for the search tool. If you do not have API keys, get keys at
at [OpenRouter](https://openrouter.ai/) and [Tavily](https://tavily.com/). You're also welcome
to use models from other providers or locally.

If you use [LangSmith tracing](https://smith.langchain.com/), you can set those environment variables in your `.env` file as well.

```bash
cd examples/langchain_deepagent
cp .env.example .env   # fill in OPENROUTER_API_KEY and TAVILY_API_KEY
```

Then, run the agent standalone with a query that likely uses Tavily search:
```bash
cd langchain_agent
uv run run_agent.py "When is the Valkyries next game?"
```

`run_agent.py` prints the agent's final answer:

```python
result = agent.invoke({"messages": [{"role": "user", "content": sys.argv[1]}]})
```
The output, `result`, is LangChain's message format. 

## Define NeMo Gym Compatible APIs for your agent

As specified in [Drive a Remote Agent](/agent-server/remote-agent), Gym gives your agent service task messages, 
and every response you return is a single Responses API object. That means
you must convert from Gym's input task messages to LangChain's message format, and then back to the
format NeMo Gym requires.

This conversion is implemented in [`service.py`](https://github.com/NVIDIA-NeMo/Gym/blob/main/examples/langchain_deepagent/service.py):

- **`POST /v1/responses`** — the one HTTP endpoint Gym calls. Takes the request `params`, runs the
  agent, and returns a Responses API object.
- **`to_langchain(input_items)`** — converts Gym's `input` items into LangChain messages
  (`HumanMessage`/`AIMessage`/`SystemMessage` by role), skipping any non-`message` items (paired
  tool-call records).
- **`to_responses(new_messages)`** — converts the agent's new LangChain messages back into a
  Responses object, using the last `AIMessage`'s content as the final assistant `message`.
- **`_text(content)`** — small helper both conversions share, normalizing content that's either a
  plain string or a list of content blocks (from `use_responses_api=True`) into plain text.

## Start the new agent service and send a request

```bash
# Terminal 1 — the agent service with format conversion between the APIs
cd examples/langchain_deepagent
uv run uvicorn service:app --host 0.0.0.0 --port 9000
```

You can send a request directly to the agent — this is basically what Gym does each time:

```bash
curl -s http://localhost:9000/v1/responses \
    -H "Content-Type: application/json" \
    -d '{"input": [{"role": "user", "content": "What year was the Eiffel Tower completed, and who designed it?"}]}'
```

## Wire up the environment to your agent service
One config file wires the environment to your agent service. There are several example config
files in the [`configs`](https://github.com/NVIDIA-NeMo/Gym/tree/main/examples/langchain_deepagent/configs) directory
for different benchmarks, but both use the same agent service. 

Here is an example config file for the reasoning_gym benchmark. NeMo Gym, as per this config, will
coordinate the local servers:
- `reasoning_gym` is the resources server that provides the tasks for the reasoning_gym benchmark.
- `remote_agent` is the agent service for the remote agent, in this case the LangChain DeepAgent. 
  - Within `remote_agent`, the `responses_api_agents` server type is used to specify the agent service, 
  - The `remote_agent` server type is used to specify the agent service
    which is the LangChain DeepAgent at the `agent_base_url` http://localhost:9000 where we already spun up
    the agent service.

```yaml
# config.yaml
reasoning_gym:                # server_id — your name for this instance
  resources_servers:
    reasoning_gym:             # implementation — must match resources_servers/reasoning_gym/
      entrypoint: app.py
      domain: knowledge

remote_agent:                 # server_id — your name for this instance
  responses_api_agents:
    remote_agent:                # implementation — must match responses_api_agents/remote_agent/
      entrypoint: app.py
      agent_base_url: http://your-service-host:9000
      resources_server:
        type: resources_servers
        name: reasoning_gym       # references the server_id above, not the implementation
      concurrency: 32
      max_steps: 1        # this service answers in one call
```


We use the `reasoning_gym` resource server in this example, but this is configurable — swap the
`resources_server` ref to point at a different benchmark; `service.py` doesn't change. See
[`configs/config_reasoning_gym.yaml`](https://github.com/NVIDIA-NeMo/Gym/blob/main/examples/langchain_deepagent/configs/config_reasoning_gym.yaml)
for the real file, and
[`configs/config_tavily_search.yaml`](https://github.com/NVIDIA-NeMo/Gym/blob/main/examples/langchain_deepagent/configs/config_tavily_search.yaml)
for a second worked example below.

## Start the NeMo Gym environment

```bash
gym env start "+config_paths=[examples/langchain_deepagent/configs/config_reasoning_gym.yaml]"
```

## Collect rewards

```bash
gym eval run --no-serve +agent_name=remote_agent \
    +input_jsonl_fpath=resources_servers/reasoning_gym/data/example.jsonl \
    +output_jsonl_fpath=/tmp/deepagents_rollouts.jsonl
```

The output should be something like:

```bash
Collecting rollouts: 100%|███████████████████████████████████████████████████| 5/5 [00:11<00:00,  2.26s/it]
Sorting results to ensure consistent ordering
Computing aggregate metrics

Key metrics for remote_agent:
{
    "mean/reward": 1.0,
    "mean/score": 1.0
}
Finished rollout collection! View results at
```

Expect 5 rows in the output JSONL and non-zero `mean/reward`. Anything in the `_failures` sidecar
carries an `error` field naming the hop that failed. A run that completes cleanly but scores zero
across the board almost always means the answer format wasn't followed — check `extracted_answer` in
the verify output before suspecting the agent.

## What the remote agent already does

Gym's `remote_agent` server drives the loop, so your service never sees it:

- It posts the conversation so far to your service, appends whatever you return, and repeats.
- **The pairing rule is the whole protocol.** A `function_call` with no matching
  `function_call_output` in the same response means "Gym, execute this." A call and its output
  together mean "I already ran this myself — just record it." That second form is what lets a
  framework's internal tools ride into the trajectory without Gym trying to execute them.
- The rollout ends when you return an assistant `message` with no unpaired calls (also on
  `incomplete_details`, or at `max_steps`).
- Failures never crash a collection run: a down service, a timeout, or a malformed reply becomes a
  reward-0 row in the failures sidecar, retried on `+resume_from_cache=true`.
- The environment session and the task's answer key stay inside Gym. Your service never receives
  `verifier_metadata`.

## The three decisions any framework forces

**1. Whose tools run?** Gym's (return unpaired calls and get called once per tool step), the
framework's (run everything internally and return one final message), or both.

deepagents ships its own toolset — `write_todos`, `ls`/`read_file`/`write_file`/`edit_file`,
`glob`/`grep`, `execute`, and `task` for subagents — and `reasoning_gym` rows declare no tools at
all. So: the framework's tools, one call per rollout. Mixing both is supported by the protocol but
costs real design work, because the framework has to pause mid-run and resume on the next call
(in LangGraph terms, a checkpointer plus `interrupt`).

**2. How many times will you be called?** This falls out of the first answer. One call per rollout
means the service can be completely stateless. If you need state across calls, set a cookie — Gym
echoes your cookies back within a rollout.

**3. What does the verifier actually accept?** This is an *environment* question, not a framework
one, and it's the most common reason a working agent scores zero. `reasoning_gym` extracts
`<answer>...</answer>` from the final text, falls back to `\boxed{}`, and otherwise scores the whole
response — so the system prompt has to demand that format. **Read the verifier before you write the
prompt.** See "Trying a different benchmark" below for two concrete examples — one that works despite
a mismatched toolset, one that doesn't.

## The service

Install `deepagents`, `fastapi`, and `uvicorn`; the endpoint is the interesting part:

```python
from deepagents import create_deep_agent
from fastapi import FastAPI

app = FastAPI()

@app.post("/v1/responses")
async def responses(params: dict):
    # `params["tools"]` is ignored on purpose: deepagents brings its own tools and runs them
    # internally, so this service never asks Gym to execute anything.
    agent = create_deep_agent(model=MODEL, system_prompt=SYSTEM_PROMPT)
    state = await agent.ainvoke({"messages": to_langchain(params["input"])})
    return to_responses(state)   # last AI message -> one assistant `message` item
```

`create_deep_agent()` returns a compiled LangGraph graph, so `ainvoke` works directly. Everything
between the request arriving and the final message — planning, file edits, subagent spawning — is
internal to that one call.

Two translation helpers carry the weight. `to_langchain()` turns the request's `input` items into
LangChain messages; `to_responses()` turns the final state back into a Responses object with the
required fields (`id`, `created_at`, `model`, `object`, `output`, `parallel_tool_calls`, `tools`,
`tool_choice`). Emitting deepagents' internal tool calls as paired `function_call` +
`function_call_output` records is optional, and worth it — the trajectory becomes legible to
`gym eval profile` instead of collapsing to a single message.

## Trying a different benchmark: tavily_search

Let's see how to use a different benchmark via another resources server in NeMo Gym.

[`resources_servers/tavily_search`](https://github.com/NVIDIA-NeMo/Gym/tree/main/resources_servers/tavily_search)
is a web-research benchmark, judged by an LLM on whether the final answer text matches
`ground_truth` — it doesn't execute or inspect tool calls at all (`num_tool_calls` is reported as a
metric only, not part of the reward), so it doesn't matter that our agent uses its own internal
`TavilySearch` instead of this resources server's Gym-hosted `web_search`/`find_in_page`/
`scroll_page` tools. This is *not* true of every environment. Sometimes tools live in the resources
server itself rather than or in addition to the agent; see
[Tools in Agent vs. Resources Server](/agent-server/integrate-existing-agents#tools-in-agent-vs-resources-server)
for that distinction.

[`configs/config_tavily_search.yaml`](https://github.com/NVIDIA-NeMo/Gym/blob/main/examples/langchain_deepagent/configs/config_tavily_search.yaml)
wires this up: `remote_agent` pointed at `tavily_search_resources_server`, plus a `judge_model` block
(the judge needs its own model — this reuses OpenRouter and `OPENROUTER_API_KEY` for it, via
`SEARCH_JUDGE_MODEL` env var). A judge generally shouldn't be the same model it's judging, so it
defaults to `anthropic/claude-sonnet-4.5` — stronger than, and distinct from, the agent's own free
default (`nvidia/nemotron-3-ultra-550b-a55b:free`, see `.env.example`).

```bash
# Terminal 1 — the agent service (same as above)
cd examples/langchain_deepagent
uv run uvicorn service:app --host 0.0.0.0 --port 9000
```
```bash
# Terminal 2 — Gym: tavily_search + remote_agent + judge_model. Needs TAVILY_API_KEY (this
# resources server's own key, for its Gym-hosted search tools — separate from the agent's) and
# OPENROUTER_API_KEY (reused as the judge's key) in the environment.
set -a; source examples/langchain_deepagent/.env; set +a
gym env start "+config_paths=[examples/langchain_deepagent/configs/config_tavily_search.yaml]"
```
```bash
# Terminal 3 — once terminal 2 is up
gym eval run --no-serve +agent_name=remote_agent \
    +input_jsonl_fpath=resources_servers/tavily_search/data/example.jsonl \
    +output_jsonl_fpath=/tmp/deepagents_tavily_search_rollouts.jsonl
```

Verified end to end: 5 rows, no failures, `mean/reward: 0.4` (2/5 correct per judge) — these are
hard, multi-hop research questions and our agent does a single shallow search per query, so a
middling score is expected, not a broken pipeline.

**Why this benchmark works but not every one will:** `single_step_tool_use_with_argument_comparison`
(a different resources server) expects the agent to pick the correct *next* tool call from a
dynamic, per-task tool set declared in `responses_create_params.tools`, comparing the call's
arguments directly — it doesn't work with this agent as-is, because deepagents binds a fixed
toolset once at import time and never looks at `params["tools"]` (`service.py` ignores it on
purpose). Before pointing this agent at a new resources server, read its `verify()` function to see
what it actually inspects — see
[`service.py`](https://github.com/NVIDIA-NeMo/Gym/blob/main/examples/langchain_deepagent/service.py)'s
docstring and [Drive a Remote Agent](/agent-server/remote-agent).

## Gotchas

- **Returning no assistant message hangs the rollout.** If your `output` holds only paired records,
  or is empty, neither the finish check nor the tool branch fires, and Gym re-posts until
  `max_steps` or `run_timeout_secs`. Always end with a `message`.
- **Partial `usage` fails validation.** Report the full object or omit it entirely (allowed; token
  metrics are then empty). LangChain's `usage_metadata` has the numbers — sum it across the run.
- **`concurrency` defaults to 32**, so 32 framework runs can be in flight at once. Anything the
  framework writes to disk needs to be per-request or in memory.
- **One internal loop is one HTTP call**, bounded by `remote_responses_timeout_secs` (1800s) and the
  whole rollout by `run_timeout_secs` (2100s). A framework that legitimately thinks for half an hour
  needs both raised.
