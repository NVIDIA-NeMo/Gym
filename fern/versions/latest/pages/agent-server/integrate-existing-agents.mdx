You can use an existing agent in NeMo Gym, integrate an external one, or build your own from scratch.

[`SimpleAgent`](https://github.com/NVIDIA-NeMo/Gym/tree/main/responses_api_agents/simple_agent) is a native NeMo Gym agent that handles general-purpose multi-step tool calling with configurable max steps, and works with any Resources server out of the box. NeMo Gym also includes agents that integrate external tools: for example, [`MiniSWEAgent`](https://github.com/NVIDIA-NeMo/Gym/tree/main/responses_api_agents/mini_swe_agent) wraps an external coding harness running in Docker containers and converts its output back into the NeMo Gym format, and [`claude_code_agent`](https://github.com/NVIDIA-NeMo/Gym/tree/main/responses_api_agents/claude_code_agent) runs the Claude Code CLI. Because every Gym model server speaks Anthropic Messages, you can point Claude Code at any backend — see [Anthropic Messages](/model-server/anthropic-messages).

## Migrate from the standalone sandboxed Hermes agent

`hermes_sandboxed_agent` and its configuration files have been removed. Use `hermes_agent`
through an Environment Server. Include the environment and agent configuration in both
server startup and evaluation commands so collection routes through the Environment Server.
Direct HTTP callers must call the Environment Server's `/run`, not the agent's `/run`;
renaming the agent in an existing `/run` call does not enable sandbox sessions.

- Move model, toolset, and sampling settings to your agent deployment's
  `responses_api_agents.hermes_agent` configuration. Remove the old `runtime_python`,
  `remote_run_root`, `results_dir`, `sandbox_timeout`, `cleanup_timeout`, `api_timeout`,
  `context_length`, and `chat_template_kwargs` settings. Use `sandbox_runner_timeout_seconds`
  for the runner deadline; the Environment Server controls episode and cleanup deadlines.
- Keep sandbox providers in the shared configuration. For Apptainer, copy the provider
  settings into your configuration under `sandbox.apptainer`; the shared
  [provider configuration reference](https://github.com/NVIDIA-NeMo/Gym/blob/main/nemo_gym/sandbox/providers/apptainer/README.md#selecting-and-configuring-the-provider)
  describes the supported fields. The old agent-specific `configs/apptainer.yaml` is removed.
- The old `prepare_runtime.sh`, libc-selecting launcher, and `/opt/hermes` mount convention
  have been removed. The unified agent uses the Hermes revision pinned in its
  `requirements.txt`, which differs from the old standalone upstream runtime. It installs
  that revision at seed time, or reuses an already installed runtime at
  `/tmp/nemo-gym-hermes-runtime-<commit>/venv`. Network-restricted deployments must preinstall
  that runtime. The old portable glibc/musl bundles are not a drop-in replacement; validate
  each task image's architecture and libc with the unified runtime before migrating a batch.
- Remove request `max_output_tokens`: the unified agent rejects it with HTTP 422.
  Agent config `max_tokens` limits each model call, not the whole response.
  Retune budgets explicitly rather than treating the two limits as equivalent.
- Update reporting that consumes standalone `hermes_*`, `verifier_reward`, or
  `agent_image_provenance` fields to use the Environment Server rollout and observation
  records. Incomplete runs, infrastructure failures, and scoring exclusions follow the
  Environment Server's outcome policy; compare coverage as well as rewards when migrating.

The Hermes revision, execution settings, and failure reporting differ between the adapters,
so previous benchmark scores are not an accuracy baseline for the migrated configuration.
Revalidate representative tasks, including Alpine/musl images and offline deployments when
used by your configuration. For the SWE-Pro recipe and configuration mapping, see
[Evaluate SWE-bench Pro with Hermes](/main/evaluation-tutorials/hermes-swe-bench-pro).

## Agent session hooks

For Environment Server execution, implement these `SimpleResponsesAPIAgent` hooks:

- `_seed_agent_session_state(body)`: validate grants, initialize the harness, and return
  an `AgentSessionState`. If setup fails and cleanup cannot finish, raise
  `AgentSessionSetupError(state, error=original_error)` so close can retry cleanup.
- `_close_agent_session_state(state)`: stop the harness and its tools, then return an
  `AgentCloseSessionResponse` with observations. Raise if cleanup is not confirmed.

The base handles seed retries and close receipts. In `responses()`, use
`_require_agent_session()` to reject incomplete or closing sessions before execution.
A borrowed task sandbox remains owned by the Resources Server: disconnect from it after
stopping the harness; do not destroy it. Verification starts only after agent close succeeds.

When using the shared process supervisor, confirm its cleanup receipt before cancelling the
provider's exec request. Cancellation can kill the provider's entire process group, including
the supervisor when it is already the group leader (as with the local provider).
`setsid()` alone does not guarantee cleanup; the close ordering does.

## Tools in Agent vs. Resources Server

Existing agents may come with predefined tools, allowing you to leverage them directly and use the Resources server to supplement with any additional external tools. When building a new environment, prefer defining tools in the Resources server rather than the Agent server. This separation of concerns allows different agents to share the same Resources server without duplicating tool logic.
