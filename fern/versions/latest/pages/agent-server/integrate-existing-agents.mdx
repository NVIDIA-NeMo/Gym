You can use an existing agent in NeMo Gym, integrate an external one, or build your own from scratch.

[`SimpleAgent`](https://github.com/NVIDIA-NeMo/Gym/tree/main/responses_api_agents/simple_agent) is a native NeMo Gym agent that handles general-purpose multi-step tool calling with configurable max steps, and works with any Resources server out of the box. NeMo Gym also includes agents that integrate external tools: for example, [`MiniSWEAgent`](https://github.com/NVIDIA-NeMo/Gym/tree/main/responses_api_agents/mini_swe_agent) wraps an external coding harness running in Docker containers and converts its output back into the NeMo Gym format, and [`claude_code_agent`](https://github.com/NVIDIA-NeMo/Gym/tree/main/responses_api_agents/claude_code_agent) runs the Claude Code CLI. Because every Gym model server speaks Anthropic Messages, you can point Claude Code at any backend — see [Anthropic Messages](/model-server/anthropic-messages).

## Agent session hooks

For Environment Server execution, implement these `SimpleResponsesAPIAgent` hooks:

- `_seed_agent_session_state(body)`: validate grants, initialize the harness, and return
  an `AgentSessionState`. If setup fails and cleanup cannot finish, raise
  `AgentSessionSetupError(state, error=original_error)` so close can retry cleanup.
- `_close_agent_session_state(state)`: stop the harness process group, collect observations,
  and release the session. Preserved task services remain for the sandbox owner.
  Missing termination evidence remains retryable; a final negative receipt fails the activation
  and skips verification while close releases the borrowed connection.

The base handles seed retries and close receipts. In `responses()`, use
`_require_agent_session()` to reject incomplete or closing sessions before execution.
A borrowed task sandbox remains owned by the Resources Server: disconnect from it after
stopping the harness; do not destroy it. Verification requires a gradable activation and
successful agent close. Releasing a failed session does not make its activation gradable.

When using the shared process supervisor, confirm its cleanup receipt before cancelling the
provider's exec request. Cancellation can kill the provider's entire process group, including
the supervisor when it is already the group leader (as with the local provider).
`setsid()` alone does not guarantee cleanup; the close ordering does.

The shared supervisor stops live harness-group processes and reaps its children. Before
signalling a timed-out or closing harness, it records already adopted children, typically
services from completed tools. It preserves those outside the harness group and drains
newly adopted children within the cleanup deadline, including tools in separate sessions.
After natural CLI exit, unfinished tools in separate sessions cannot be distinguished
from services. Adoption races, PID reuse, and later service forks also limit this cutoff;
it is not a security boundary or a guarantee that task state cannot change.

## NOOA worker checkpoints

The [NOOA sandbox worker](https://github.com/NVIDIA-NeMo/Gym/blob/main/responses_api_agents/nooa_agent/sandbox_entrypoint.py)
publishes `checkpoint.json` as partial evidence at model-response and completed-tool boundaries.
It projects and deeply copies the evidence on the rollout event loop, then uses a single background
writer for JSON serialization, file writes, `fsync`, and atomic replacement. Projection and copying
still run synchronously and grow with transcript length, including JSON conversion within trajectory
projection. The writer never reads the live trace.

Only one snapshot is being written and one latest snapshot can be pending. New boundaries replace
the pending snapshot; writes remain ordered. Normal completion flushes the pending evidence before
publishing `result.json`. Cancellation waits for writes to finish before shutdown returns. An abrupt
kill may lose the pending or in-progress update, but leaves the previous published checkpoint valid.
Checkpoint failures are logged and do not fail an otherwise successful run.

Checkpoints carry `partial: true` and an incomplete response; they do not establish completion or
authorize grading. A valid final result takes precedence. Missing or malformed final evidence with
unsuccessful worker termination is an infrastructure failure. Callers must enforce a process deadline,
including enough shutdown grace for pending writes; the worker has no independent deadline. Artifacts
use mode `0600` and require the worker UID or privileged access for collection.

## Tools in Agent vs. Resources Server

Existing agents may come with predefined tools, allowing you to leverage them directly and use the Resources server to supplement with any additional external tools. When building a new environment, prefer defining tools in the Resources server rather than the Agent server. This separation of concerns allows different agents to share the same Resources server without duplicating tool logic.
