# New Environment

An environment defines tasks, tools, state, and verification. A harness decides how to solve each task. Gym config wires the runnable components; `manifest.yaml` describes the workload and mirrors that composition for catalog and validation.

For a first resources server, follow [Single Step Environment](/environment-tutorials/single-step-environment). For a benchmark, also follow [Add a benchmark](/contribute/environments/adding-a-benchmark).

## Add a manifest-backed workload

Search for an existing workload, scaffold, and validate it:

```bash
gym search "task description"
gym env init --environment my_eval --profile custom-gym-verifier
gym env validate my_eval
gym env test my_eval
gym env publish my_eval
```

Use `--benchmark` for benchmark scaffolding. Reuse an existing verifier fixture with `--reuse-verifier NAME` when applicable. Scaffolding stops if it would overwrite files.

Every workload needs a `manifest.yaml`, a runnable Gym config, datasets, and a resources server that owns task state and verification. A benchmark also needs a preparation script and prompt contract. Start from the [reference manifest](https://github.com/NVIDIA-NeMo/Gym/blob/main/environments/example_single_tool_call/manifest.yaml); Gym's schema rejects unknown fields.

The manifest owns metadata such as workload identity, license, reward range, and determinism. Gym config remains authoritative for component wiring. Update the manifest's mirrored composition when the config changes. Named configs use a relative `config_path`; set `dataset_owner` only when multiple config instances own datasets. `prompt_source` distinguishes template, prepared, and agent-owned prompts.

Keep benchmark-specific task setup, tools, state, and verifier behavior with the resources server. Keep reusable harness behavior with the agent server. Do not add a benchmark wrapper just to host episode execution: the runtime composability RFC proposes an Environment Server for protocol ordering, timeouts, results, and cleanup. That proposal is not yet the runtime contract.

## Validate and contribute

Before opening a pull request:

- Run `gym env validate NAME` and `gym env test NAME`.
- For behavior changes, run a representative model rollout and inspect both the agent trace and verifier result.
- For an existing benchmark, compare Gym's result with the benchmark's published baseline where reproducible.
- Include the dataset source and license, selected split/config, validation performed, and any limits in the pull request.

See [Contributing](/contribute) for repository checks. Metadata-only manifest changes do not require model compute.
