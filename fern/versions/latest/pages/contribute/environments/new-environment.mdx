<Info>
**Goal:** Add a new **scorer** (resources server) when no existing one can grade the task.

A resources server is the program under `resources_servers/` that implements `verify()` — the function that returns a numeric score. An **overlay** (a named benchmark) comes later, in step 6.

**Time:** Budget a working session for scoring code, tests, and five example tasks.

**In this guide you will:**

1. Create `resources_servers/<name>/`
2. Implement `verify()` (and any tools or session state)
3. Add unit tests
4. Produce five example tasks, metrics, and rollouts
5. Open a pull request that matches CI
6. Add a named benchmark overlay that points at this scorer

If `math_with_judge`, `mcqa`, or a similar scorer already fits, stop and follow [Add a benchmark](/contribute/environments/adding-a-benchmark).
</Info>

<NavButton href="/contribute/environments/onboarding-decision-tree" label="Onboarding decision tree" direction="back" />

**Before you start**

1. [Development setup](/contribute/development-setup) and a gitignored `env.yaml` from the [Quickstart](/get-started/quickstart).
2. For a full hands-on `verify()` and tool example, work through [Single-Step Environment](/environment-tutorials/single-step-environment) first.
3. Run every command from the repository root.

## 1. Scaffold

Search first, then generate the folder:

```bash
gym search resources-servers "task description"
gym env init --resources-server my_server
```

```text
resources_servers/my_server/
+-- __init__.py
+-- app.py                 # scoring code (starter tests use VerifierFixture — see step 2)
+-- configs/my_server.yaml # block names: my_server_resources_server, my_server_simple_agent
+-- data/
|   +-- .gitignore
+-- tests/
|   +-- __init__.py
|   +-- test_app.py
|   +-- verifier_cases.jsonl
+-- requirements.txt
+-- README.md
```

In YAML, the scorer block is `{name}_resources_server` and the agent block is `{name}_simple_agent`. Pass the agent block as `--agent`.

<Warning>
For pull requests to this repository, run `gym env init --resources-server` only. `--environment`, `--reuse-verifier`, and `--benchmark` create an experimental layout — see the accordion at the bottom of this page.
</Warning>

**Next:** implement `verify()` in `app.py`.

---

## 2. Implement `verify()`

`gym env init --resources-server` generates starter tests around a **VerifierFixture**: `verify()` lives on a `{Name}Verifier` class, `VERIFIER_FIXTURE` is exported, and `tests/test_app.py` runs those cases from `tests/verifier_cases.jsonl`.

<Warning>
The [Single-Step Environment](/environment-tutorials/single-step-environment) tutorial puts `verify()` on `SimpleResourcesServer` and uses hand-written pytest. Most shipped scorers use that pattern (see [`example_single_tool_call`](https://github.com/NVIDIA-NeMo/Gym/tree/main/resources_servers/example_single_tool_call)). Pick one:

1. **Keep the generated tests** — update `verifier_cases.jsonl` and leave `VERIFIER_FIXTURE` in place.
2. **Switch to the tutorial pattern** — rewrite `tests/test_app.py` so it no longer imports `VERIFIER_FIXTURE`.

Do not mix the two without updating tests.
</Warning>

Edit `resources_servers/my_server/app.py`. Scoring (and any tools or session state) lives there:

```python
async def verify(self, body: BaseVerifyRequest) -> BaseVerifyResponse:
    # Read the trajectory from body.response. Return a numeric reward.
    return BaseVerifyResponse(**body.model_dump(), reward=1.0)
```

If the model output is missing or malformed, return `reward=0.0`. Do not crash the server. Add tools as extra FastAPI handlers on the same class. For per-task memory (`seed_session`, cookies), see [Stateful Environment](/environment-tutorials/stateful-environment). If `simple_agent` is the wrong loop, see [Complex benchmarks](/contribute/environments/adding-a-benchmark#complex-benchmarks).

Worked SimpleResourcesServer example: [Single-Step Environment](/environment-tutorials/single-step-environment). Scoring pattern catalog: [Build Verifiers](/build-verifiers).

In `resources_servers/my_server/configs/my_server.yaml`, set `domain` to one of: `math`, `coding`, `agent`, `knowledge`, `instruction_following`, `long_context`, `safety`, `games`, `translation`, `e2e`, `rlhf`, or `other`. See [Resources Server Fields](/reference/configuration#resources-server-fields).

Fill in `README.md` with licensing. The `add-verified-flag` git hook sets `verified: false` — leave it.

**Next:** add tests, then five example tasks.

---

## 3. Tests

You need at least one test in `tests/test_app.py`. The scaffold already adds `test_verifier_fixture` plus `verifier_cases.jsonl` — replace or extend those when you change how scoring works. Cover a passing score, a failing score, and empty model output.

```bash
gym env test --resources-server my_server
```

That command runs pytest only. Add `+should_validate_data=true` after you create the five example files in the next step. Pull-request CI always sets that flag.

**Next:** write `data/example.jsonl` (five lines).

---

## 4. Example data and rollouts

Create `resources_servers/my_server/data/example.jsonl` with **exactly 5** lines **before** you generate metrics. These rows include chat messages (`responses_create_params.input`). Overlay JSONL that uses a prompt file does not — see [Add a benchmark](/contribute/environments/adding-a-benchmark#3-wire-config-prepare-and-data).

```json
{"responses_create_params": {"input": [{"role": "user", "content": "what's it like in sf?"}]}}
```

Add whatever fields `verify()` reads (`expected_answer`, `verifier_metadata`, tools). Examples: [`example_single_tool_call/data/example.jsonl`](https://github.com/NVIDIA-NeMo/Gym/blob/main/resources_servers/example_single_tool_call/data/example.jsonl) and [Single-Step §2](/environment-tutorials/single-step-environment#2-task-preparation).

CI then requires all three files under `resources_servers/my_server/data/`:

| Artifact | Rule |
| --- | --- |
| `example.jsonl` | Exactly **5** rows (often the first five of your train split) |
| `example_metrics.json` | `"Number of examples": 5` |
| `example_rollouts.jsonl` | Exactly **5** rollouts (full run records, including `reward`) |

Generate metrics:

```bash
gym dataset collate \
  "+config_paths=[resources_servers/my_server/configs/my_server.yaml]" \
  +output_dirpath=data/my_server \
  +mode=example_validation
```

<Note>
**Before rollouts:** [Development Setup](/contribute/development-setup) (`uv sync --extra dev`) and root `env.yaml` (`policy_base_url`, `policy_api_key`, `policy_model_name`) from the [Quickstart](/get-started/quickstart). Never commit `env.yaml`. Start servers in one terminal, collect in another. `--agent` is `my_server_simple_agent`.
</Note>

```bash
gym env start --resources-server my_server --model-type openai_model
gym eval run --no-serve \
  --agent my_server_simple_agent \
  --input resources_servers/my_server/data/example.jsonl \
  --output resources_servers/my_server/data/example_rollouts.jsonl \
  --limit null
```

Then:

```bash
gym env test --resources-server my_server +should_validate_data=true
```

Worked example: [`resources_servers/example_multi_step`](https://github.com/NVIDIA-NeMo/Gym/tree/main/resources_servers/example_multi_step). `gym env test` (all servers) only discovers directories that contain `README.md`. Do not leave `*conflict*` files under `data/`.

<Note>
Train and validation dataset entries need a YAML `license` field. The scaffold already sets `license: Apache 2.0` — change it when you publish real splits. Hugging Face `source:` is the public default. GitLab is NVIDIA-internal only. See [Prepare Data](/data).
</Note>

**Next:** open a pull request, then name the eval in step 6.

---

## 5. Open a PR

- [ ] `tests/test_app.py` and `gym env test --resources-server my_server +should_validate_data=true`
- [ ] Five-row `example.jsonl`, `example_metrics.json`, `example_rollouts.jsonl`
- [ ] `domain` on the server YAML; `license` on train/validation datasets
- [ ] `verified: false` (leave the hook default)
- [ ] SPDX header on every new file
- [ ] `git commit -s` (Developer Certificate of Origin; cryptographic `-S` signing is optional)
- [ ] `pre-commit run --files resources_servers/my_server/**/*` (stage auto-fixes from ruff / `add-verified-flag` / `update-readme-table`)
- [ ] README with licensing
- [ ] PR description: what the environment measures, how `verify()` works, data source and domain

Score checks and a training run are optional for merge. They help before `verified: true`. See [Add a benchmark](/contribute/environments/adding-a-benchmark#6-reward-profiling).

**Next:** add a named benchmark overlay so people can run `gym eval run --benchmark …`.

---

## 6. Name the eval

A resources server is the scorer, not the named benchmark. After the server exists, add `benchmarks/<name>/` that points `config_paths` at `resources_servers/my_server/configs/my_server.yaml`. A training mix can live under `environments/<name>/` the same way.

Follow [Add a benchmark](/contribute/environments/adding-a-benchmark) from step 2, and set `config_paths` to **your** server instead of `math_with_judge`.

<Accordion title="Experimental manifest contract">
This layout is experimental and not required for catalog PRs. Environments and benchmarks in this repository do not ship `manifest.yaml`. The commands below are implemented but incomplete.

```bash
gym env init --environment my_eval --profile custom-gym-verifier
gym env validate my_eval
gym env test my_eval
gym env publish my_eval
```

`--reuse-verifier` requires the reused server to export `VERIFIER_FIXTURE`. Production scorers do not. Reuse them with `config_paths` and `_inherit_from` instead.

The fixture contract (full-reward, zero-reward, malformed, plus reseed when `seeded`) is the local bar on that path. Publication records readiness as `experimental`. CODEOWNERS, immutable versions, and a hosted catalog index are not automated yet.

Integration profiles (`custom-gym-verifier`, `custom-gym-agent-loop`, `external-agent-loop`, `external-rollout-driver`) classify where the episode is driven. They are authored labels, not a runtime dispatcher. See `nemo_gym/environment/manifest.py` and [CLI: gym env init](/reference/cli-commands#gym-env-init).
</Accordion>

<Accordion title="Recommended technical design">
Handlers should be async. Use the NeMo Gym OpenAI client from the top-level `nemo_gym` package, not LiteLLM. Extend `BaseVerifyRequest` / `BaseVerifyResponse` for extra fields. Return tool errors to the model instead of crashing. Pass configuration through Gym YAML, not environment variables.

On multi-step rollouts, propagate `prompt_token_ids`, `generation_token_ids`, and `generation_log_probs` on later model calls. Details: [Single-Step Environment](/environment-tutorials/single-step-environment) and [`AGENTS.md`](https://github.com/NVIDIA-NeMo/Gym/blob/main/AGENTS.md).
</Accordion>
</AccordionGroup>
