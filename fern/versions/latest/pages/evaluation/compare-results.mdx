# Compare Results

Use `gym eval compare` to compare a baseline evaluation with one candidate. The report shows metric deltas, confidence intervals, and which tasks changed from passing to failing or the reverse. Use it to evaluate a model, quantization method, prompt, or harness change. Use `gym eval compare-suite` to combine benchmarks within each model and across a model–benchmark matrix.

| Goal | Command | Confidence level |
| --- | --- | --- |
| Inspect one benchmark's metrics and task changes | `gym eval compare --baseline ... --candidates ...` | 95% by default; adjustable |
| Aggregate selected benchmarks and models | `gym eval compare-suite --suite suite.yaml` | 90% by default; adjustable |

## Prepare Comparable Runs

Keep the benchmark, dataset split, task order, task limit, and verifier settings the same. Vary the model or configuration you want to evaluate, and save each run in a separate directory. The task order matters because the sample-flips table matches tasks by their recorded task index.

Collect repeats to measure variation in the score. For example, after [starting the MCQA servers](/main/get-started/quickstart#run-evaluation), collect a baseline:

```bash
gym eval run --no-serve \
    --agent mcqa_simple_agent \
    --input resources_servers/mcqa/data/example.jsonl \
    --output results/baseline/rollouts.jsonl \
    --num-repeats 8
```

After applying the change you want to evaluate, collect the same tasks into `results/candidate/rollouts.jsonl` with the same collection settings. If you change the model or server configuration, restart the servers with that configuration first.

Each run writes `rollouts_aggregate_metrics.json` beside its rollout file. Comparison reads these aggregate files, so it needs no running servers or new model calls. If collection used `--disable-aggregation`, run [`gym eval aggregate`](/main/reference/cli-commands#gym-eval-aggregate) first.

<Note>
Eight repeats is an example, not a prescribed sample size. A repeat evaluates the task set once. Both runs need at least two usable per-repeat values for a metric to receive a repeat-based delta confidence interval; a single-repeat run can still have its point estimates compared.
</Note>

## Run the Comparison

```bash
gym eval compare \
    --baseline results/baseline/rollouts.jsonl \
    --candidates results/candidate/rollouts.jsonl \
    --agent mcqa_simple_agent \
    --output-dir results/comparison \
    --report-format both
```

Despite the plural option name, `--candidates` currently accepts one candidate run. Omit `--agent` to compare every agent name shared by the two runs. When the names differ, select each side with `--baseline-agent` and `--candidate-agents` instead.

Delta confidence intervals default to 95%. To request 90%, add `--confidence-level 0.90`. Supply a fraction strictly between `0` and `1`. This option changes the delta intervals; each run's separate confidence intervals remain the recorded 95% intervals.

The command prints key metrics and writes:

| File | Contents |
|---|---|
| `compare_report.md` | Key metrics, other metrics, and task-level sample flips. |
| `compare_report.json` | Metric values, delta interval endpoints, and task-level results for further analysis. |

The JSON report records the selected delta confidence level in the top-level `confidence_level` field, for example `0.90`.

Without `--output-dir`, reports are written beside the candidate's rollout file. Repeating the command in the same output directory replaces the report files. See the [CLI Reference](/main/reference/cli-commands#gym-eval-compare) for aggregate-file overrides and all options.

## Read the Report

**Delta is candidate minus baseline.** A positive delta means the candidate's metric is numerically higher. Whether that is better depends on the metric: higher reward is usually better, while lower latency is usually better. Metrics retain their original units; this command does not normalize or combine them into a single score.

For each metric, the rendered report and delta use each run's mean across repeats when available, otherwise its recorded point estimate. JSON exposes `value` and, when available, `mean_across_repeats`; use the latter to reproduce the delta when present. The two fields can differ for uneven task coverage or nonlinear metrics.

The **CI for the delta** is a two-sided Welch t confidence interval computed from the per-repeat metric values at the selected confidence level (95% by default). Each repeat is one observation. The method treats baseline and candidate repeat sets as independent; it does not pair repeats by index.

A delta CI requires `mean_across_repeats/<metric>` on both sides after loading and at least two finite, same-named metric values in each side's `repeat_level_metrics`. For legacy aggregate entries without the `repeat_level_metrics` key, comparison first reconstructs generic repeat statistics in memory from stored per-rollout summaries. An explicitly present list is not recomputed. If the required statistics remain unavailable, the delta CI is unavailable (`—` in Markdown and `null` endpoints in JSON). A custom metric computed only for the whole run may have a point estimate without a delta CI. See [Repeat-Level Metrics](/main/evaluation/aggregate-metrics#repeat-level-metrics) for how these values are produced.

The sample-flips table helps locate changed tasks. For binary rewards, a task passes when its mean reward over repeats is greater than `0.5`; exactly `0.5` is a tie. A flip describes the observed outcomes and does not by itself establish a model regression or improvement.

<Warning>
Check that both runs completed the intended tasks before interpreting the intervals. Comparison warns about incomplete or unequal task coverage across repeats but can still display a CI. Missing tasks can mix a change in task difficulty with a change in model quality. The command does not verify that the two runs used the same dataset or verifier configuration. Use [Rollout Health Checks](/main/evaluation/rollout-health) and the collection completion summary to inspect the evidence.
</Warning>

## Interpretation of the Confidence Interval

The example below uses the default 95% confidence level.

### Start with the Difference

When evaluating a change such as quantization, an observed score difference may reflect both the change and variation between repeated evaluations. Consider a GPQA example in which both models answer the same 198 questions in each of eight repeats. A correct answer earns `1`, and an incorrect answer earns `0`.

| Metric | Baseline | Candidate | Candidate − baseline | 95% CI for the difference |
|---|---:|---:|---:|---:|
| `mean/reward` | 0.7645 | 0.7689 | +0.0044 | [-0.0140, +0.0228] |
| As a percentage | 76.45% | 76.89% | +0.442 percentage points | [-1.400, +2.284] percentage points |

The baseline answered 1,211 of 1,584 responses correctly; the candidate answered 1,218 correctly. Seven additional correct responses produce the observed gain of 0.442 percentage points (pp). The interval, calculated from the spread of the eight repeat scores per model, spans a 1.400 pp loss to a 2.284 pp gain. The higher observed score alone does not establish an improvement.

### Could the Candidate Be Too Much Worse? (Noninferiority)

Choose the largest acceptable loss **before** examining the result. For a metric where higher is better, the interval's lower end must exceed the negative of that margin to rule out an unacceptable loss at this confidence level.

| Largest acceptable drop | Required lower bound | Example lower bound | Interpretation |
|---|---:|---:|---|
| 2 pp (`0.02` in reward units) | Above -2 pp | -1.400 pp | Rules out a loss of 2 pp or more. |
| 1 pp (`0.01`) | Above -1 pp | -1.400 pp | Inconclusive: a loss of 1 pp or more is not ruled out. |
| 0 pp (`0`) | Above 0 pp | -1.400 pp | Does not establish that the candidate is at least as good. |

An inconclusive result does not demonstrate that the candidate exceeds the allowed loss. It means the evaluation cannot rule that loss out. The acceptable margin is an evaluation criterion you justify; the command does not choose it or issue a pass/fail verdict.

### Could We Say the Candidate Is Better? (Superiority)

For a metric where higher is better, the whole delta interval must be above zero to support an improvement. For example, `[+0.2, +1.8] pp` would support that conclusion. The GPQA interval includes both negative and positive differences, so it establishes neither an improvement nor a decline. Including zero also does not establish equivalence.

Use the interval for the **difference** to answer this question. Overlap between the baseline's and candidate's separate confidence intervals is not the corresponding comparison test. For a metric where lower is better, reverse the direction: an interval entirely below zero supports improvement.

### What Does 95% Mean?

Imagine repeating the entire eight-versus-eight evaluation many times under the same conditions. Under the method's assumptions, about 95 out of 100 intervals constructed this way would contain the fixed, unknown true difference. About 2.5 would lie entirely below it and 2.5 entirely above it.

This is a statement about the method over repeated evaluations. It does not assign a 95% probability to the true difference lying inside this particular interval.

### Connection to Statistical Testing

Using the lower end of the two-sided 95% CI in this example for either decision above corresponds to a **one-sided test at the 2.5% significance level**. If the true difference were exactly the -2 pp acceptable-loss cutoff, about 2.5% of repeated evaluations would incorrectly place the lower bound above -2 pp. At a true difference of zero, about 2.5% would incorrectly place it above zero and support improvement. These rates change when you select a different confidence level.

These are long-run false-positive rates at the specified cutoff, not the probability that this particular candidate fails a criterion. They rely on the Welch method's assumptions: repeat scores are independent within each run, and the baseline and candidate repeat sets are independent of each other. The t approximation must also be appropriate for the repeat-score distributions, especially with few repeats; approximately normal repeat scores support that approximation. The interval describes variation from rerunning the evaluated task set; it does not account for sampling a new set of questions. If those assumptions fail, the actual error rates can differ.

## Compare a benchmark suite

`gym eval compare-suite` calculates one score difference per model–benchmark pair, one aggregate per model, and one overall aggregate. Configure exactly one baseline and one candidate run for each included pair. Sources are not pooled.

Save a manifest such as `suite.yaml`:

```yaml
schema_version: 1
benchmarks:
  birdbench:
    metrics:
      - name: mean/reward
  mmlu-redux:
    metrics:
      - name: mean/strict_boxed_reward
        low: 0
        high: 1
        higher_is_better: true
      - name: mean/normalized_reward
        low: 0
        high: 1
        higher_is_better: true
models:
  model-a:
    birdbench:
      baseline:
        rollouts: runs/model-a/birdbench/baseline/rollouts.jsonl
      candidate:
        rollouts: runs/model-a/birdbench/candidate/rollouts.jsonl
    mmlu-redux:
      baseline:
        rollouts: runs/model-a/mmlu-redux/baseline/rollouts.jsonl
      candidate:
        rollouts: runs/model-a/mmlu-redux/candidate/rollouts.jsonl
  model-b:
    birdbench:
      baseline:
        rollouts: runs/model-b/birdbench/baseline/rollouts.jsonl
      candidate:
        rollouts: runs/model-b/birdbench/candidate/rollouts.jsonl
    mmlu-redux:
      baseline:
        rollouts: runs/model-b/mmlu-redux/baseline/rollouts.jsonl
      candidate:
        rollouts: runs/model-b/mmlu-redux/candidate/rollouts.jsonl
```

Paths are relative to the YAML file. Model names are report labels; each model's candidate is compared with that model's baseline. Include only the model–benchmark pairs you intend to measure; a complete rectangular matrix is not required.

This example uses MCQA's existing dual scoring for MMLU-Redux. Collect both sides with the resources-server override `mmlu-redux_mcqa_resources_server.resources_servers.mcqa.grading_mode=boxed_and_normalized` to record both selected reward metrics. Selecting a metric in the suite YAML does not compute a missing metric.

```bash
gym eval compare-suite \
    --suite suite.yaml \
    --output-dir results/suite

# Recalculate the interval at a different confidence level using the same data.
gym eval compare-suite \
    --suite suite.yaml \
    --confidence-level 0.95 \
    --output-dir results/suite-95
```

`--confidence-level` accepts a fraction strictly between zero and one; the default is `0.90`. The separate `gym eval compare` command defaults to 95% difference intervals. For `compare-suite`, sources and aggregate-entry selection come from the YAML. See the [CLI reference](/main/reference/cli-commands#gym-eval-compare-suite) for all command options.

### Source options

Each `baseline` or `candidate` mapping supports:

| Field | Meaning |
| --- | --- |
| `rollouts` | Required run identity. Its aggregate-metrics sibling is read. |
| `aggregate_metrics` | Optional explicit path when the aggregate file has a different name or location. |
| `agent` | Optional selector matching an aggregate entry's `agent_ref.name`. This is usually the agent name; entries for several environment servers sharing an agent can use server names as labels. |
| `environment_server` | Optional selector matching an aggregate entry's `_ng_environment_server`. Use the server's configuration instance name. Older aggregate files can lack this field. |
| `materialized_inputs` | Optional path to the collection inputs used to verify planned task/repeat coverage. The usual sibling is discovered automatically when present. |

Selection happens independently for every baseline and candidate source. If neither selector is set, the aggregate must contain exactly one entry. If a selector is set, exactly one entry must match; when both are set, that entry must match both. Missing or ambiguous matches are errors that list the available choices.

For example, baseline and candidate may use different environment servers and agents for the same benchmark:

```yaml
baseline:
  rollouts: runs/birdbench/baseline/rollouts.jsonl
  agent: bird_sql_agent
  environment_server: birdbench_simple_env
candidate:
  rollouts: runs/birdbench/candidate/rollouts.jsonl
  agent: bird_hermes_agent
  environment_server: birdbench_hermes_env
```

Gym retains both identities from the selected entry. To verify planned coverage, rows stamped with `_ng_environment_server` are matched to that server; unstamped rows use `agent_ref.name` when available. This supports inputs containing both taskset-routed and agent-routed rows without counting another server's planned tasks. Server and agent names need not match between baseline and candidate; their task coverage and selected metrics must still be comparable.

Referencing the same run and selected aggregate entry more than once is rejected because this method assumes independent source observations.

## Normalize metrics and preserve benchmark weights

Every selected metric needs theoretical lower and upper bounds and a score direction. For `mean/reward`, Gym reads `reward.range` and `higher_is_better` from the named benchmark's manifest. Other metrics need explicit `low`, `high`, and `higher_is_better` values. A complete explicit definition overrides manifest metadata.

Metric bounds and directions are defined once per benchmark and shared across all models. The report's metric normalization table lists each benchmark's metric definitions once.

Bounds must be finite, with `high > low`. They describe the metric's possible values, not the smallest and largest values observed in these runs. Values outside the declared bounds are errors.

For every metric value in a repeat, Gym calculates:

```text
normalized = 100 * (raw - low) / (high - low)
```

For a lower-is-better metric, it then uses `100 - normalized`, so positive candidate-minus-baseline deltas consistently favor the candidate. For example, accuracy `0.8` with bounds `[0,1]` becomes `80`; an error rate `0.2` with the same bounds and `higher_is_better: false` also becomes `80`.

Aggregation proceeds in this order:

1. Average a benchmark's normalized metrics equally **within each repeat**.
2. Calculate each side's mean and sample variance (divisor `n - 1`) from these composite repeat scores.
3. Weight eligible benchmarks equally within each model.
4. Weight eligible model–benchmark pairs equally in the overall result.

MMLU-Redux therefore has the same benchmark weight as BirdBench in the example, despite having two selected metrics. Averaging metrics before estimating variance preserves their covariance within a repeat. The number of metrics and number of tasks do not become additional independent repeat observations.

For a sparse matrix, a model with more included benchmarks contributes more cells to the overall result. The overall calculation uses equal cell weights rather than equal model weights.

## Understand the confidence interval

Suite comparison uses an **unpaired Welch interval for a fixed-suite mean delta**. Each cell's estimated delta is:

```text
delta = candidate_mean - baseline_mean
```

Its estimated variance is the sum of each side's sample variance divided by that side's repeat count. The aggregate adds these variances using squared cell weights and uses Welch–Satterthwaite effective degrees of freedom for its Student-t interval.

The numerical method, including normalization and metric averaging, is isolated in `nemo_gym/eval/comparison/statistics/unpaired_welch_fixed_suite.py`. The [NIST two-sample t-test reference](https://www.itl.nist.gov/div898/handbook/eda/section3/eda353.htm) and [coverage-factor guidance](https://www.nist.gov/pml/nist-technical-note-1297/nist-tn-1297-appendix-b-coverage-factors) describe the independent-sample and effective-degrees-of-freedom calculations.

<Note>
The interval quantifies repeat uncertainty for the fixed selected benchmarks, models, and task sets. It assumes independent repeats within each side, independent baseline/candidate collections, and independent cell estimates. It does not include uncertainty from sampling different benchmarks or models. Shared conditions or genuinely paired samples can require covariance terms beyond this method.
</Note>

A positive delta favors the candidate. An interval containing zero does not demonstrate a change at the selected confidence level; it also does not prove equivalence or an acceptable regression margin. Inspect individual benchmark results alongside the aggregate, because positive and negative deltas can cancel.

Confidence intervals are not clipped to the score bounds. A constant-score cell retains its weight; when total empirical variance is zero, suite comparison reports the point estimate and zero SE with an unavailable interval and degrees of freedom.

## Check exclusions and coverage

`gym eval compare-suite` requires stored `repeat_level_metrics`. If the field is missing, regenerate aggregation; this command does not reconstruct repeat statistics from embedded rollout summaries.

A repeat with no scored tasks can still contain token-usage accounting. When such a token-only row lacks a selected quality metric, suite comparison preserves the accounting in the source aggregate and omits the repeat from quality estimates, without assigning a zero score. The report lists the unscored repeat indices, warns about incomplete coverage, and suppresses affected confidence intervals. If a token-usage metric itself is selected, its available repeat observations remain usable.

Each side needs at least two repeats with estimates for the selected metrics. If either side has fewer, Gym excludes the entire model–benchmark pair with a warning. Remaining eligible cells receive recomputed equal weights. The requested suite, exclusions, and effective weights are recorded; no eligible cells is an error.

Every selected metric must be present in every included repeat. Gym does not silently remove missing metric values or change metric weights between repeats.

Recorded task sets must agree across repeats and sides. When materialized inputs are available, Gym also verifies planned coverage. Without those inputs, planned coverage remains unverified; recorded coverage checks cannot prove that a task absent from every completed result was collected. Known incomplete or inconsistent coverage suppresses affected confidence intervals while retaining descriptive results.

## Optionally check rollout health

Health checking is **off by default**. Add `--check-health` to include trajectory-integrity warnings in the suite report:

```bash
gym eval compare-suite \
    --suite suite.yaml \
    --check-health \
    --health-check-workers 8 \
    --health-check-output-dir results/health-checks \
    --output-dir results/suite-with-health
```

Gym checks each rollout JSONL referenced by the suite, together with its own failure and materialized-input siblings. The check covers **all agents in each file**, even when the comparison selects one agent. It scans the saved records afresh rather than reading an existing `quality_summary.json`. `--health-check-workers` must be a positive integer; by default Gym uses up to eight available CPUs.

Gym validates the full comparison and checks that the configured health output directory is writable before starting any health scans.

Suite health checks set both final and retryable failure thresholds to **zero**: any recorded failure that has no later saved result makes the run unhealthy and appears in the warning. Zero failures pass. Evaluating these thresholds requires the rollout file's materialized-input sibling to establish the expected rollout count; without that inventory, failure-fraction checks are unobserved, but known failures still appear in warnings. These suite-specific thresholds replace any saved failure limits.

During checking, the terminal shows each file when its scan starts, phase changes, record-progress updates approximately every 30 seconds, and final health counts and elapsed time. These progress messages are enabled by default; no `--verbose` flag is needed.

The report's **Warnings** section and terminal output show one summary line per affected source. A source with detected findings is **unhealthy**; missing evidence is **unobserved**, which does not establish that the trajectories are unhealthy. If a source cannot be checked, for example because its rollout file is missing or unreadable, the warning reports health as unavailable. The comparison JSON retains health counts and issue summaries.

`healthy`, `unhealthy`, and `unobserved` count saved records; `failed` counts rollouts without a saved result (`null` when unavailable). Therefore, `failed.total > 0` can coexist with `unhealthy = 0`.

Health findings are advisory: they do not change comparison scores, weights, or confidence intervals. Without `--check-health`, comparison continues to read aggregate metrics without opening the rollout JSONL. The separate `gym eval compare` command is unchanged.

`--health-check-output-dir` retains full reports in a separate subdirectory for each rollout file: `health-check-<source-path-hash>/quality_summary.json` and `rollout_verdicts.jsonl`. The comparison's Markdown and JSON reports include these retained paths. If you omit the option, detailed health reports use temporary files that are deleted after checking; the comparison still retains health counts and issue summaries. Setting an output directory alone does not enable checking: include `--check-health` too. See [Rollout Health Checks](/main/evaluation/rollout-health) for check definitions and detailed report schemas.

## Read the reports

`gym eval compare-suite` writes these files to `--output-dir`, defaulting to the YAML file's directory:

| File | Contents |
| --- | --- |
| `suite_compare_report.md` | Candidate and baseline scores, per-model and overall deltas (`candidate - baseline`), intervals for delta, effective membership, metric scales, source runs, and coverage notes. |
| `suite_compare_report.json` | Raw/scaled repeat metrics, composite scores, repeat counts, means, `delta` (`candidate - baseline`), variances, SE, effective degrees of freedom, variance contributions, and provenance. |

The suite JSON report has its own versioned format with `"schema_version": "1"`. Its filename identifies the report type; it has no `level` field.

Use `--report-format md`, `json`, or `both` (default). After quantifying the differences, use [Diagnose Results](/main/evaluation/diagnose-results) to investigate task-level causes and possible improvements.
