An agent harness turns a model into an agent: it manages conversation state, routes tool calls, and
decides when a task is complete. Two harnesses can produce materially different scores on the same model and tasks, and a harness that performs well with one model may underperform with another. Treat the harness as an experimental variable to isolate and evaluate, not a fixed part of the environment

`--agent-type` runs an environment or benchmark with a harness other than the one its config names,
without editing any config. To ablate the harness, hold everything else fixed — model, dataset, and repeat count — and vary only `--agent-type`, writing each run to its own output:

```bash
gym list agents
gym eval run \
    --benchmark terminal_bench_2_1/opencode \
    --agent-type terminus_2_sandboxed_agent \
    --model-type vllm_model
```

Each run writes its own `_aggregate_metrics.json` next to its rollouts file. Comparing those across harnesses *is* the ablation — for example (illustrative, not real output):

| Harness | Pass rate |
|---|---|
| `opencode_sandboxed_agent` | 41% |
| `terminus_2_sandboxed_agent` | 68% |

A spread this size, with the model and dataset held identical, means the harness — not the model — is the lever to pull. Refer to [Diagnose Results](/evaluation/diagnose-results) to have an agent explain *why* the harnesses diverged, or [Aggregate Metrics](/evaluation/aggregate-metrics) to build your own comparison across shards. For the flag reference itself, see
[Swapping the agent](/reference/cli-commands#swapping-the-agent).

## Offline scientific evaluation with OpenCode or Pi

The shared `harness_agent` runs each task in a sandbox and sends its response to
the benchmark's existing verifier. Compose one benchmark and one native harness
preset in a config file:

```yaml
config_paths:
  - benchmarks/apex_shortlist/harness.yaml
  - responses_api_agents/harness_agent/configs/opencode.yaml
use_absolute_ip: true
```

For HLE, use `benchmarks/hle/harness.yaml`. To run Pi, replace the OpenCode preset
with `responses_api_agents/harness_agent/configs/pi.yaml`; select one preset.
The `apex_shortlist/opencode`, `hle/opencode`, and `hle/opencode_search` benchmark
entrypoints provide composed OpenCode configurations. Search uses Gym's Tavily
MCP service and the [search exclusion policy](/main/infrastructure/tavily-search).

Set `HARNESS_SANDBOX_IMAGE` to a compatible image digest and configure OpenSandbox
access. The [runtime Dockerfiles and build instructions](https://github.com/NVIDIA-NeMo/Gym/tree/main/responses_api_agents/harness_agent/image)
include scientific Python, SageMath, Lean/Mathlib, and the native harness binaries.
Each sandbox includes `/opt/science/README.md` with tool usage instructions.

The sandbox must be able to reach the advertised Gym model and tool addresses.
`use_absolute_ip: true` uses the Gym host's resolved IP; otherwise configure
routable server `host` values. Model and tool URLs both rewrite local addresses
to the host address, but this cannot create a network route or open a firewall.
Use `sandbox_model_base_url` when a separate model proxy is required.

The Python-only preset allows the model host; search also allows the configured
tool hosts. Other direct internet access is denied by the OpenSandbox policy.
Model and Tavily credentials stay in the host-side Gym services.

### Preset behavior and compatibility

- Both presets disable automatic compaction and omit the per-request output cap
  so the inference server can use the remaining context. Configure the server's
  context window and default generation limits accordingly.
- Enclosing rollout budgets are four hours. OpenCode uses 400 steps and disables
  background titles. Pi caps Bash calls at 120 seconds; shorter requested limits
  are preserved. This cap is opt-in outside the benchmark preset.
- The OpenCode benchmark preset sets `interleaved_reasoning: false` to avoid a separate
  assistant `reasoning` request field that Gym's benchmark chat schema rejects.
  The standalone adapter retains its existing `interleaved: {field: reasoning}`
  default. Explicit native model overrides now take precedence; previously the
  adapter overwrote a supplied `interleaved` value.
- OpenCode configurations combining legacy `tools` with `permission` are rejected:
  move tool allow/deny rules to `permission` so legacy settings cannot override a deny.
- Benchmark answer-format instructions are retained; HLE's instructions are placed
  in the user message. Harness prompts add brief network and installed-tool guidance.
- With `execution_failure_reward_zero`, an explicitly failed or incomplete harness
  invocation gets reward zero without grading. A completed empty answer still goes
  to the verifier. Include failed and missing rows when reporting benchmark coverage.
  This option requires invocation observations and is supported only for Hermes,
  OpenClaw, OpenCode, and Pi; other adapters reject it at startup. It does not convert
  setup, runner, export, or verifier exceptions into scored results.

With `tool_servers` configured, call `/run` to initialize authenticated MCP sessions.
Direct `/v1/responses` calls return HTTP 400 before creating a sandbox; they cannot
initialize those sessions. Direct calls without `tool_servers` remain supported.

Buffered chat streams send keepalive comments after 15 seconds of silence. Fast
backend failures retain normal HTTP error handling. After headers have been sent,
an HTTP status cannot change: late backend failures end with an SSE error, while
serialization or capture-finalization failures abort the stream. Clients must treat
either as failure, not a successful empty completion.
Keepalives currently apply to chat-completions streams; Responses-API streams still
wait silently for the backend response.

## The composed instance is renamed

Composition replaces the environment's agent and renames the server instance after the harness that
runs it, so metrics and `gym env status` report what actually ran. Composing
`terminus_2_sandboxed_agent` onto `terminal_bench_2_1_opencode_sandboxed_agent` produces
`terminal_bench_2_1_terminus_2_sandboxed_agent`.

That name is what you use to route rollouts when the servers are already up:

```bash
gym env start \
    --benchmark terminal_bench_2_1/opencode \
    --agent-type terminus_2_sandboxed_agent \
    --model-type vllm_model
gym eval run --no-serve --agent terminal_bench_2_1_terminus_2_sandboxed_agent --input rows.jsonl
```

End-to-end rollouts collection (without the `--no-serve` flag) keeps working — rows stamped with the
pre-swap instance are re-routed for you under the hood.

## Not every pairing is valid

A verifier is written against the behavior of a particular harness. A resources server can declare
which harnesses are compatible with it in
[`allowed_agents`](/reference/configuration#resources-server-fields), and Gym refuses an undeclared
pairing before any server starts:

```text
'simple_agent' is not declared compatible with 1 of the agent instance(s) it would replace,
so it cannot be scored correctly:
  - terminal_bench_2_1_opencode_sandboxed_agent uses terminal_bench_2_1_opencode_resources_server
    and accepts opencode_sandboxed_agent, terminus_2_sandboxed_agent

Select one of: opencode_sandboxed_agent, terminus_2_sandboxed_agent. Or pass
--allow-unsupported-pairing (or set NEMO_GYM_ALLOW_UNSUPPORTED_PAIRING=1) to bypass the check.
```

<Warning>
`--allow-unsupported-pairing` bypasses this check at your own risk: an unsupported harness can score incorrectly without erroring.
</Warning>

A server that declares nothing accepts any harness — such environments are swappable without further
setup.

## Self-contained environments

Some agent servers own their environment and declare no resources server. Those are left alone by a swap,
because there would be nothing for the incoming harness to bind to. If every agent in a config
is self-contained, selecting a harness fails with `no other agent instance to rehost it on`.
