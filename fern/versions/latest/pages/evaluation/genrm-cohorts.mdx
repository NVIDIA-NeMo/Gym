# GenRM Comparison Groups

The `genrm_compare` resources server scores multiple answers to one prompt using a generative reward model.
Each rollout calls `/verify` separately. The server collects the configured number of members, compares
their answers, and returns an individual reward to each rollout. A comparison group is also called a cohort.

## Collecting with Gym

Set these fields under `genrm_compare_resources_server.resources_servers.genrm_compare`:

```yaml
num_rollouts_per_prompt: 4
cohort_timeout_s: 1800
cohort_result_ttl_s: 21600
max_terminal_cohorts: 4096
```

For `gym eval run`, use a number of repeats divisible by the group size and concurrency at least as large
as one group. Gym gives each task/agent's consecutive sets of four answers separate group identities.
Fan-out targets stay in separate groups. The collector reserves concurrency for complete groups so that
members of different groups cannot occupy every slot while waiting for each other.

The materialized inputs record the group ID, group attempt and member slot before generation starts.
`_ng_rollout_index` remains the global per-task rollout index used for output and profiling; the separate
`_ng_group_member_index` identifies the answer's position within its comparison group.

Gym's file collector explicitly requests tagged failure rows. A missing member or failed judge call sends
the arrived answers to the failures sidecar with `_ng_failure_class="judge_failed"` and a failure kind.
These rows retain the generated answers and are excluded from ordinary score aggregation. The wire row
contains a placeholder reward of zero for compatibility with the existing failure envelope; it is not
a scored answer. This routing does not require `route_failures_to_sidecar=true`, which covers generic
agent request errors separately.

## Completion deadline

`cohort_timeout_s` must be finite and positive. Its default is 1800 seconds. The deadline starts when the
first valid member arrives and covers both collecting answers and judging them. Duplicates and subsequent
arrivals do not extend it. Increase it for workloads with long tool executions or slow judging.

The server releases every waiter on incomplete membership, a judge call failure, a judging deadline, or
shutdown. It never caches a successful score for a failed judge HTTP/transport call. A successful judge
reply that cannot be parsed retains the existing configured parse-retry/default-score policy.

Cancelling one request detaches that waiter without cancelling scoring needed by other members. Its
accepted answer remains available until completion or expiry. A disconnect does not authorize a newly
sampled answer to replace it: resend the exact saved answer, or coordinate a replacement for the whole group.

Pairwise judging starts after the complete group arrives. Members are ordered by their logical slots, so
HTTP arrival order does not determine comparison pairs or reward assignment. This changes generation/judge
overlap compared with incremental comparison dispatch; comparative performance has not been established.
Shared judging runs outside any individual member's rollout capture and trace context.

## External caller contract

External callers, including NeMo-RL, own their group dispatch and retry policy. Send these fields through
the agent to `/verify`:

| Field | Meaning |
| --- | --- |
| `_ng_group_id` | Unique identity for one logical comparison group, distinct across runs and prompt occurrences. |
| `_ng_group_attempt` | Nonnegative integer shared by every member of one group attempt. |
| `_ng_group_member_index` | Optional member slot from zero through `num_rollouts_per_prompt - 1`. |
| `_ng_rollout_index` | Rollout identity; used as the member slot when `_ng_group_member_index` is omitted, as in NeMo-RL's current caller. |

All members must have the same prompt and principle. An exact response-payload duplicate attaches another
waiter or returns its cached reward. A different response for an occupied slot is rejected with HTTP 409.
Successful responses echo the group coordinates. Framework group counters are excluded from score metrics.

A caller replacing a group must increment `_ng_group_attempt` for every member. A newer attempt retires
older active attempts, releases their waiters, and rejects late older requests. A late judge completion
cannot publish into the replacement. Repeating a failed attempt returns failure; it does not silently
create another group. An individual rollout's retry counter never advances a group attempt.

The default external failure protocol is HTTP 503 with no reward. This preserves RL's infrastructure-retry
signal. Only consumers that exclude tagged failure rows from scoring may opt into
`_ng_cohort_failure_mode="row"`, which uses the JudgeError sidecar envelope described above. Gym's file
collector sets this field; the low-level `run_examples` API does not change an external caller's protocol.

Legacy callers can provide `_ng_task_index` or a nonempty `prompt_id`, plus a member slot, without an explicit
group ID. They must keep those identities unique and coordinate attempts themselves. Prompt-only requests
without member identity are rejected because arrival counting cannot distinguish retries from new answers.
An omitted group attempt defaults to zero and emits one bounded migration log when a group ID was supplied.

## Resume and reverification

Gym can resume a completely pending group from its materialized inputs. It preserves that group's ID,
advances its shared attempt, persists the updated inputs, and regenerates every member. This also advances
the group attempt when a previous process died without writing a failure row. Other completed groups remain
unchanged. Existing per-rollout retry limits still apply.

Partial-group resume is unsupported. For example, if a process stops after writing only two of a completed
four-member group's rewards, Gym rejects the remaining partial group before generation. Rerun the complete
group into a fresh output file. Old caches without group identities also require a fresh output file.
The current implementation does not reconstruct a group from saved successful and failed answers.

`gym eval reverify` rejects configured GenRM cohorts, including `force=true` and `judge_failed_only=true`.
Individual reverification cannot reconstruct complete membership or coordinate a fresh group attempt, and
an unchanged request might return a cached reward without running the judge. Durable answer reuse and
coordinated group reverification require a separate implementation.

## Retention

Run this resources server with one HTTP worker. Its registry and duplicate-result cache are local to that
process, not shared across workers or persisted to disk.

Completed and failed groups retain compact response digests and outcomes, limited by `max_terminal_cohorts`
and `cohort_result_ttl_s`. Both limits must be positive and the TTL finite. Entries expire in completion order;
normal requests within the limits inspect only the oldest terminal entry. Shutdown clears the registry.

Cached replay and stale-request detection are available only while their state is retained. The count cap
can evict a group before its TTL at high throughput. Callers must enforce accepted attempt identity across
eviction and server restart; this cache is not a durable replay guarantee.
