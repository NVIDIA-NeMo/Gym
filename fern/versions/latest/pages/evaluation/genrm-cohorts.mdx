# GenRM Comparison Groups

The `genrm_compare` resources server compares several answers to one prompt using a generative reward
model. Each rollout calls `/verify` separately. A comparison group, also called a cohort, contains exactly
`num_rollouts_per_prompt` members. Rewards are published only after all members and comparisons finish.

## Caller contract

The caller must dispatch every member of a group concurrently enough to reach verification. It must also
own the group identity and decide whether to replace a failed group. The server does not schedule rollouts,
regenerate answers, persist results, or resume a collector.

Send these fields through the agent to `/verify`:

| Field | Meaning |
| --- | --- |
| `_ng_group_id` | Unique identity for one logical comparison group, distinct across runs and prompt occurrences. |
| `_ng_group_attempt` | Nonnegative integer shared by every member of one attempt. |
| `_ng_group_member_index` | Member slot from zero through `num_rollouts_per_prompt - 1`. |
| `_ng_rollout_index` | Existing rollout index; used as the member slot when `_ng_group_member_index` is omitted. |

All members must have the same prompt and principle. The optional separate member index lets a caller
use global rollout indices without changing the group's local slots. Responses echo these coordinates;
framework counters are excluded from reward metrics.

For four answers A, B, C, and D, a caller sends four concurrent `/run` requests with one group ID, attempt
zero, and slots 0, 1, 2, and 3. Comparisons start as their two answers arrive. The server retains the existing
circular or all-pairs schedule, then waits for every comparison before assigning rewards by member slot.
Shared judge calls run outside any individual member's rollout capture context.

An exact response duplicate can attach another waiter while the group is active. A different response for
an occupied slot receives HTTP 409. A completed attempt also rejects late requests with HTTP 409; there is
no cached reward replay. This avoids treating a newly requested verification as a fresh judge result.

## Deadlines and failures

Configure these fields under `genrm_compare_resources_server.resources_servers.genrm_compare`:

```yaml
num_rollouts_per_prompt: 4
cohort_timeout_s: 1800
cohort_result_ttl_s: 21600
max_terminal_cohorts: 4096
```

The finite, positive deadline starts with the first valid member and covers collection and judging.
Later arrivals and duplicates do not extend it. Allow enough time for both generation skew and judge latency.
The supplied server YAML uses 16 members; this example explicitly changes it to four.

The initial policy is to fail the whole group. If D never arrives, A, B, and C receive HTTP 503 without a
reward when the deadline expires. Judge HTTP errors, transport errors, empty or incomplete judge responses,
and a judging timeout also fail the group. A nonempty completed judge answer that cannot be parsed retains
the existing configured parse-retry/default-score policy.

If a member loses its last waiting request, the active group fails and releases its siblings. This matters
because retrying `/run` may generate a different answer. Disconnecting one duplicate leaves an attached
original valid. Failure and shutdown cancel owned comparisons and discard answers and waiters. Each
terminal transition logs one bounded disposition event without prompt or answer content.

The simple agent preserves verification HTTP statuses: 503 for a failed group, 409 for a conflict or retired
attempt, and 422 for invalid coordinates. These errors contain no ordinary reward. Existing collector
failure handling applies; this server does not add a saved-answer failure envelope or a judge-only recovery
channel.

## Replacement attempts and retention

To replace a group, the caller increments `_ng_group_attempt` for every member and dispatches the complete
group again. A newer attempt retires older active attempts and releases their waiters. A late completion
from an older judge task cannot publish into the replacement. Repeating a failed attempt returns failure
while its disposition is retained. An individual rollout retry counter never advances a group attempt.

Run this resources server with one HTTP worker. Its registry is local to that process. Completed and failed
groups retain only compact dispositions and prompt/attempt coordinates, bounded by `max_terminal_cohorts`
and `cohort_result_ttl_s`. Answers, rewards, and waiter futures are discarded at completion or failure.

The count cap can evict a disposition before its TTL. After eviction or server restart, the server cannot
recognize a replay from retained state. Callers must enforce accepted attempt identity across those
boundaries and use fresh group IDs for unrelated work. This is bounded server cleanup, not durable recovery.

## Using the file collector

The file collector's scheduling and resume behavior are unchanged. It does not create local group slots,
reserve concurrency for entire groups, or advance shared group attempts. In particular, arbitrary fan-out,
multiple groups of repeats, or mixed-group scheduling require a caller that supplies the grouping and
admits complete groups. Concurrency below the group size cannot fill even one group.

A small check can use one task, one agent, and exactly four repeats with the four-member configuration above.
Give that task a fresh `_ng_group_id` and `_ng_group_attempt: 0`. The collector's rollout indices 0–3 then
serve as the local slots:

```bash
gym eval run --no-serve --agent genrm_simple_agent \
    --input one-task.jsonl --output fresh-results.jsonl \
    --num-repeats 4 --concurrency 4
```

Start the configured policy, judge, and Gym servers first. Use a fresh group ID and output path for another
independent check. This example does not provide group resume: the caller must coordinate a complete new
attempt after failure, including when only some completed rewards reached disk.

Legacy requests can use `_ng_task_index` or `prompt_id` plus member slots instead of `_ng_group_id`. Keep
these identities unique across work sharing the server and coordinate attempts explicitly. An omitted
group attempt defaults to zero, with one migration log for explicit group IDs. Anonymous prompt-only
requests are rejected because arrival counting cannot distinguish retransmission from a new member.

GenRM declares individual `gym eval reverify` unsupported. Forcing it does not reconstruct group membership
or coordinate attempts, and a retained completed attempt returns 409. Durable answer reuse, group resume,
and group reverification belong in follow-up work with the collector or training framework's retry policy.
