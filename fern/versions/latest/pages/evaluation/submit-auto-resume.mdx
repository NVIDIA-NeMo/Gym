---
title: "Auto-Resume Submitted Jobs"
description: "Let gym eval submit requeue a Slurm benchmark job that hits its time limit or fails, and continue from the rollouts already written."
position: 8
---

A benchmark in `gym eval submit` can resume on its own when its Slurm job stops early. Set `resumable` on the benchmark:

```yaml
driver:
  benchmarks:
    gpqa:
      resumable: true            # defaults: max_retries 3, no walltime cap
    aime25:
      resumable:
        max_retries: 5           # resubmits after a non-timeout failure
        max_walltime: "48:00:00" # cap on the chain's total runtime, Slurm duration syntax
```

Only the Slurm executor supports it. A config that sets `resumable` for another executor fails at submit time.

## How it works

Each job queues its own successor with `sbatch --dependency=afternotok:<its job id> --kill-on-invalid-dep=yes` before
doing any work. The successor starts only if the job did not complete. When the job completes, Slurm drops the successor.

When a successor starts, it reads the previous job's state with `sacct` and decides:

| Previous state | Action |
| --- | --- |
| `COMPLETED` | Stop. |
| `CANCELLED` | Stop. Cancelling a job ends the chain. |
| `TIMEOUT`, `PREEMPTED`, `NODE_FAIL` | Resume. Does not count against `max_retries`. Stops once `max_walltime` is reached. |
| Any other failure | Resume and count one retry. Stops with exit code 1 after `max_retries` retries. |
| Unknown (`sacct` returned nothing after about a minute) | Resume. Does not count against `max_retries`. |

The resumed job runs `gym eval run` with `resume_from_cache=true`, so rollouts already in the output file are kept and only
the missing ones run. A final line cut short by the kill is dropped and that rollout runs again.

## Limits

- A benchmark that sets `command` cannot set `resumable`. The resume flag only reaches `gym eval run`, so a custom command
  would start over from zero on every resubmission.
- A benchmark that uses its own `rollout_collection_driver` receives `resume_from_cache` in its config and must honour it.
  A driver that ignores it restarts from zero on every resubmission.

## Files in the job directory

Every job of a chain runs in the same job directory. Tools that read a run use these names:

| Path | Contents |
| --- | --- |
| `logs/driver-<SLURM_JOB_ID>.log` | Driver output of one job. |
| `logs/<service>-<SLURM_JOB_ID>.log` | Output of one service in one job, for example `logs/policy-1234.log`. |
| `logs/otel_collector-<SLURM_JOB_ID>.log` | Collector output of one job, when the collector is on. |
| `.gym_job_chain` | Slurm job ids of the chain, one per line, in start order. Resumable benchmarks only. |
| `.gym_accumulated_walltime` | Seconds of walltime used by the earlier jobs of the chain (the running job is not included). |
| `.gym_infra_retries` | Retries spent on non-timeout failures so far. |

The log names carry the Slurm job id for every submitted job, resumable or not. The job id recorded in `gym-job.json` is
the first job of the chain. Read `.gym_job_chain` for the later ones.
