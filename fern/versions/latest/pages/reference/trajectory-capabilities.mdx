# Trajectory capability matrix

This matrix reports trajectory evidence supported by the implemented agent paths. It is a static source audit of
[Gym commit `609c3d150`](https://github.com/NVIDIA-NeMo/Gym/tree/609c3d150f869d45e5402eebbf7ac71b1f4ffb42),
not a claim that every path has been validated with live rollouts. Coverage depends on configuration and the evidence
actually saved for a rollout.

`ng_trajectory` schema version `1.0` combines available model-call capture and agent observations in a rollout record.
Model-call capture records qualifying calls routed through the Gym Model Server, while agent observations provide
harness-side turns and tool activity. The trajectory joins the available evidence from both sources. Direct-provider
calls bypass Gym Model Server capture, so the trajectory cannot obtain Gym-captured model-call evidence for those calls
even when agent observations are available.

The trajectory can contain task and rollout identity, model calls and token usage, semantic turns, invocation-scoped
model-visible histories, tool attempts, resolution, step count, and explicit evidence gaps. Source attachments remain
under `ng_model_call_capture` and `ng_agent_observations`.

## Key caveats

- Coverage is path-dependent. A producer may use both captured Gym Model Server calls and uncaptured direct-provider
  calls.
- Model-call evidence requires `observability_enabled: true`, `model_call_capture_dir: /data/model-calls`, and calls
  through a `/ng-rollout/<rollout_id>` Gym Model Server prefix. See
  [Model-call capture](/model-server/model-call-capture).
- `O` and `X` describe current producer output, not fields that the `ng_trajectory` schema is unable to represent.
- Token fields are nullable, and provider-reported details are preserved only when available. LabBench rows with the
  `multimodal_history_redacted` gap omit captured request and response payload copies from `ng_trajectory`.
- Aggregate-metrics requests omit `ng_trajectory`, `ng_model_call_capture`, and `ng_agent_observations` attachments.

See [Model-call capture](/model-server/model-call-capture) for payload retention and access-control requirements. Token
fields are `prompt_tokens`, `completion_tokens`, `reasoning_tokens`, `total_tokens`, and `cached_tokens`.

## Acceptance criteria

| ID | Criterion |
|---|---|
| C1 | Model-call identity, status, error, and termination metadata |
| C2 | Prompt, completion, reasoning, total, and cached token counts when available |
| C3 | Canonical `TrajectoryTurn` records preserve answer, reasoning, and tool-call activity |
| C4 | Model-visible input and output history can be reconstructed from persisted rollout JSONL |
| C5 | Tool output, status, start and completion timestamps, and duration |
| C6 | Independent timing for parallel tool calls |
| C7 | Resource-server-backed and custom or sandbox-backed benchmarks |
| C8 | Turn identity, timestamp, question, resolution, and step metadata |
| C9 | Captured model requests and responses retain their payloads |
| C10 | Model calls have exact ownership references on an `AgentInvocation` |
| C11 | Model calls have exact ownership references on a `TrajectoryTurn` |

Each criterion describes one evidence dimension. C1 describes the model-call envelope, C2 its token values, and C9 its saved
payloads. C3 describes agent activity within canonical turns, while C8 describes turn metadata and outcome. C10 and C11
separate invocation ownership from turn ownership. The `V`, `O`, and `X` values below express whether each dimension is
complete, partial or path-dependent, or unavailable; completeness is not a separate criterion.

## Agent coverage

- `V`: complete for the documented path under the documented observability configuration.
- `O`: currently partial or path-dependent.
- `X`: currently unavailable.

In practice, rely on `V` for the documented path when observability is configured as documented, inspect configuration
and trajectory gaps before relying on `O`, and do not expect the producer to supply `X` on the evaluated path. These
symbols are not absolute agent capabilities: alternate execution paths can produce different evidence. For C1, C2,
C4, and C9 through C11, `V` evaluates the correlated Gym Model Server path; direct-provider alternatives are outside
capture.

### Coverage notes

- The inventory starts with the 46 built-in harnesses admitted by the
  [agent registry](https://github.com/NVIDIA-NeMo/Gym/blob/609c3d150f869d45e5402eebbf7ac71b1f4ffb42/nemo_gym/agent_registry.py#L134)
  and also checks configured entrypoints, including the four nested `conversational_tool_use` harnesses.
  A harness is listed when at least one of C1, C2, C3, C9, C10, or C11 is `V` or `O`.
  The two legacy SWE frameworks have separate rows. Custom harnesses from additional search roots require their own audit.
- The original [`mini_swe_agent`](https://github.com/NVIDIA-NeMo/Gym/blob/609c3d150f869d45e5402eebbf7ac71b1f4ffb42/responses_api_agents/mini_swe_agent/app.py#L127)
  is excluded: it uses an unprefixed model URL, emits no canonical observations, and returns placeholder zero usage.
  `mini_swe_agent_2` has a separate, correlated Model Server path.
- C2 `O` can mean usage survives only on the rollout response, without per-call capture or an `ng_trajectory`
  attachment. Finance, Harbor, Harbor General, Image Tools, LangGraph, Remote, SciCode, and VCQA retain such usage;
  ToolSandbox retains only the last model response's usage. Missing details, defaulted zeros, or incomplete totals
  must not be treated as measured per-call counts. Harbor General also retains only the first Harbor task step's
  converted conversation. The [LegalAgentBench bridge](https://github.com/NVIDIA-NeMo/Gym/blob/609c3d150f869d45e5402eebbf7ac71b1f4ffb42/resources_servers/legal_agent_bench/harbor_bridge.py#L19)
  inherits the `harbor_agent` evidence path.
- LangGraph includes its orchestrator, parallel-thinking, ReWOO, and reflection implementations. The
  [reflection config](https://github.com/NVIDIA-NeMo/Gym/blob/609c3d150f869d45e5402eebbf7ac71b1f4ffb42/responses_api_agents/langgraph_agent/configs/reflection_agent.yaml#L3)
  names `reflection_agent`, for which no matching harness directory exists in this snapshot. That config's execution
  path remains an open issue; the row describes the available implementations.
- Simple, Simple with Compaction, and LabBench emit canonical turns and exact response references. C8 is partial
  because verifier responses may omit resolution status; C5 is partial because raised execution failures can prevent
  a tool observation from being returned. Simple with Compaction records the actual compacted input in each turn's
  `question`. LabBench image stripping makes C4 and C9 partial.
- AnySWE and AnyTerminal pass a correlated Model Server URL into their sandbox harnesses, but return the nested
  harness's response without forwarding its canonical observations. NeMo Fabric, Prime, Simple Strands, and
  `terminus_2_agent` also supply model-call capture without canonical turns or ownership. A caller-provided model URL
  or an alternative provider must preserve capture routing explicitly; it does not inherit coverage from these rows.
- CVDP capture covers its Simple path; generic sandbox paths use different routing. OSWorld M3 and Pointer can call
  providers directly. Stirrup capture covers the policy client; calls outside that client are not guaranteed captured.
- OpenClaw and PinchBench use the same session-observation adapter and retain partial model-visible history.
  PinchBench can capture both policy and judge calls, but its invocation references identify OpenClaw policy calls;
  judge calls have no corresponding invocation. C10 describes policy-call ownership for this path.
- Verifiers routes the client it hands to the environment through the rollout capture prefix. Calls using that client
  can supply C1, C2, C4, and C9, but the agent emits no canonical turns or invocation ownership. An environment's
  independently created client requires its own capture routing.
- OpenCode includes the standalone, sandboxed, and ViBench paths. The sandboxed and ViBench paths retain OpenCode
  observations and compose them with verifier-sandbox evidence. Invocation ownership uses the captured session header
  matched to a saved invocation by the
  [collector](https://github.com/NVIDIA-NeMo/Gym/blob/609c3d150f869d45e5402eebbf7ac71b1f4ffb42/nemo_gym/rollout_observability.py#L305);
  OpenCode's configured version 1.17.11
  [sends that header for Gym's provider](https://github.com/anomalyco/opencode/blob/v1.17.11/packages/opencode/src/session/llm/request.ts).
  Other installed versions must preserve it. Response-ID adapters instead require an exact Model Server and response-ID match.
- Legacy OpenHands retains one cumulative root conversation, so C4 remains partial. Its
  [capture overlay](https://github.com/NVIDIA-NeMo/Gym/blob/609c3d150f869d45e5402eebbf7ac71b1f4ffb42/responses_api_agents/swe_agents/app.py#L3760)
  is installed only when training-token capture is enabled for the agent. With that overlay and evaluation
  observability enabled, its Model Server requests preserve the rollout prefix and supply C1, C2, and C9.
  Evaluation observability alone does not install the overlay.
- C7 requires standardized agent-side trajectory evidence; model HTTP capture alone does not satisfy it.
- C10 is invocation ownership and C11 is turn ownership. Exact references describe the calls they identify; they do
  not establish that every call was assigned to a turn or included in rollout usage. Missing references and explicit
  scope gaps still matter when deriving [rollout health checks](/evaluation/rollout-health).
- C9 is independent from C4: saved request and response payloads can coexist with incomplete conversation evidence.
  Raw-capture-only rows remain in this matrix even when ownership-dependent health checks cannot run.

### Terminus2 decisions and invocation ownership

With model-call capture enabled as described above, `terminus_2_sandboxed_agent` emits an `AgentInvocation` for each
identified rollout execution. Its execution-specific `x-session-id` header lets the collector link captured model
calls to that invocation, including retries without a response ID and summarization calls.

The adapter records `TrajectoryTurn` entries at Harbor's main-agent decision boundary, before terminal commands
execute. Each observed decision retains the exact input sent for its selected response, the answer and reasoning,
and an exact model-server/response-ID reference. Its timestamp is the observed response time. `turn_no` counts main
decision attempts; `step_count` counts completed nonempty terminal-command batch attempts before that decision. A
returned batch timeout counts as an attempt, not proof that every command ran. One decision can request several
commands. `resolved` remains unset because a model's completion claim does not establish task success.

Decisions remain available after parser errors, tool failures, or cancellation. Responses rejected by the adapter and
synthetic Harbor fallback messages are not presented as accepted main-agent decisions. Their available model-call
evidence remains invocation-owned, with diagnostic gaps. Known summarization boundaries also emit
`ContextCompactionObservation` records with exact response references; auxiliary fallback calls are not mislabeled as
main decisions. Missing or reused response IDs produce gaps instead of guessed associations. `turns_unavailable` is
reported only when no actual decision response could be represented.

Observed turns enable `rollout_missing_agent_turns` and `agent_turn_hollow`. Invocation ownership enables
`model_call_failed`, `model_call_missing_token_counts`, `model_call_zero_completion_tokens`,
`model_call_runaway_generation`, and `trajectory_capture_mismatch` under their documented capture and payload
requirements. See [Rollout health checks](/evaluation/rollout-health).

The underlying HTTP transport can retry after server admission without notifying the adapter. The adapter always
emits `transport_retry_visibility_unavailable` and `turn_model_call_scope_incomplete`. These gaps keep complete
turn-call accounting, rollout token reconciliation, and full policy-call coverage unobserved while
preserving those seven checks. This producer does not establish an overall healthy rollout or task success from calls.
