# Harness: Trajectory Evidence

Trajectory Evidence (TE) describes the execution facts available from a particular harness integration. Each claim
identifies evidence that a validator can inspect in a saved rollout. The location of the evidence does not change
its meaning: a tool observation can establish tool timing without a canonical turn record.

This page defines a proposed vocabulary for harness onboarding and artifact validation. It does not certify individual
harnesses or introduce a validator command.

## Scope and assumptions

The unit being assessed is a harness integration under a declared configuration, model API, and modality. Gym's shared
capture, collection, serialization, aggregation, and verification implementations are assumed to work correctly. The
harness must expose the execution facts those shared components need. Reward calculation and generic aggregation are
outside this harness evidence taxonomy.

For this first validation scope, model calls are assumed to route through Gym's Model Server adapters. There is no
independent observer: inspecting saved evidence cannot prove that no call bypassed capture or that no event was omitted
entirely. A direct-provider path does not inherit Gym's capture guarantees.

A validator reads the final rollout artifact, such as `evaluator_rollouts.jsonl` in an evaluator run. Gym's output filename
is configurable and commonly `rollouts.jsonl`. It checks evidence availability, structure, and internal relationships.
Claims about request fidelity or complete attempt membership are assessed against the retained evidence under the routing
assumption, not against an independent execution trace.

## Gym integration prerequisites

A harness can satisfy a TE claim using evidence produced by Gym's shared components. It does not need to record a second
copy itself. The integration must supply the routing, identifiers, and observations those components require:

| Prerequisite | Integration requirement |
|---|---|
| Capture configuration and routing | Enable `observability_enabled`, configure `model_call_capture_dir`, and route the relevant model clients through the `/ng-rollout/<rollout_id>` Model Server prefix. Include subagent, retry, and compaction clients within the claimed scope. |
| Correlation | Preserve rollout identity through downstream execution. For claimed invocation or turn ownership, retain the exact identifiers used by the integration's correlation mechanism, such as session IDs or model-server/response-ID references. Do not infer ownership from message order alone. |
| Evidence forwarding | If a nested harness, subprocess, or adapter produces observations or trajectory records, forward that evidence through the integration to rollout collection. Returning only the final answer does not preserve those records. |

See [Model-call capture](/model-server/model-call-capture) for capture configuration and routing. These are integration
prerequisites, not additional TE categories. They do not require re-testing Gym's shared capture or serialization code.
Recorded identifiers and relationships can be checked in artifacts; the absence of calls that bypass capture cannot be
established from those artifacts alone.

Validate the saved individual rollout records. Gym omits `ng_trajectory`, `ng_agent_observations`, and
`ng_model_call_capture` from requests to `/aggregate_metrics`; the resulting metrics summary is not an evidence artifact.
This does not remove the attachments from saved rollout records. Supplying only a metrics summary to a TE validator is
an unsuitable validation input, not evidence that the harness lacks instrumentation.

## Evidence records and locations

These are distinct concepts:

- An **agent invocation** is one agent execution or conversation. A rollout may include root and child invocations.
- An **agent turn** is one harness-level model-driven decision. A turn can involve multiple model attempts and request
  multiple tool executions. It is not necessarily one message, one model call, or one tool execution.
- A **model-call attempt** is an individual exchange at the declared capture boundary. Its owner, selected decision,
  retry relationship, and auxiliary purpose are separate facts.

`TrajectoryRecord`, stored as `ng_trajectory`, is an evidence container. Its `invocations`, `model_calls`, `tool_calls`,
and `turns` collections are independent; `turns` may be empty. `TrajectoryTurn` is a decision record inside that container.
Having turns does not establish complete turn-to-call attribution.

Current rollout records can retain three attachments:

| Attachment | Evidence available there |
|---|---|
| `ng_trajectory` | Normalized model calls and usage, invocations, producer-supplied turns, enriched tool records, and gaps |
| `ng_agent_observations` | Harness observations, including invocations, tools, compaction, sandbox observations, source information, and gaps |
| `ng_model_call_capture` | Captured model exchanges and metadata; some fields overlap the trajectory projection |

These attachments overlap but are not interchangeable. Compaction and sandbox records currently remain in observations;
raw capture also retains metadata not represented in the trajectory. Successful trajectory projection removes duplicate
request/response payloads from the capture attachment. Their absence there is not evidence loss when the authoritative
payload is retained in `ng_trajectory`.

The validator reads each kind of evidence from its supported locations in the rollout record. Duplicate copies count
once; conflicting copies are reported. Evidence satisfies only the claims it explicitly supports—for example, a saved
conversation alone does not establish agent turn boundaries.

## Evidence taxonomy

TE1, TE2, and so on are families. Each decimal entry is a separately testable claim; a family does not pass merely because
one of its fields is present. Scenario examples below describe behaviors to exercise, then inspect in saved artifacts.
They do not imply an independent observer or an already implemented test suite.

| Family | Evidence claims | Example artifact-validation scenario |
|---|---|---|
| **TE1 — Model-call attempts** | **TE1.1** Attempt identities; **TE1.2** Outcomes and termination reasons; **TE1.3** Call timing; **TE1.4** Retry relationships | Exercise successful, failed, and retried calls; inspect distinct recorded attempts, outcomes, and explicit retry references. |
| **TE2 — Model-visible content** | **TE2.1** Actual requests/context; **TE2.2** Returned responses; **TE2.3** Returned reasoning; **TE2.4** Images/audio/other media and their references | Inspect requests and responses across multiple turns and supported modalities, including context changes. Preserve native roles and content. |
| **TE3 — Per-call token usage** | **TE3.1** Prompt tokens; **TE3.2** Completion tokens; **TE3.3** Reasoning tokens; **TE3.4** Cached tokens; **TE3.5** Total tokens | Inspect each claimed count on the relevant calls. Missing values stay distinct from zero; each metric is assessed separately. |
| **TE4 — Agent turns** | **TE4.1** Turn identity, ordering, and timestamp; **TE4.2** Turn content: answer, reasoning, and requested actions; **TE4.3** Selected model-response reference; **TE4.4** Associated model attempts | Exercise multiple decisions and recovery; inspect turn records and distinguish the selected response from other attempts associated with the turn. |
| **TE5 — Tool executions** | **TE5.1** Execution identity and tool name; **TE5.2** Dispatched arguments; **TE5.3** Results/errors; **TE5.4** Execution outcome; **TE5.5** Individual execution timing; **TE5.6** Originating request/turn reference | Exercise successful and failed tools, with overlapping execution where supported. Inspect execution records and their references; a model request alone is not proof of execution. |
| **TE6 — Invocations and subagents** | **TE6.1** Invocation identity and outcome; **TE6.2** Parent/child relationships; **TE6.3** Delegated input and returned result; **TE6.4** Invocation-to-model-call ownership | Exercise child agents and inspect their relationships, delegated work, results, and explicit ownership of recorded model calls. |
| **TE7 — Context compaction** | **TE7.1** Compaction occurrence and outcome; **TE7.2** Before/after context references; **TE7.3** Summary or transformation evidence; **TE7.4** Compaction model-call references | Trigger completed and interrupted compaction; inspect the event, subsequent recorded context, and any explicitly identified helper calls. |
| **TE8 — Execution resources** | **TE8.1** Resource identity and association with agent/tool activity; **TE8.2** Resource lifecycle/outcome; **TE8.3** Measured CPU usage; **TE8.4** Measured memory usage; **TE8.5** Measured GPU usage | Inspect resources associated with harness activity and the scope of available measurements. Sandbox-wide usage must not be presented as per-tool usage. |

Each claim must state its eligible population. For example, usage for root-agent decisions does not establish usage for
subagents or compaction. Provider-unavailable reasoning/cache counts cannot earn the corresponding availability claim.
Metrics also retain their provider semantics: do not add reasoning or cached tokens to another count that already
includes them.

Retry relationships in TE1.4 require explicit evidence at the declared boundary. A harness or its own SDK may retry
independently of Gym. Recorded transport attempts do not by themselves establish which turn caused the retry. Hidden
retries within an upstream service are outside the capture boundary.

Malformed command output can be useful turn evidence. Its presence does not mean the command executed, and a parser
rejection followed by recovery does not by itself establish an unhealthy rollout. A harness's completion claim is also
not an authoritative verifier result.

### Examples: combining evidence

Some questions require more than one kind of evidence. The examples below show which claims must be satisfied together
to answer them.

| Information or analysis | Required evidence |
|---|---|
| Exact context used for a turn | TE4.3 selected-response association and TE2.1 request content |
| Tokens used by a subagent | TE6.4 invocation ownership and the relevant TE3 metrics; TE6.2 identifies the parent/child relationship |
| Tokens used for compaction | TE7.4 helper-call references and the relevant TE3 metrics |
| Named parallel-tool timeline | TE5.1 and TE5.5, exercised with parallel execution and comparable timing boundaries |
| Retry cost for a turn | TE1.4 and TE4.4, plus the relevant TE3 metrics |

A compaction event does not imply known compaction cost. Context sizes before and after compaction are not helper-call
usage. Tool timing does not measure CPU utilization; token counts and model latency do not measure GPU utilization.
Resource measurements require their own TE8 claims.

## P0 validation contracts

P0 is the highest onboarding priority. The initial scope covers attempt identity/outcome (TE1.1–TE1.2), retained model
requests/responses (TE2.1–TE2.2), applicable reasoning/media (TE2.3–TE2.4), and individual token metrics (TE3.1–TE3.5).
Model-call ownership can be established through **invocations (TE6.4) or turns (TE4.3–TE4.4)**. The ownership route also
needs invocation identity or turn identity, respectively. It does not require the other parts of TE6.1 or TE4.1 merely
because those families include identity. Parent/child relationships, tool execution, and compaction events are not
additional mandatory P0 claims.

These are proposed validation contracts, not an implemented qualification runner. The JSON Schema bundle contains one
named rollout-record schema per claim:

Each schema uses JSON Schema Draft 2020-12 and accepts unrelated properties. Select the relevant `$defs` entry; the
bundle itself deliberately rejects instances to prevent accidentally treating it as a complete rollout validator.

### Evidence in the rollout file

`evaluator_rollouts.jsonl` contains the evidence. Evidence may appear in different fields depending on the harness and
Gym version. Each TE schema validates a complete rollout record and accepts the supported locations for that evidence.
There is no need to extract or rename fields before validation.

For example, TE3.1 accepts prompt-token counts in **either**
`ng_trajectory.model_calls[].token_stats.prompt_tokens` **or** `ng_model_call_capture.calls[].tokens_in`.
The schema expresses this choice with `anyOf`. The chosen call collection must be nonempty, and every call in it must
have a valid count. Missing or empty collections cannot pass.

### Schemas and supported locations

All named TE schemas take one complete JSON object from the rollout file. The table shows where they look inside it.
These are evidence checks, not replacements for Gym's full artifact schema.

| Claim / schema entry | Supported evidence locations and requirements |
|---|---|
| **TE1.1** | Nonempty `model_call_id` on every call in `ng_trajectory.model_calls[]` **or** `ng_model_call_capture.calls[]`. |
| **TE1.2** | Outcome and termination fields in each trajectory call's `response_metadata` **or** directly on each capture call. HTTP status alone is insufficient; termination needs a known reason/error or `response_status: completed`. |
| **TE2.1** | Each trajectory call's `request` **or** each capture call's `request` / `request_raw`, as a nonempty object or string. |
| **TE2.2** | Each trajectory call's `response` **or** each capture call's `response` / `response_raw`, as a nonempty object or string. |
| **TE2.3** | Reasoning within each trajectory call's `response` **or** each capture call's `response` / `reasoning_content`. Supported response paths are Chat Completions `choices[].message.reasoning_content` / `reasoning`, Responses reasoning items' `summary[].text` / `content[].text`, and Messages `thinking` blocks. Ordinary answer text and token counts do not satisfy this claim. |
| **TE2.4** | Media in each call's parsed `request` or `response`, under either call collection. Supported paths include request `input` / `messages` content blocks, response `output` / `content` blocks, and Chat Completions `choices[].message.content` / `audio`. |
| **TE3.1** | `ng_trajectory.model_calls[].token_stats.prompt_tokens` **or** `ng_model_call_capture.calls[].tokens_in`. |
| **TE3.2** | `ng_trajectory.model_calls[].token_stats.completion_tokens` **or** `ng_model_call_capture.calls[].tokens_out`. |
| **TE3.3** | `ng_trajectory.model_calls[].token_stats.reasoning_tokens` **or** `ng_model_call_capture.calls[].tokens_reasoning`. |
| **TE3.4** | `ng_trajectory.model_calls[].token_stats.cached_tokens` **or** `ng_model_call_capture.calls[].cached_tokens`. |
| **TE3.5** | `ng_trajectory.model_calls[].token_stats.total_tokens` **or** `ng_model_call_capture.calls[].tokens_total`. |
| **TE6.4** — invocation ownership route | Invocation identity and explicit `model_calls` references in `ng_trajectory.invocations[]` **or** `ng_agent_observations.records[]` entries with `kind: agent_invocation`. At least one invocation must reference a call; other observation types do not count as invocations. |
| **TE4.3** — turn ownership route | Turn identity and `selected_model_call` in `ng_trajectory.turns[]`. **This field is proposed, not present in current `TrajectoryTurn` 1.0.** |
| **TE4.4** — turn ownership route | Turn identity and nonempty `model_calls` references in `ng_trajectory.turns[]`. Reference lists alone do not establish complete membership. |

The token schemas require nonnegative integer counts and a nonempty call ID. Call references require either
`model_call_id` or both `model_ref` and `response_id`. Turn identity consists of `task_id`, `rollout_id`, `invocation_id`,
and positive integer `turn_no`. The trajectory branches target `ng_trajectory.schema_version: "1.0"`.

The reasoning schemas check returned text, not hidden or encrypted-only reasoning. Media schemas recognize the listed
native image/audio/media blocks and their required data or references. They do not parse raw JSON strings to look for
reasoning or media, and they do not search arbitrary nested objects. Additional formats need explicit schema support.

An OR branch must supply a complete representation for the tested claim. The schemas do not join partial call records
across attachments. If both attachments are present, agreement between their values and call populations remains an
additional validation check; a schema match alone does not establish that agreement.

### Required assertions and scenarios

| Claim | Assertions beyond field shape | Focused scenario |
|---|---|---|
| TE1.1 | IDs are unique among logical attempts within the rollout; duplicate attachments do not count as new attempts. | Two distinguishable recorded model calls. |
| TE1.2 | Outcome and reason agree with each other and the scripted response/error. `unknown` does not establish availability. Preserve failure evidence without interpreting every failure as an unhealthy rollout. | A normal completion, a length-limited response, and an error or cancellation supported by the integration. |
| TE2.1–TE2.2 | Compare the retained native payload with known fixture fields, including roles, tool arguments/results, and distinguishable content across calls. A generic object/string match alone does not establish fidelity. Preserve malformed returned content when it was actually received. | Two calls with different context and scripted responses, including tool feedback where supported. |
| TE2.3 | Every expected returned reasoning segment survives at its dialect-specific location and remains associated with the correct call. | A fixture that explicitly returns reasoning text; no claim if the provider does not expose it. |
| TE2.4 | Retain the expected media content and metadata. Decode inline data or resolve references in the declared validation environment and compare with the fixture. Check audio format metadata in the request when the output object does not carry it. A nonempty URL or file ID alone is insufficient. | A known image/audio fixture for each claimed modality and direction. |
| TE3.1–TE3.5 | Compare each available count with the scripted provider usage under the documented provider token semantics. Do not add reasoning or cache counts to totals that already include them. | Known usage values, including a reported zero; missing, null, negative, fractional, and string-valued cases. |
| TE6.4 | Every reference resolves to exactly one recorded call. All populated reference fields agree. Each eligible call has one invocation owner; IDs are unique after deduplication. | Multiple calls with explicit invocation ownership; child invocations only when claimed. |
| TE4.3 | The selected reference resolves to exactly one recorded response and agrees with the decision's content/context. A reference list alone does not identify selection. | Distinguishable model responses where the harness makes an explicit decision. |
| TE4.4 | References resolve uniquely, turn identity matches the containing rollout, and `(invocation_id, turn_no)` is unique. Compare attempt membership against the declared scenario and explicit associations; a known incomplete-scope gap prevents a completeness claim. | A basic decision followed by a retry scenario where supported. If compaction is in scope, helper calls need explicit attribution rather than being guessed into a turn. |

Fixtures specify expected retained content; they are not a general independent observer. These checks remain subject to
the declared Gym-routing assumption. Passing a simple scenario does not establish retry, subagent, or compaction
coverage. A complete claim must state which behaviors and call population were exercised.

### Selected response and current schema limits

`TrajectoryTurn` 1.0 has `model_calls`, but no generic discriminator for which response was selected. A list of one or
more references is therefore insufficient by itself to establish TE4.3 across all harnesses. The TE4.3 schema in the
bundle specifies a proposed `selected_model_call` property; it does **not** add that field to Gym's Python models or
change existing artifacts.

Existing producer conventions would need an explicit supported schema branch before they can establish selection with
this bundle. It does not assume that the first, last, or only reference is the selected response. The invocation
ownership route remains available without turn records. TE4.4's reference list similarly needs the membership assertions
above; the schema cannot prove that unrecorded attempts did not occur.

### Checking a rollout file

Select a TE schema and apply it directly to each record. For example, check TE3.1 with a Draft 2020-12 validator:

```python
import json
from pathlib import Path
from jsonschema import Draft202012Validator

bundle = json.loads(Path("fern/assets/trajectory-evidence-p0.schema.json").read_text())
schema = {
    "$schema": bundle["$schema"],
    "$defs": bundle["$defs"],
    "$ref": "#/$defs/TE3.1",
}
validator = Draft202012Validator(schema)
records_checked = 0
with Path("evaluator_rollouts.jsonl").open() as rollouts:
    for line in rollouts:
        validator.validate(json.loads(line))
        records_checked += 1
if records_checked == 0:
    raise ValueError("No rollout records to validate")
```

Change the `$ref` to check another TE. Both storage locations are handled by the schema. A bare token count, an extracted
call object, or an aggregate metrics summary is not a valid input to these rollout-record schemas.

These schemas describe focused test outputs where every call in the chosen collection is expected to supply the tested
evidence. For example, use known usage values for the token scenario, and explicitly returned reasoning for the reasoning
scenario. A mixed run containing failed calls without usage needs an explicit eligibility profile; these schemas do not
silently exclude calls with missing fields. Such calls can be legitimate execution records without satisfying a token
availability test.

Reported zero is valid; missing/null counts, negatives, fractional counts, numeric strings, and booleans fail. Declare
applicability before running a scenario. Provider-unavailable metrics and unexercised modalities cannot earn an
availability pass. Unsupported artifact formats must be distinguished from missing evidence.

Report the claim, scenario, contract version, harness/configuration, and results alongside the additional assertions.
An empty file or empty evidence collection cannot pass. Passing these schemas establishes the supported evidence shapes;
reference resolution, agreement between duplicate copies, expected content, and scope coverage still need the checks
listed above.
