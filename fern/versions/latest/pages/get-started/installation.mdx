<Info>
Python 3.13.14 is required. Refer to [Prerequisites](/get-started/prerequisites) for full system requirements.
</Info>

Install from PyPI for the quickest setup. Clone from git if you need the latest features and environments, or use a NeMo RL container if you intend to train with NeMo Gym and NeMo RL.

<Tabs>
<Tab title="PyPI">

```bash
python3.13 -m pip install nemo-gym
```

Or with [uv](https://docs.astral.sh/uv/):

```bash
uv venv --python 3.13.14 && source .venv/bin/activate
uv pip install nemo-gym
```

The package includes built-in environments and CLI commands. Config and data paths resolve against the package install location automatically. To pin a release: `python3.13 -m pip install nemo-gym==0.7.0`.

Ray isn't included by default. To run environments that use Ray, such as `local_vllm_model` or the SWE agents, install the `ray` extra: `python3.13 -m pip install "nemo-gym[ray]"`.

</Tab>
<Tab title="Git">

```bash
git clone https://github.com/NVIDIA-NeMo/Gym.git
cd Gym
uv venv --python 3.13.14 && source .venv/bin/activate
uv sync --locked
```

Add `--extra ray` to `uv sync` to run environments that use Ray.

</Tab>
<Tab title="Container">

Container choice depends on your NeMo Gym version and model recipe. See [RL Framework Compatibility](/reference/rl-framework-compatibility) for the full mapping.

### Pre-built NeMo Gym image

NeMo Gym publishes a pre-built container to NGC with each release, tagged with the release version (for example `v0.7.0`):

```bash
docker run --gpus all -it --rm \
  -v "$PWD:/workspace" \
  --shm-size=128g \
  --ipc=host \
  -p 8888:8888 \
  -p 6006:6006 \
  --ulimit memlock=-1 \
  --ulimit stack=67108864 \
  nvcr.io/nvidia/nemo-gym:v0.7.0
```

The image's default entrypoint is `gym`, so it drops you straight into the CLI. To get a shell instead, override the entrypoint:

```bash
docker run --gpus all -it --rm \
  --entrypoint /bin/bash \
  -v "$PWD:/workspace" \
  --shm-size=128g \
  --ipc=host \
  -p 8888:8888 \
  -p 6006:6006 \
  --ulimit memlock=-1 \
  --ulimit stack=67108864 \
  nvcr.io/nvidia/nemo-gym:v0.7.0
```

<Note>
The image ships the `enroot` sandbox backend along with `nvidia-container-toolkit`,
so enroot's NVIDIA GPU hook (`/etc/enroot/hooks.d/98-nvidia.sh`) can find
`nvidia-container-cli` and inject GPUs into enroot sandboxes. If your workload
doesn't need GPUs inside enroot sandboxes (for example CPU-only
SWE-bench-style tasks) and you see hook-related errors, you can remove the
hook: `rm /etc/enroot/hooks.d/98-nvidia.sh`.
</Note>

### NeMo RL recipe containers

For NeMo Gym **v0.3.0** with the Nemotron 3 Ultra recipe, build the container from the NeMo RL `ultra-v3` branch (there is no pre-built NGC tag for this pairing):

This command uses Docker Buildx and Docker 23+ syntax. By default, Docker builds for your host platform; add `--platform` only if you need to target a different architecture.

```bash
git clone https://github.com/NVIDIA-NeMo/RL
cd RL
git checkout ultra-v3
# See build options in the Nemotron 3 Ultra guide:
# https://github.com/NVIDIA-NeMo/RL/blob/ultra-v3/docs/guides/nemotron-3-ultra.md#container
docker buildx build \
  -f docker/Dockerfile \
  --target release \
  -t nemo-rl-ultra:latest \
  --build-context nemo-rl=. \
  .
```

For other Gym versions and recipes (for example Nemotron 3 Nano), use the container listed in the compatibility table for that pairing.

## Verify Installation

```bash
gym --version
```

You should see output like:

```text
NeMo Gym v0.7.0
Python 3.13.14
Installation: /path/to/Gym
```

## Component dependency locks

Repository-managed servers have their own `pyproject.toml` and committed
`uv.lock`, enforced by CI. `gym env start`, `gym env prefetch`, and `gym env test`
prefer `uv sync --locked`, including when `uv_venv_dir` places the virtual
environment outside the checkout. Components are not combined into one workspace.
Existing custom components with `requirements.txt` or an unlocked `pyproject.toml`
retain their previous setup, discovery, and onboarding behavior without migration.

A stale component lock fails setup; sync errors do not trigger an unlocked retry.
After intentionally editing managed dependencies, run `uv lock` in that directory
and commit both files. Do not use `--frozen` to hide a stale lock.

If a successful locked sync does not satisfy inherited parent requirements, setup
automatically uses compatibility resolution against the component's dependency
metadata without changing its committed project or lock. This propagates parent-only
sandbox provider plugins (including their exact sources and dependencies) and the
parent's compatible OpenAI version. Ray constraints also act as overrides and apply
only to components that require Ray. The resulting environment is checked again;
unresolvable requirements or source mismatches still fail explicitly. Telemetry
retains its selected extra. No user configuration changes are required.

Wheel installations carry the source metadata needed for relative Gym dependencies;
the installer reconstructs that metadata beside the writable component environment
without modifying site-packages or resolving a different Gym version from PyPI.
Custom indexes and prerelease policy belong in the project used to generate the
lock, not in a startup-only dependency override.

### Benchmark preparation

A dataset that needs additional preparation dependencies declares `prepare_project`
pointing at an isolated project with `pyproject.toml` and `uv.lock`. Gym syncs it with
`uv sync --locked` and imports/runs the preparer in that environment, including its
cache-freshness hook, without installing packages into the running Gym interpreter.

Existing `dataset.prepare_dependencies` configs remain supported unchanged. These
arguments are passed to `uv pip install --python <running Gym interpreter>` before
importing the preparer, including editable installs and requirements-file options.
When nonempty, `prepare_dependencies` takes precedence over `prepare_project`, so
existing config overrides keep their behavior. Use `prepare_project` for a
reproducible locked environment; migrating existing preparation configs is optional.
