Configure your model with the inference backend of your choice.

NeMo Gym uses the [Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create) as its native schema because it natively represents tool calls, multi-turn conversations, and structured outputs. NeMo Gym provides middleware to automatically convert other protocols — Chat Completions and Anthropic Messages — into Responses format.

For training, use a backend that returns token IDs and log probabilities (marked with <Badge minimal outlined>training</Badge> below).

## Embeddings

Every Model Server exposes an OpenAI-compatible `POST /v1/embeddings` route, so memory- and retrieval-based agents can route embedding calls through Gym instead of calling a provider directly. The [OpenAI](/model-server/openai) and [Inference Providers](/model-server/inference-providers) backends implement it as a passthrough to the provider's `/v1/embeddings` (this covers OpenAI, NVIDIA's hosted endpoint, and any other OpenAI-compatible provider); backends without an embeddings model return `501`.

The passthrough merges the server's `extra_body` under the request (a field the request sets wins), replaces `model` with the configured one, and returns the provider's JSON unchanged, so `encoding_format: base64` and providers that omit optional fields such as `usage` both work.

Embeddings calls are not recorded by [model-call capture](/model-server/model-call-capture), which covers only `/v1/responses`, `/v1/chat/completions`, and `/v1/messages`. A call under a rollout's `/ng-rollout/<rollout_id>` prefix still reaches the embeddings route, and it does not mark a token-capture rollout incomplete, because the route is declared non-generating.

An embedding model is usually distinct from the policy model, so wire it as a separate Model Server instance (referenced via `ModelServerRef`), following the existing one-server-one-model pattern.

## Decisions

Every Model Server also exposes `POST /v1/systemone`, the decision API that decision models such as Jev serve; the [Decision Index kit](https://github.com/apolinario/decision-index) documents its question and answer types. A request carries `model`, a `state` (a string or a JSON object) and `questions`, a map of typed questions (`choice` with an option map, `noul` for a yes/no probability, `score` with ordered levels); the reply maps every question key to a typed answer with probabilities. The [OpenAI](/main/model-server/openai) and [Inference Providers](/main/model-server/inference-providers) backends implement it as a passthrough to `{base_url}/systemone`, with the same `extra_body` merge and `model` replacement as embeddings, and return the provider's JSON unchanged. Backends without a decision model return `501`.

Provider errors follow the server's usual upstream status and retry settings, as for embeddings. To let a harness tell a capacity refusal (for example a `422` for too many options) from an error, list that status in `propagate_upstream_http_status_codes` on the OpenAI backend, and also in `upstream_retry_policy.terminal_http_status_codes` when `upstream_retry_policy` retries (otherwise the status is retried until the policy is exhausted and then returns `500`); the Inference Providers backend already returns provider errors unchanged.

Decision calls are not recorded by [model-call capture](/main/model-server/model-call-capture) and, like embeddings, the route is declared non-generating, so a call under a token-capture prefix does not mark the rollout incomplete. Decision rollouts therefore carry no token IDs for training.
