# Harbor Tasks

NeMo Gym runs datasets written in the [Harbor](https://github.com/harbor-framework/harbor) task format directly: a
folder of task folders is both the dataset and the input to `gym eval run`. Harbor is the input format; Gym owns
execution (sandboxes, agents, verification). This page covers the dataset layout, the dataset-level settings Gym
reads, and the three commands that work on such a dataset.

## Dataset layout

```
my-dataset/
├── dataset.toml          # Harbor's dataset file; Gym's settings live in its [gym] table
├── task_data.py          # optional: the TaskData model every task's fields are validated against
├── compose-images.json   # written by Gym at prepare: recorded image configurations (do not edit)
└── hello/                # one task folder per task; the folder name is the task id
    ├── task.toml
    ├── instruction.md
    ├── task_data.json    # optional: the task's own fields, carried in its row's task_data
    ├── environment/      # Dockerfile or docker-compose.yaml, plus files the task needs
    ├── tests/test.sh     # the verifier; writes /logs/verifier/reward.txt or reward.json
    └── solution/solve.sh # the reference solution `gym dataset validate` runs (optional)
```

`task.toml` belongs to the task author and is read-only once fetched. A task runs in a sandbox when it declares
`[environment].docker_image`, or a Dockerfile Gym can run without a build (`FROM` plus `WORKDIR`, `ENV`, `USER`,
`LABEL`, and `RUN` lines that Gym applies in the pulled base image at seed). Each task's rows are materialized
with a digest of the task folder plus the dataset settings applied to it, and the environment server refuses a
task whose digest no longer matches, so edits after materialization are caught rather than silently run.

## `dataset.toml` and the `[gym]` table

Harbor's own tables (`[dataset]`) are left to Harbor. What a dataset needs on top of its tasks goes in a `[gym]`
table, as data: the facts Harbor has no field for (which split the rows enter and under which license, which
harnesses may run them, catalog metadata), defaults that scale every task or set how often an evaluation plays
each one, and per-task overrides written with Harbor's own `[environment]` fields.

```toml
[dataset]
name = "local/my-dataset"   # Harbor requires org/name here
version = "0.1.0"

[gym]
# The split the rows enter: train, validation, example or benchmark. Unset means validation with a license,
# else benchmark, which needs no license and never enters a training split. A license (one of Gym's dataset
# license values) is required for train and validation.
type = "validation"
license = "Apache 2.0"
# The harnesses admitted to run the dataset, by implementation name (responses_api_agents/<name>, what --agent
# resolves to). Unset admits any. The oracle of `gym dataset validate` is always admitted.
allowed_agents = ["terminus_2_sandboxed_agent", "hermes_agent"]
# Catalog metadata, carried into the generated run config: one of Gym's domain values (any other value is refused
# with the values named), and whether the rewards were baselined and reviewed (false unless declared).
domain = "coding"
verified = false
# A committed entry under environments/harbor/ names the hub dataset `gym dataset pull <entry>` fetches into its
# folder (see below). An authored dataset, whose task folders are its own, leaves it unset.
# source = "harbor:terminal-bench/terminal-bench@4.0.0"

[gym.defaults]
# Rollouts per task for an evaluation. `+num_repeats=` on the command line replaces it; it never enters a task's digest.
num_repeats = 1
# Scales every task's [agent] and [verifier] timeout_sec.
timeout_multiplier = 1.0
# Scales cpus, memory_mb and storage_mb of the agent's and the verifier's environments. GPUs never scale.
resource_multiplier = 1.0

# Per-task overrides, keyed by the task folder name. `env` merges over the task's own; every other field
# replaces the task's value. Harbor's legacy spellings (`memory = "4G"`, `allow_internet = false`) are accepted
# and normalized. A key that names no task folder, or an unknown field, fails `gym eval run` and
# `gym dataset validate` with the file and table named.
[gym.tasks."hello".environment]
env = { EXAMPLE = "1" }
memory_mb = 4096
# `inputs` is a Gym extension of `[verifier]`: files under /logs/verifier a Compose sidecar writes during the rollout
# for test.sh to read. The server empties /logs/verifier before a shared verification; these names alone survive.
[gym.tasks."hello".verifier]
inputs = ["actions.jsonl"]
```

`source` is provenance for a committed entry and shapes no task (it does not enter the `datasets:` entry; the
dataset digest covers the file that holds it). The generated run config's `datasets:` entry carries `type`, `license`, `domain`, `verified` and `allowed_agents`
as declared, its top-level `num_repeats` is `[gym.defaults].num_repeats`, and `gym eval run` starts from that split
and repeat count (`+split=` and `+num_repeats=` on the command line replace them); `gym dataset validate` plays each
reference solution once unless `+num_repeats=` says otherwise. None of these keys enters a task's `_ng_digest`; only
`[gym.defaults]` scaling and `[gym.tasks]` overrides do. Every materialized row carries
`task_source` (the dataset folder's name: the parent's for a single task folder target inside a dataset, one whose
parent holds a `dataset.toml` or a `manifest.toml`; a standalone task folder is labelled by its own name) and
`_ng_digest` (the task
folder's digest), and every results row carries them too, with `reward` and, when the verifier's `reward.json`
named no `reward` key, `reward_components`:
the keys that sum to the reward. That mapping is Harbor's optional, task-specific reading of the file, not the shared
multi-reward contract of `BaseMultiRewardVerifyResponse` (a required mapping with the same objective keys on every
task): tasks of one dataset may name different keys and a measured row may name none, so a trainer reads it row by
row and takes the scalar `reward` alone where a row has none; a dataset meant for a fixed-objective trainer such as
GDPO must have every task write the same keys without a `reward` key, which Gym does not pad or check across tasks.
`gym eval run` with a harness outside `allowed_agents` fails before any image is
recorded or built or any server started, naming the harness and the admitted list, and a run config edited to
another harness afterwards is refused at dispatch by the collector's pairing guard. An `example` dataset is not
runnable: that type marks committed smoke-test samples, and both commands refuse it at the same early point, before
any image is recorded or built. `domain`, `verified` and `allowed_agents` stay out of the
metrics sidecar Gym writes beside the rows. The rows' metrics sidecar and the collated split's are removed and
rewritten on every fresh run, because the rows are regenerated from the task folder each time: growing or narrowing
the selection or editing `type` or `license` between two runs of one taskset and harness never fails data
preparation, and `overwrite_metrics_conflicts` is never needed. A `--resume` run keeps the collated metrics, as its
rows are unchanged.

Deployment settings (which sandbox provider, registry credentials, image mirrors) do not belong here: a dataset
must run unchanged on every deployment. Those live in the sandbox provider block of the run configuration. See
[OpenSandbox](/main/infrastructure/sandbox/opensandbox) for the provider's `images` and `setup` blocks.

<Note>
**Harbor round trip.** `harbor add`, `harbor remove` and `harbor sync` rewrite `dataset.toml` from Harbor's
manifest model, which serializes only Harbor's own tables. The `[gym]` table is dropped, so a round trip resets
the multipliers and per-task overrides to their defaults without an error. Keep the dataset in git and restore the
table from there after running one of these commands.
</Note>

## `task_data.py` and typed task fields

A task may carry its own field values in `task_data.json`, a JSON object in its folder (a question and its
expected answer, a tool subset, anything the dataset's own grading needs). The loader writes them into the task's
row under `task_input.task_data`, beside the reserved `_ng_digest` and `_ng_dataset_digest` keys Gym adds, and the
file is part of the task digest, so an edit after materialization is caught like any other.

A dataset that ships `task_data.py` beside `dataset.toml` types those fields. The module exports one Pydantic
model named `TaskData`:

```python
from pydantic import BaseModel, Field


class TaskData(BaseModel):
    question: str
    answer: str = Field(min_length=1)
    difficulty: int = 1
```

Every row is validated against it at the three points it crosses a boundary, with the task named in the error:

- **Materialize.** `gym eval run` and `gym dataset validate` import the module once per dataset and check every
  task folder's `task_data.json` against it before any image is recorded or built (the loaded tasks are checked
  again before a row is written), and refuse the whole dataset when a task's fields do not satisfy the model, when
  a field the model does not declare appears (whatever the model's `extra` setting; `TaskData` is the complete
  description, validated with extras forbidden: the input names pydantic itself reads, aliases, `AliasChoices` and
  `AliasPath` included, are the declared ones, and a key no field consumed, such as a field's name where only its
  alias is accepted or a second spelling of a field already given, is refused rather than ignored), or when
  the module does not import. Values are validated strictly, as JSON: `"3"` does not pass as an `int` nor `"no"`
  as a `bool`, since the row and the verifier's `task_data.json` carry the file's values as written, never the
  model's coerced ones (JSON's own spellings of a type still pass: an ISO string for a `datetime`, an integer for
  a `float`). A validator that raises something pydantic does not wrap (a `KeyError` from a
  lookup) is the same refusal at all three points, with the exception named. A task without `task_data.json` has
  no fields, which is a violation only if the model requires some.
- **Seed.** The `harbor` environment server imports each taskset's module at startup and validates the row it is
  handed before anything is provisioned; a row the model rejects, or whose fields are not the pinned folder's
  `task_data.json`, fails the episode at the seed stage (terminal, never retried). The pin holds for every task,
  one without `task_data.json` included: a row that carries keys beside the reserved `_ng_*` ones for such a task,
  which the server used to accept and ignore, is refused the same way (re-materialize it). A module that does not
  import refuses every episode of its taskset with the import error.
- **Collate.** `gym dataset collate` validates the taskset's rows against the server's reserved keys and the
  dataset's `TaskData` in one report; the dataset's declared fields are not reported as unknown keys.

A dataset without `task_data.py` (every hub dataset) is checked only for the reserved keys and behaves as before.
The module is imported by Gym, so it runs on the host like `dataset.toml` is read there: keep it to the model.
The reserved `_ng_*` keys are never task fields and are refused in `task_data.json`.

## Parameterized tasks

One template folder plus `tasks.jsonl` stands in for many copied task folders. The template is a task folder with
`tasks.jsonl` beside its `task.toml`, one row per task:

```text
my-qa/
├── dataset.toml
├── task_data.py              # optional: types the rows
├── task.toml                 # shared by every task
├── tasks.jsonl               # {"task_id": "q-1", "task_data": {"question": "...", "answer": "4"}} per line
├── instruction.template.md   # {{ task_data.question }} is filled from the row
├── environment/Dockerfile
├── tests/verifier.py         # or tests/test.sh
└── solution/answer.template.md   # the reference answer per row (or a solution/solve.sh)
```

Prepare (`gym eval run`, `gym dataset validate`) renders the template into one plain task folder per row under
`results/harbor/<taskset>/rendered/<task_id>/`. Both commands render there (`gym dataset validate` keeps its rows and
results under `results/harbor/validation/`, but the rendered folder is the dataset root prepare records into, so one
render, one manifest and one built image serve both): a file named `<stem>.template<suffix>` has its
`{{ task_data.key }}` (or `{{ key }}`) placeholders filled and is written as `<stem><suffix>`, every other file is
copied (hidden files under `environment/`, `tests/`, `solution/` and `steps/` included, such as `environment/.env`
and `.dockerignore`, which enter the task digest and reach the sandbox), and the row's fields become the task's
`task_data.json`. The rendered `task.toml` is the template's with `[task].name` rewritten to `<org>/<task_id>` (the
template's org): Harbor keys a dataset on that name (`harbor add` keeps one folder per name), so every rendered task
needs its own; a template without a `[task]` table renders without one (Harbor then names the task after its folder,
and `harbor add --scan` asks for `harbor task update --scan` to add names). Not copied: what the task digest skips (`__pycache__`, `*.pyc`, editor leftovers), the template
root's hidden entries (`.git`, `.venv`; the root `.gitignore` is the exception, since Harbor's packager reads it as the
task's ignore rules, so every rendered task carries the template's), `tasks.jsonl`, the dataset-level files, prepare's
records and the root `README.md`, which describes the template rather than a task (a per-task README is
`README.template.md`). A placeholder that names no field, any other `{{ ... }}` left in a rendered file (`{{ q | upper }}`,
`{{ task-data.q }}`: only the two spellings above are placeholders, and a literal `{{ ... }}` belongs in a file
without the `.template` marker) or a `{{` that never closes (`{{ a }{{ q }}`), two entries that would land under one name (`instruction.md` beside
`instruction.template.md`), a `task_data.json` or `task_data.template.json` at the template root (the rendered
task's `task_data.json` is written from its row; a `tests/task_data.json` fixture below the root is copied like any
other file), a duplicate or
invalid `task_id` (one outside the characters Harbor admits in a task name when the template has a `[task].name`,
or longer than 255 bytes, a folder name's limit), or a row the template's `TaskData` rejects fails prepare with the task named. Rendering is
deterministic, so digests are stable, and a re-render leaves an unchanged task folder in place (it is rendered beside
the output and swapped in only where the content differs), so a server still running an earlier prepare of the same
template keeps finding whole folders. A row may carry its fields flat beside `task_id` instead of under
`task_data`. Placeholders are inserted verbatim: a value that must survive shell quoting (a reference answer with an
apostrophe) belongs in a rendered text file such as `solution/answer.template.md`, not inside a quoted literal of a
`solve.template.sh`. `gym dataset init <name> --parameterized` scaffolds this shape with two rows, a `task_data.py`,
a Python verifier that reads `answer.md` and the reference answer as `solution/answer.template.md`.

## Python verifiers

A task without `tests/test.sh` may grade with `tests/verifier.py`, and a dataset may ship one `verifier.py` beside
`dataset.toml` that grades every task without a `tests/` folder. `tests/test.sh` wins whenever it exists: on the hub a
`tests/verifier.py` beside it is the helper that `test.sh` runs (whole datasets ship that shape), so such a task is a
plain `test.sh` task and the module an ordinary test file. The module defines `verify`, which declares the arguments
it reads and returns the reward:

```python
from pathlib import Path

from nemo_gym.verifiers.files import read_text


def verify(workspace: Path, task_data: dict) -> float:
    answer = read_text(workspace, "answer.txt")
    return float(answer is not None and answer.strip() == task_data["answer"])
```

| Argument | What it is |
| --- | --- |
| `workspace` | The task's working directory inside the sandbox, as a `Path`. |
| `task_data` | The task's own fields (`task_data.json`, a parameterized row). |
| `response` | The agent's final Responses API response, as a dict (`nemo_gym.verifiers.final_text` reads its text). Gym-only: a published Harbor task cannot see it. |
| `state` | `{"workspace": Path}`, the RFC's spelling of the workspace. |

The return value is a number, or a dict with a `reward` key and other numeric keys as metrics; an `async def verify`
is awaited. A `verify` that requires `response` without a default leaves no reward wherever no response exists, which
is every published Harbor task. Helpers:
`nemo_gym.verifiers` (`final_text`, `exact_match`, `numeric_match`) and `nemo_gym.verifiers.files` (`read_text`,
`file_exists`, `text_file_equals`, which stay inside the workspace; `read_text` drops one trailing newline unless told
not to). They are standard library only, and in the sandbox they always resolve to the vendored copy under
`/tests/.ng`: the runner ranks that folder ahead of the verifier's own folder, `/tests` and the image's packages, so a
`nemo_gym` shipped in, or planted into, the task's `tests/` never replaces them.

No verifier code runs on the host. At verification the environment server uploads a shim over `/tests` after the
task's own `tests/`: a `test.sh` that finds `python3` (or `python`) in the image and checks it is 3.8 or newer (an
older one is refused with the version named, exit 127, no reward), the runner, a vendored copy of
`nemo_gym.verifiers`, the task's fields, the agent's response and, for a dataset-level module, the module itself.
The shim runs under the same `timeout` wrapper, user and mode (shared or separate) as any `test.sh`, with the
session's working directory as the workspace, and writes `reward.txt` or `reward.json`. In separate mode the
verifier runs in a fresh container, so a verifier that reads `workspace` (or `state`) needs the task's top-level `artifacts`
to include the working directory (`artifacts = ["/workspace"]` for a task whose `workdir` is `/workspace`), as for
any separate-mode `test.sh` that reads the agent's files; without it the workspace is empty there and the task
scores 0. Separate mode is Gym-only for a Python verifier: Harbor uploads nothing into a separate verifier
container, so the published shim could never reach it, and `publish --harbor` refuses such a task. A verifier that
raises, asks for an argument the runner does not know, or returns something else leaves no reward, which scores as
the usual missing-reward outcome with the runner's stderr in the verifier log. The shim removes any `reward.json` or
`reward.txt` already in `/logs/verifier` before the runner starts (and the runner again before `verify` runs): Harbor
shares that folder with the agent's container for the whole run and reads `reward.json` first, so a file planted there
would otherwise be the verdict of a published task; Gym's server removes the reward files before every upload, Harbor
does not. The image needs a Python 3.8 or newer (the runner and the vendored helpers keep to it); the examples
use `ghcr.io/astral-sh/uv:python3.13-bookworm-slim`.

## `solution/answer.md`

A task verified by its answer rather than by a script ships the reference answer as `solution/answer.md`
(`solution/answer.template.md` in a template, for example `{{ task_data.answer }}`). `gym dataset validate` treats it
as a solution: the oracle copies the file to `answer.md` in the task's working directory (the file the published
`solve.sh` writes there under Harbor's oracle, with `printf '%s' <answer> > answer.md`) and submits the file's text
as its response. It reads the file as bytes (`base64` over the sandbox exec, decoded on the host) rather
than as raw exec output, so a multi-line answer, its blank lines, CR characters and trailing newline reach the working
directory unchanged on every sandbox provider; an image without `base64`, or an `answer.md` that is not UTF-8 text,
is a failed oracle naming the reason. The publishable shape is a Python verifier that reads `workspace / "answer.md"` (for
example `read_text(workspace, "answer.md") == task_data["answer"]`): it grades the same file under `gym dataset
validate` and under Harbor. A verifier that declares `response` grades the submitted text in Gym only;
`publish --harbor` refuses it. A task with `solve.sh` keeps playing the script.

## `gym dataset publish --harbor`

Writes a Gym-authored dataset as plain Harbor task folders that run under Harbor as they are, and refuses, with
the task named, the shapes that could not:

```bash
gym dataset publish --harbor my-qa --output ./published/my-qa
```

| Option | Description |
| --- | --- |
| `TARGET` | A dataset folder, a task folder, or a parameterized template folder. |
| `--harbor` | Required: the output format is Harbor's task folder. |
| `--output` | A new or empty folder for the task folders. |

The rows are expanded and checked against the dataset's `task_data.py` (the check prepare runs: a row `gym eval run`
refuses is refused here too, with the task named, before anything is written), every Python verifier is wrapped in a `tests/test.sh` shim (the same files the environment
server uploads, without the response; a task's own `tests/verifier.py` stays where it is, fixtures beside it, and the
shim runs it there, a dataset-level module travels under `tests/.ng/verifier.py`, and the folder loads back into Gym
as a plain `test.sh` task), every `answer.md` becomes a
`solution/solve.sh` that writes the answer to `answer.md` in the working directory (the file Gym's oracle leaves too,
so a verifier that reads it grades the same in both places), and `dataset.toml` is written without its `[gym]` table
(Harbor's own tables byte for byte; the license, defaults and per-task overrides are Gym's and stay with the source).
What remains has to be a manifest Harbor reads, since `harbor add` takes the dataset branch as soon as the file exists:
a `[dataset]` table with an `org/name` `name` is required (refused otherwise, with or without the `harbor` package),
Harbor's `DatasetManifest` reads the published text as part of the format check, and a `dataset.toml` that held `[gym]`
alone is not published at all (the report says so; the output is then a plain folder of task folders).
`tasks.jsonl`, `task_data.py` and a dataset-level `verifier.py` stay behind. Of each task folder, what the digest
covers is published (`task.toml`, `instruction.md`, `README.md`, `trajectory.json` and the `environment/`, `tests/`,
`solution/` and `steps/` folders, byte-code caches and editor leftovers left out), plus a root `.gitignore`: together
the set Harbor's own packager reads, the `.gitignore` being its ignore rules at `harbor add` and `harbor publish`
(`harbor task init` writes one that leaves `node_modules/`, `.venv/` and `.env` behind at any depth), so a task
published as it is, with no shim and no `solve.sh` written for an `answer.md`, packages to the source's hub content
hash (a shim adds `tests/test.sh` and `tests/.ng/`, and an `answer.md` task `solution/solve.sh`, which Harbor packages
too), unless the source holds a byte-code cache or editor leftover that its own
`.gitignore` does not list: publish leaves those out, where Harbor's packager reads the `.gitignore` in place of its
defaults and would package them (the one `harbor task init` writes names `__pycache__/` and `*.pyc` but no `*~` or
`*.swp`). A root `.env`, `.git/`, `.venv/` or scratch folder is the author's and stays behind, while a hidden file
below the root (`environment/.env`) is task content and travels, and a template's root `.gitignore` reaches every
published instance. A task folder holding a symbolic link among the published paths is refused naming the link:
publish does not follow links (a copy would ship the target's bytes, host files outside the dataset included), as the
renderer and the hub fetcher refuse them. Two Python-verifier shapes are refused
with the task named: a `verify` that declares `response` (Harbor's `test.sh` sees only the container), and a task
whose verifier runs in separate mode (`[verifier] environment_mode = "separate"`, or a `[verifier.environment]`
table, which implies it), because Harbor uploads nothing into a separate verifier container and the shim would never
run there; a `test.sh` task in separate mode publishes as it is. A multi-step task (`[[steps]]`) is copied as it is
with no shim, even under a dataset-level `verifier.py`: Gym grades each step by a `test.sh`, never by a Python
verifier, and a shim would become Harbor's fallback grader for every step without its own script. Two folders that
share a `[task].name` are refused naming both, since Harbor would keep one of them. The folders are written beside `--output` first;
when the `harbor` package is installed, Harbor's own task loader checks every one of them there, and the command
exits 1 for any it refuses, naming each with Harbor's message. They appear under `--output` only once every task
published and passed, so a publish refused by Gym or by Harbor leaves nothing to clean up and a retry into the same
folder works. Gym does not depend on Harbor, and the report says how to install it otherwise (a `harbor` that does
not import is an error naming the problem, not a skipped check, and nothing is published).

`environments/hello_world`, `hello_dataset`, `hello_mcp_tool`, `hello_python_verifier`, `hello_verifier_reuse` and

## `gym dataset init`

Scaffolds a dataset in exactly the shape the loader accepts: `dataset.toml` with a `[gym]` table and one task
(`hello`) with an instruction, a verifier and a reference solution. Harbor requires `org/name` in the manifest,
so a bare name is written as `local/<name>` (and the task as `local/hello`); give `org/name` to choose the org.
The folder is the name without the org, as `harbor task init` does for a task.

```bash
gym dataset init my-dataset                  # ./my-dataset, named local/my-dataset
gym dataset init acme/my-dataset --root ~/work --image ubuntu:24.04   # ~/work/my-dataset, named acme/my-dataset
```

| Option | Description |
| --- | --- |
| `NAME` | Dataset name as `org/name`, or a bare name that becomes `local/<name>`. The folder must not exist yet. |
| `--root DIR` | Where to create the folder (default: current directory). |
| `--image IMAGE` | The task's prebuilt image (default: `python:3.12-slim`). |
| `--parameterized` | Scaffold a template folder (`task.toml`, `instruction.template.md`, `tasks.jsonl`, `task_data.py`, a Python verifier, the reference answer as `solution/answer.template.md`) instead of one task. |

## `gym dataset pull` and committed entries

`gym dataset pull TARGET` fetches a Harbor dataset into `environments/harbor/` of the Gym checkout, or under the
working directory when Gym is installed as a package (`$NEMO_GYM_DATASETS_DIR` when set), and prints where it landed,
its task count and its dataset digest. It is the fetch `gym eval run` and `gym dataset validate` make for a `harbor:`
target, on its own: nothing is prepared, built or run, a folder that was edited by hand, left by an interrupted fetch
of another version, or written for another package is refused in the same words, and a second pull of an unchanged
dataset downloads nothing and says so.

```bash
gym dataset pull terminal_bench_4                                  # the entry's source, into environments/harbor/terminal_bench_4/
gym dataset pull harbor:terminal-bench/terminal-bench@4.0.0        # the same folder: the entry declares this reference
gym dataset pull harbor:terminal-bench/terminal-bench-2-1          # no entry declares `latest`: environments/harbor/terminal-bench-2-1/
gym dataset pull harbor:terminal-bench@2.0                         # a registry dataset (registry.json cached under environments/harbor/.harbor/)
```

| Option | Description |
| --- | --- |
| `TARGET` | `harbor:<org>/<name>[@<tag> \| @sha256:<digest>]` (a package-store dataset), `harbor:<dataset>[@<version>]` (a registry dataset), or the name of a committed entry. An entry under the working root (the checkout, or the working directory of a package install) is pulled into its own folder; an installed entry (one a package install ships under `site-packages`, a project-local `.venv` included) or one committed outside the working root is pulled into `environments/harbor/<entry>/` under the working directory (`$NEMO_GYM_DATASETS_DIR` when set), by its name and by the reference it declares alike, and the installation is left untouched. That copy folder never shadows the installed entry (its `.gym-layer.json` tells it apart): lookup keeps resolving to the entry, so its edited `dataset.toml` reaches the next pull, while an entry of the same name the checkout commits itself keeps precedence. The record file marks the copy: delete it and the folder becomes a user-authored entry that shadows the installed one, so move the folder aside instead; a copy whose installed entry is gone is run by its path. |

A **committed entry** is a folder `environments/harbor/<entry>/` the checkout keeps for one dataset: a README,
deployment YAML overlays and a `dataset.toml` whose `[gym]` table declares `source`, the hub reference its task
folders come from. `terminal_bench_4` declares `harbor:terminal-bench/terminal-bench@4.0.0`; `terminal_bench_2_1`
pins the store's Terminal-Bench 2.1 by content hash, since the store tags it `latest` only. The pulled task
folders and `manifest.toml` are gitignored next to the committed files, and a pull of the declared reference
itself lands in the same folder, so one dataset never lives in two sibling folders. The match is exact:
`harbor:terminal-bench/terminal-bench` (the store's `latest`) is another reference and lands in
`environments/harbor/terminal-bench/`, as any reference no entry declares does. The entry's `dataset.toml` is the
dataset's: its other `[gym]` keys apply as on any dataset and the dataset digest covers it. An entry is pulled into
its own folder when that folder is under the working root (the checkout of an editable install, the working directory
of a package install) and is not installed; an installed entry, one a package install ships under `site-packages` or
another Python installation prefix (shared, often read-only; a project-local `.venv` under the working directory
counts), or an entry committed outside the working root (one a `NEMO_GYM_EXTRA_ROOTS` root commits), is pulled into
`<datasets dir>/<entry>/` with a copy of its Gym layer, as under `NEMO_GYM_DATASETS_DIR` below, and its own folder is
left untouched. That copy folder, told by its `.gym-layer.json`, is never itself an entry: the name and the reference
keep resolving past it to the installed entry, so an edit of the installed entry's `dataset.toml` reaches the next
pull, validate or run, while a folder of the entry's name without that file (one the checkout commits itself) keeps
precedence over the installed one. `gym dataset validate
<entry>` and `gym eval run <entry>` read what the pull left and refuse
task folders in the entry's folder that carry no record of the declared fetch (no `manifest.toml`, or one of another
source, or one recording a fetch of another reference than `source` declares now, since the manifest records the
reference each fetch was made from), with the pull to run, instead of running them as a local dataset under the
entry's name. With `NEMO_GYM_DATASETS_DIR`
set, an entry's tasks live in `<datasets dir>/<entry>/` with a copy of the entry's Gym layer beside them, its
`dataset.toml` and whatever dataset-level `task_data.py` or `verifier.py` it commits, placed before
the first task lands and replaced when the entry's files change (by the next pull, validate or run alike, which
brings the manifest beside the tasks up to date with the copies at once and announces the digest change; a copy
edited in place is refused, never overwritten, however the folder was run since: edit the entry's files. The copies
are checked against a hidden `.gym-layer.json` beside them that records what was placed).

A checkout that fetched `harbor:terminal-bench/terminal-bench@4.0.0` before the entry declared it still holds
`environments/harbor/terminal-bench-4.0.0/`: the reference now lands in `terminal_bench_4/` (fetched afresh; no
folder is moved), the pull and a run of the reference name the old folder while it is there, and it can be moved
aside or deleted. Runs of that reference now carry the entry's name as the taskset, as the rows' `task_source` and in
the `results/harbor/terminal_bench_4/` path, and a dataset digest that covers the entry's `dataset.toml`, so they
differ from runs of the same reference made before the entry declared it. `dataset.toml` is not gitignored in any
folder under `environments/harbor/`, pulled hub folders included, so one written into such a folder by hand (the
`nextjs-performance` override an earlier TB4 README placed in `terminal-bench-4.0.0/`) now shows as untracked: move
its keys into the entry's `dataset.toml` and delete it.

To move an entry to another version, change `source` in its `dataset.toml`, delete (or move aside) only the pulled
task folders and `manifest.toml` in the entry's folder, and pull again; the README, YAML files and `dataset.toml`
stay. A fetch refused because the folder was written for another version of the dataset, or because a task folder no
longer matches the store, says so in the fetcher's words and, when the folder is a committed entry's own, adds what
to delete there. A pull whose fetch downloaded nothing still brings the manifest's digest of `dataset.toml` up to
date, so the digest it reports after an edit of the entry's table is the one the next run carries.

`gym dataset validate <entry>` and `gym eval run <entry> ...` resolve the bare name to that folder without
fetching: an entry not pulled yet names the pull to run, and an existing folder of the same name in the working
directory, or an explicit path, keeps meaning the path for these two commands, which take paths (`gym dataset pull
<entry>` takes none and finds the entry from any working directory). Publishing a dataset to the hub is not part of
this command.

## `gym dataset validate`

Runs each task's reference solution (`solution/solve.sh`) through the task's verifier with an oracle harness and
reports the rewards. Every solution must score 1; the command exits non-zero otherwise. Tasks without a
solution are listed as unvalidated. Validation outputs never share inputs, configs or cached results with an
evaluation run.

```bash
gym dataset validate my-dataset --sandbox opensandbox
gym dataset validate harbor:terminal-bench/terminal-bench@4.0.0 --sandbox opensandbox --only-tasks 'hello-*'
gym dataset validate terminal_bench_4 --sandbox opensandbox      # the committed entry, after `gym dataset pull terminal_bench_4`
```

| Option | Description |
| --- | --- |
| `TARGET` | A task folder, a folder of task folders, a `harbor:<dataset>[@<version>]` hub reference, or the name of a committed entry under `environments/harbor/` after `gym dataset pull`. |
| `--sandbox PROVIDER` | Sandbox provider for the task containers (for example `opensandbox`, `docker`). |
| `--config PATH` | Extra config file to load. Repeatable. |
| `--only-tasks PATTERNS` | Comma-separated task names or globs; only matching tasks are validated. |
| `--exclude-tasks PATTERNS` | Comma-separated task names or globs to leave out. |
| `--limit N` | Maximum number of tasks to validate. |
| `--concurrency N` | Maximum number of concurrent tasks. |
| `--output`, `-o` | Output rollouts JSONL file. |

## `gym eval run` with a task target

`gym eval run` takes the same targets in place of a benchmark name. Gym prepares the dataset (recording the base
images the Dockerfiles resolve against, loading every task, writing the rows and the per-taskset environment
server configuration), then starts the servers and collects rollouts as for any benchmark.

```bash
gym eval run my-dataset --agent hermes_agent --sandbox opensandbox \
  --model-type openai_model --model <model> --model-url <url> --model-api-key <key>

gym eval run harbor:terminal-bench/terminal-bench@4.0.0 --agent hermes_agent --sandbox opensandbox \
  --exclude-tasks 'gpu-*' --model-type openai_model --model <model> --model-url <url>
```

| Option | Description |
| --- | --- |
| `TARGET` | A task folder, a folder of task folders, `harbor:<dataset>[@<version>]`, or the name of a committed entry under `environments/harbor/` after `gym dataset pull` (for example `terminal_bench_4`). `harbor:<org>/<name>[@<tag>]` fetches a package-store dataset. Fetched datasets land in `$NEMO_GYM_DATASETS_DIR` (default `environments/harbor/` in the Gym checkout, or under the working directory when Gym is installed as a package), in the folder of the entry that declares the reference as its `[gym] source` when one does; the fetch stages its clone in a hidden `.nemo-gym-harbor-*` directory there, which discovery skips. An unhidden `nemo-gym-harbor-*` directory left by a fetch interrupted under a `main` build from before this change is refused as a duplicate task ID: delete it once. |
| `--agent`, `-a` | The harness that works in the task sandbox. It must accept `sandbox_access` in its session seed, and the dataset's `[gym] allowed_agents`, when set, must name it; otherwise the run stops before any image is built or server started. |
| `--sandbox PROVIDER` | Sandbox provider for the task containers. |
| `--only-tasks`, `--exclude-tasks` | Select tasks by name or glob. Left-out tasks are listed on stdout. |
| `--skip-unloadable` | Run the loadable subset when some tasks do not load. Without it the run lists them and stops. |

A task folder that does not load is left out of the prepared rows and recorded in `skipped.json` next to them
with the reason; the rest of the dataset still prepares. By default `gym eval run` then lists every task left
out and stops before starting servers. Pass `--skip-unloadable` to run the loadable subset instead; the omitted
tasks stay listed in `skipped.json`. Tasks that declare GPUs run on the environment server's `gpu_sandbox_provider`
block when one is configured. The run's rows, generated configuration and outputs are the same artifacts every
other `gym eval run` produces, so `gym eval aggregate`, `gym eval export` and the health check apply unchanged.

### Run summary and verbosity

Both commands leave a per-run summary beside the rollouts, `rollouts_run_summary.json` (`<stem>_run_summary.json`
when `--output` names another file). It records the command, target, taskset and agent, the dataset's folder,
source and digests, the run's `task_source` (the dataset label the rows were materialized with, beside the one the
result rows carry as `rows_task_source`), the files of the run (rollouts and sidecars, the health check's
reports, the rows and the data processor's files beside them, the collated collector input, run config,
`skipped.json`, `images.json`, the verifier root; `null` for one the run did not write, for the aggregate
metrics when an older file by that name predates this run's rollouts, for the health reports unless the quality
summary records this rollouts file as the one it was computed from (their names are shared by every `--output`
stem in the folder), and for rollouts,
failures and materialized inputs a fresh start never got to clear, such as after servers that failed to start;
such files are named under `stale_files` instead, and their rows are not this run's), and one entry per
selected task and repeat: its status,
reward and `failure_kind`, the verifier's mode, wall time and return code, the relative paths of its verifier log
folder (`test-stdout.txt`, `trajectory.json`, collected `artifacts/`), and the input the row carried (task and
dataset digests, `agent_timeout_sec`, the step for a multi-step task). A path a row names that is missing on
disk is listed under `missing_paths`. The file is written whatever the run did, a validate that found no task
with a `solution/` included (beside the requested `--output`): the tasks a validate left out for want of one are
named under `unvalidated` with the reason (`no reference solution`), beside the tasks that did not load under
`skipped`, so a selection that ran nothing explains why. Start from this file when a score needs checking.

`gym dataset validate ... -v` (or `--verbose`, the `verbose` config key) raises the log level to DEBUG in the CLI
and in the spun-up servers: the Harbor environment server then traces every episode's seed, verifier exit and
score, and the oracle agent its `solve.sh` run.

## Job-level Compose overlay

A run can attach services and tools to every task without touching the tasks, as Harbor's job config does with
`extra_docker_compose`, `agents[].mcp_servers` and an agent's `prompt_template_path`. The environment server's
`compose_overlay` block names Compose `files` merged onto every task's Compose group after the task's own file
(a task with only an image first becomes Harbor's one-service group `main`), `mcp_servers` merged by name with
the task's `[[environment.mcp_servers]]` (the overlay's winning, as Harbor merges the job's) and granted with them,
and a Jinja `prompt_template` with `{{ instruction }}` rendered around the instruction of the episode's first
turn. The files merge as Compose merges `-f` files, `!reset` and `!override` included, and are interpolated with
the task's variables, the deployment's `compose_variables` standing above the task's own sources in them (the overlay
files are the operator's, like the values); their relative paths (`env_file` entries, bind sources) resolve against the
Compose project directory, the task's `environment` folder, as Compose resolves every `-f` file's and Harbor's
`--project-directory` names it, never against the overlay file's own folder; their `env_file` entries may be any
readable file and are read once after the merge, the merged `environment` winning, as Compose reads them. Prepare
reads the block from the configuration the command names, so the overlay's images are recorded with the tasks'
and the merge is checked per task before any sandbox starts; set it in a `--config` file, and swap the backend by
swapping the block. A dataset prepared without the block the server runs with is refused at seed (terminally,
naming the services whose images have no record) until it is prepared again with it, and so is an overlay the
deployment cannot run (the seed runs every check prepare ran on the merged document: the field check, the volume
planner, the services the task's artifacts and collect hooks name, the non-root sidecar `extra_hosts` rule); the
reason names the task's Compose file and the overlay files merged onto it. The template is read and compiled once,
when the block is read.

```yaml
harbor_environment_server:
  environment_servers:
    harbor:
      compose_overlay:
        files: [/path/hindsight-docker-compose.yaml, /path/hindsight-docker-compose.harbor.yaml]
        mcp_servers:
          - {name: hindsight-memory, transport: streamable-http, url: "http://hindsight:8888/mcp/default/"}
        prompt_template: /path/memory_prompt.md.j2
```

See the environment server README, "Job-level Compose overlay", for the merge rules and what the group cannot run.
