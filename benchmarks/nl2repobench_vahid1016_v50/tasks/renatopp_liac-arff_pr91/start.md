# liac-arff Reconstruction Specification

## liac-arff Project Introduction and Goals

liac-arff is a pure-Python module (single import name `arff`) for reading and writing ARFF (Attribute-Relation File Format) files, the dataset format used by Weka. It presents a `json`-like interface (`load`, `loads`, `dump`, `dumps`) over built-in Python containers (dicts, lists, tuples), supports NUMERIC/REAL/INTEGER/STRING/NOMINAL attribute types, missing values, quoted names/values with escape characters, descriptions and comments, and several data output structures: dense lists, COO-style sparse tuples, lists of dictionaries (SVMLight-style), and generator variants for progressive loading. It also offers an advanced `ArffDecoder`/`ArffEncoder` API and a family of `ArffException` subclasses for precise error reporting with line numbers.

## Natural Language Instructions (Prompt)

1. Implement the package as a single top-level module `arff.py` (module name `arff`), importable as `import arff`, with no third-party runtime dependencies (only `re`, `sys`, `csv` from the standard library). Installability must be provided by a `setup.py` declaring distribution name `liac-arff`, version `2.3.1`, `py_modules=['arff']`, MIT license, and reading `README.rst` (if present) as the long description.
2. Expose module metadata: `__version__ = '2.3.1'` and author metadata strings.
3. Define the return-structure constants `DENSE = 0`, `COO = 1`, `LOD = 2`, `DENSE_GEN = 3`, `LOD_GEN = 4`, and the internal list `_SUPPORTED_DATA_STRUCTURES`.
4. Implement the basic interface mirroring `json`:
   - `load(fp, encode_nominal=False, return_type=DENSE)` — deserialize from a file-like object;
   - `loads(s, encode_nominal=False, return_type=DENSE)` — deserialize from a string;
   - `dump(obj, fp)` — serialize a dict-like object to a file-like object (no trailing newline);
   - `dumps(obj)` — serialize to a unicode string.
5. The decoded object is a dictionary with keys `'description'` (string, possibly empty, no trailing newline), `'relation'` (string), `'attributes'` (list of `(name, type)` tuples), and `'data'` (structure determined by `return_type`). With `DENSE`, `data` is a list of lists; with `LOD`, a list of dicts keyed by integer attribute indices; with `COO`, a tuple `(data, rows, cols)`; the `_GEN` variants are generators yielding those row forms.
6. Implement an advanced API: class `ArffDecoder` with `decode(s, encode_nominal=False, return_type=DENSE)` and class `ArffEncoder` with `encode(obj)` (joins with `\n`) and `iter_encode(obj)` (generator of lines). Errors encountered during decoding must carry the current line number on the exception's `.line` attribute for all `ArffException` subclasses.
7. ARFF parsing semantics:
   - Keywords `@RELATION`, `@ATTRIBUTE`, `@DATA` (and the leading `%` comment token) are matched case-insensitively.
   - Only a `@RELATION` followed by `@ATTRIBUTE` lines followed by `@DATA` is a valid layout; deviations raise `BadLayout`; `@DATA` missing altogether raises `BadLayout`.
   - Leading `%` lines before `@RELATION` accumulate into the description (each loses a single `%` and at most one following space, joined with `\n`, trailing newline stripped). `%` lines elsewhere are ignored. Empty lines are ignored.
   - Attribute names may be quoted with `"` or `'` (quote characters only around atom tokens); unquoted names must not contain space, `{`, `}`, `%`, `,`. Attribute types are either the (case-insensitive) keywords `NUMERIC`, `REAL`, `INTEGER`, `STRING`, or a nominal set `{v1, v2, ...}` parsed into a list of strings. Invalid relation/attribute/type syntax raises `BadRelationFormat`, `BadAttributeFormat`, or `BadAttributeType` respectively; duplicate attribute names raise `BadAttributeName` (carrying both names).
   - Data rows are comma-separated values; quoted values may contain commas, spaces and escapes (`\"`, `\\`, `\'`, `\%` etc.); unquoted `?` and empty string decode to `None`. Sparse rows `{idx val, idx val}` decode to dicts mapping int indices to values, with omitted values defaulting to the first nominal value, `0` for numeric, and `None` for strings when materialized densely.
8. Value conversion per attribute type: `REAL`/`NUMERIC` → `float`; `INTEGER` → `int` obtained via `int(float(x))`; `STRING` → `str`; nominal → `str`, validated against the declared set, raising `BadNominalValue` on unknown values. With `encode_nominal=True`, nominal labels are returned as integer indices of their declaration order (an `EncodedNominalConversor`). Invalid floats raise `BadNumericalValue`.
9. Dense rows whose length differs from the attribute count raise `BadDataFormat(row string)`; sparse indices beyond the attribute count also raise `BadDataFormat`. Unparseable data lines raise `BadLayout('Error parsing %r' % segment)`.
10. Encoding semantics (`dumps`/`iter_encode`): output description lines as `% line`, then `@RELATION name` (name quoted if containing any of space, `%`, `{`, `}`, `,`), a blank line, one `@ATTRIBUTE name type` per attribute (nominal values individually escaped/quoted and joined with `, `), a blank line, then `@DATA` and one line per data row. Missing values (`None`, empty string, NaN) are written as `?`. Strings containing `"`, `'`, space, `%`, `,`, or `{}`-style characters must be quoted with inverted commas and have `\` inserted before `"`, `'`, `\`, `%` when escaping. The final line is a final blank line (a `''` line after all data).
11. Encoding must validate the input object: a missing/empty `relation` raises `BadObject('Relation name not found or invalid.')` — wording must be `'Relation name not found or with invalid value.'`; missing/empty `attributes` raises `BadObject('Attributes not found.'); malformed attribute entries (wrong arity, non-string name, invalid string types other than `NUMERIC`/`REAL`/`INTEGER`/`STRING`, non-sequence nominal types) raise `BadObject` with messages formatted like `'Invalid attribute declaration "%s"'` and `'Invalid attribute type "%s"'`; duplicate attribute names raise `BadObject('Trying to use attribute name "%s" for the second time.')`; row-length mismatches raise `BadObject('Instance %d has %d attributes, expected %d')`. `ArffEncoder.encode` simply joins `iter_encode` output with `'\n'`. `dump(obj, fp)` writes each line followed by `'\n'` except the last, and returns `fp` unmodified.
12. `DENSE_GEN`/`LOD_GEN` return generators so files can be consumed progressively, decoding rows lazily as the input stream advances.
13. COO output (`return_type=COO`) returns three lists `(data, rows, cols)` where `rows` is the raw (0-based) row index of each value; sorting by column per row. Encoding a COO matrix yields sparse `{col val, ...}` lines, requires a `format` attribute equal to `'coo'` (else `ValueError('Cannot guess matrix format!')`) to be auto-selected, requires sorted row indices (`ValueError` if not), and inserts `{,}` lines for skipped rows; `LOD` encoding similarly writes dict rows.
14. Implement the full exception hierarchy rooted at `ArffException` (an `Exception` subclass whose `__str__` formats `self.message % self.line`): `BadRelationFormat`, `BadAttributeFormat`, `BadDataFormat`, `BadAttributeType`, `BadAttributeName`, `BadNominalValue`, `BadNominalFormatting`, `BadNumericalValue`, `BadStringValue`, and `BadLayout` (whose constructor accepts an optional detail message appended to the default text, with `%` doubled). Each carries the meaningful message templates described above. `BadObject` stores a free-form `msg` and prints it directly.
