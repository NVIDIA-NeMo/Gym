# Benchmark notes for run-and-babysit-eval

Facts about single benchmarks that the decision steps of [the skill](../SKILL.md) rely on. Read the one
that matches the cell; none of them changes an action in the decision table.

## Agent time limit: Terminal-Bench 4.0

A clean agent timeout is the model's result under the benchmark's own time limit, and a harness that
records its agent deadline as a graded zero has settled it. For Terminal-Bench 4.0, 8 h per task is the
official agent budget (TB 4.0 release notes, "Calibrating resources"), and Gym's default
`agent_timeout_sec` of 28800 matches it. An `agent_timeout` that kept no answer is a saved failure the
recovery policy decides, retried by default; `by_failure_kind: {agent_timeout: fail}` in the benchmark's
`resumable.recovery_outcome_policy` keeps it final instead.

## GDP-PDF: incomplete answers and input limits

A policy answer that comes back incomplete because its output budget was spent is the row's result,
graded as a truncated answer and not regenerated. The HTTP 4xx input-limit negotiation (the DPI step-down
to 72, the image cap, the text-only fallback) is the benchmark's delivery protocol, counted per row
(`document_delivery.input_limit_rejections`, `output_truncation_regenerations`) and in the run facts.
`regenerate_on_incomplete_output=true` regenerates such an answer instead, the earlier behaviour, for
comparison only; with the default (false), GDP-PDF scores differ from runs that regenerated by design.

## Output cut inside an agent episode: Stirrup

A benchmark agent may recover from an output cut inside the same episode, as part of its own protocol: the
Stirrup agent's `truncation_recovery` setting follows a turn that spent its whole completion budget
without a valid tool call with one more turn that has thinking off and a transient instruction not to restart the
analysis, not recorded in the trajectory. The setting is off by default; the GDPVal benchmark config turns
it on. That is the agent's protocol, not a retry of a model failure by recovery;
regenerating an incomplete answer from scratch after a model-side failure stays excluded.

## Benchmarks that read `UNVERIFIED` by construction

A verifier that calls a judge without recording it and saves no recognised grading artifact (`judge_record`,
`rubric_verdict`, `symbolic_match`, `metric_record`, `test_execution`, `environment_reward`,
`repository_test_run`, `substep_tests`, `unit_test_results`, `node_set_f1`, `session_reward_file`,
`guarded_objective_score`, `native_scorer_score`) is unobserved by construction, and its runs read `UNVERIFIED` with
`trial_counts.unobserved_reason` naming the server; so does a run whose saved config does not name its
resources server. A resources server that sets `grading_may_use_uninstrumented_model` (it may ask a model
through an external SDK client) gets no grading record from the shared wrapper, so it is in the same case
unless it saves a recognised artifact. So is an agent that grades its own rollouts with an asynchronous or
model-judged rubric; a programmatic rubric is recorded. `UNVERIFIED` means the answers were
scored, but the grading evidence was not recorded. A resubmit cannot change it, and no flag does: it needs
a server that records its grading. Report it with the reason and do not
present the run as verified. The fix is that server's grading record, in Gym.

## Terminal-Bench 4.0: verifier outcomes, sandbox loss and tool use

A verifier that ran and ended in `VerifierTimeoutError`, `RewardFileNotFoundError`, `RewardFileEmptyError` or
`VerifierOutputParseError` is a scored 0 that stays in the pass-rate denominator, as Harbor counts it. It is
not masked and not re-judged. Count these rows from the verifier diagnostic (subphase `verifier_execution`)
before you compare with a harness that masks verifier faults.

The memory and storage zeros of `sandbox_resource_limit` are read from the provider's report that the
sandbox ended; the match does not check which container in the sandbox was killed. Read the container
named in `detail` before you count a memory zero as the agent's.

A sandbox connection lost during the episode ends the row as `infrastructure_error`, which is retried
within the per-row attempt cap (3 by default). A fault that repeats on every attempt does not become a
score: the rows reach the cap, nothing is eligible for another attempt, and the chain ends itself (driver
exit 76) with the identities listed as exhausted. Fix the sandbox side, then `--recover --extend-attempts N`.

A served chat template that renders no tools, tool results or tool calls still accepts the request. The
mini-SWE agent then gets free-text turns only, stops with `RepeatedFormatError` after a few of them, and the
row is a graded 0 with 0 tool calls. No health check flags a tool benchmark without tool calls, so a run
with this template looks healthy and scores near 0. The same holds for the other agentic benchmarks
(AutomationBench, tau2, the SWE family, GDPVal). Check that the template renders `tools` before you read
such a score; it is a model-configuration result, not a tool-use measurement.

A task may use its whole 8 h agent budget, so a chain cap of one or two hours leaves long tasks unfinished.
Single tasks have needed more than 90 minutes and over 100 model calls, so a one-hour segment, or one of an
hour and a half, cannot finish them: the task is cut, restarts from scratch in the next segment and is cut
again. Give each segment more walltime than the longest task needs.
A row in flight when a segment ends is rerun from the start in the next segment, and after the first such
end each one charges the row an attempt: a continuation can start and end with the same number of saved
rows. Such a run stops at the walltime cap with `complete: false` in `artifacts/rollouts_coverage.json`,
which is a stopped chain, not a model or evaluation failure. Continue it with
`--recover --max-walltime HH:MM:SS --walltime-reason "<why>"`, with a cap that holds at least one full task
budget per segment.

## DeepSWE and the SWE family (OpenCode)

DeepSWE gives the agent 3 h per row (`sandbox_timeout: 10800`), so a segment needs a little more than that
to hold one row plus setup and verification. A shorter `sandbox_timeout` changes the protocol: use it for a
pipe-clean only, never for a score you compare.

A DeepSWE verification that gives no verdict (no `reward.json`, no test report, or no sandbox) is run again
on a fresh sandbox with the same collected patch, up to `inconclusive_verification_retries` more times
(default 2); each rerun attempt is observed as its own failure, so a few `verifier_error` events in a
healthy run are expected. A row still without a verdict after the last attempt is masked as `verifier_error`
with the patch kept. It is re-verified from the saved patch, never regenerated, and never a scored 0.

OpenCode searches with ripgrep. `local_ripgrep_binary_path` is null by default, and in a sandbox without
network access and without `rg` the agent's grep and glob calls fail inside the trajectory ("ripgrep
execution failed"). The rows are graded as usual and no health check flags the failed calls, so the score is
silently lower. Stage the binary through `local_ripgrep_binary_path` when the sandbox has no network.

## GDPVal: wall-time stops and the episode guard

When the Stirrup agent stops at its wall time, verification returns `agent_timeout` with
`mask_sample: true`: the row is not scored, and under the default outcome policy it is retried with a fresh
budget. `by_failure_kind: {agent_timeout: fail}` keeps it final instead. Rows that outlive the environment
server's episode guard (`default_episode_timeout_seconds`, 18000 s in the benchmark config) come back as
`environment_server_failed` and are retried too; in long runs this is common (tens of rows), and most of them
finish on the retry. Report both counts beside the score.

## OSWorld: task time limits and evaluator faults

`task_timeout`, `action_timeout` and `evaluator_error` are runtime-admission reasons that OSWorld records as a
retryable `infrastructure_error`. A row that ran out of task time (7200 s in the benchmark's agent config,
1800 s in the agent default) is run again with a full budget, and an evaluator fault reruns the whole
episode instead of re-judging the saved state. A long run usually retries a few such rows; count them from
the failure records and report them with the score.

## Single-turn benchmarks and MRCR: the episode deadline

Single-turn benchmarks (GPQA, HLE, AA-LCR, MMLU-ProX, WMT24++, LiveCodeBench and the like) run through
`single_agent_turn_legacy`, whose episode deadline is 21600 s (6 h). Under a shorter Slurm segment the
allocation ends first: a hung or runaway call is then cut as `rollout_allocation_ended` (the first end of a
row is free, later ones are charged), not typed as a deadline.

With segments longer than 6 h, as long-context MRCR runs use, the deadline fires: runaway generations run
into the 6 h limit, end as `environment_server_failed`, and are retried. In one long run 63 rows ended there and 60 of them were rerun to
a graded result, so a retried row is a second sample of a generation that ran away once. Count these rows
from the failure records before you compare MRCR scores.

## Benchmarks on the legacy relay: no episode deadline by default

CritPT, SciCode, tau2 and GDP-PDF reach their agents through `legacy_agent`, whose
`default_episode_timeout_seconds` is null, and their benchmark configs do not set it. A hung policy call
there runs until the Slurm segment ends. Set `legacy_agent.default_episode_timeout_seconds` below
`compute.cluster.walltime` when the segment is short, so the row ends with a typed deadline instead of an
allocation end.

## HLE: runaway generations

A call that stops at the length limit with no usable output is the health finding
`model_call_runaway_generation`. On a 100-task HLE run of a mid-size model, 6 rows carried it. These are
model faults: the rows are scored, they appear in `trial_counts.unhealthy`, and they do not count against
the 2% evaluation-side limit. Report them as the model's behaviour, not as an evaluation problem.

## What a healthy small run looks like: GPQA

GPQA with `--limit 20` and 8 repeats is 160 rows. Most rows arrive within a few minutes of the first
request, then a tail of long generations (tens of thousands of output tokens) takes several more minutes;
that tail is normal. At the end, `rollouts_coverage.json` reads `expected 160, successful 160, masked 0,
failed 0, missing 0, complete true`, and the inspect returns `noop` ("every identity is scored or a final
model failure"), `SUCCESS`, evaluation health `PASS` with failure rate 0.0, and `trial_counts` 160 healthy,
0 unhealthy, 0 unobserved.

## Limited-sample proof runs

`--limit N` keeps the first N tasks of the data, each with all its repeats. A limited run's mean is the mean
over those tasks only: compare it with another run on the same tasks (same data, same `--limit`, same
repeats), never with a full run's mean. Agentic proofs with one to three rows (DeepSWE, Terminal-Bench 4.0,
SkillsBench) prove that the path works, not a rate; a 0.0 or 1.0 there says nothing about the model. A
limited run of a long-task benchmark under a small chain cap often ends at the walltime cap with rows
missing (for example 25 of 28 GDPVal rows, or 7 of 8 Terminal-Bench 4.0 rows); that is the cap, and
`--recover --max-walltime HH:MM:SS --walltime-reason "<why>"` continues it.
